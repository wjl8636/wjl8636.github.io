🧠 手把手拆解：一个「Plan-Act-Reflect-Generate」单智能体销售助手是怎么炼成的

🧠 手把手拆解：一个「Plan-Act-Reflect-Generate」单智能体销售助手是怎么炼成的

不再是把大模型当成一个「会聊天的 API」，而是让它真正长出「规划 → 行动 → 反思 → 生成」的完整认知闭环：自己决定用哪个工具、自己扩展检索问题、自己反思还缺什么信息、最后再用一个会「思考」的模型流式地给出答案。本文从一名 AI Agent 开发工程师的视角，深度解析开源项目 SalesPilot（全域知识增强的大模型销售智脑）（github.com/wjl8636/SalesPilot），凡是代码里真实存在的地方，我都会给出文件路径和关键实现，希望能帮你把「单智能体 + 工具调用」从概念落到工程。

0. 本文你会收获什么

这篇文章不是功能清单，而是围绕一个真实项目梳理 Agent 工程的核心知识图谱。我尽量把抽象的概念（Plan-Act-Reflect 循环、工具调用、RAG 混合检索、Reflexion 反思、查询扩展、记忆去重、模型路由、SSE 流式、结构化输出韧性……）都对应到一段真实代码，让你看完能直接用。

涵盖的主题索引：

  • 单智能体的 Plan → Act → Reflect → Generate 主循环
  • 规划模块：LLM 决定用哪个工具 + 自动查询扩展
  • 工具调用：RAG 本地检索 vs Serper 全网搜索的编排
  • 记忆收集与全局去重：多轮检索结果如何喂回生成
  • Reflexion 式反思闭环：让 Agent 自查「信息够不够」
  • 异构模型路由：规划用 qwen、生成用 deepseek-r1（省钱又保质）
  • SSE 实时流式：思考过程与正文分开推送
  • RAG 混合检索：BM25 + 向量加权到底层实现
  • 单智能体 vs 多智能体：为什么这个场景一个 Agent 就够了
  • 工程韧性：坏 JSON 兜底、try/except、真实项目里那些「半成品」

1. 先看一眼：这个系统由什么组成

「SalesPilot」是一套基于 AI Agent 的新能源车企智能销售培训助手，主打场景是「星辰电动 ES9」这台车的销售赋能。它不止有「一个会聊天的模型」，而是把本地文档知识库（RAG）+ 全网实时搜索（Serper）+ 智能 Agent 编排拧成了一条生产线：

能力线 说明 入口
智能问答（Direct Answer） 知识库检索 + Web 摘要 + 历史上下文 → 流式直答 + 推荐问题 POST /ai_search/
智能 Agent（Deep Research） Plan→Act→Reflect→Generate 闭环，自主规划工具与查询 POST /deep_research/
知识库 RAG Elasticsearch 混合检索（BM25 + 向量），覆盖车辆参数/配置/FAQ service/core/retrieval.py
实时 Web 搜索 Serper 接 Google，补充竞品对比、市场动态、用户评测 service/web_search/
文档解析入库 DeepDoc 多格式解析（PDF/Word/Excel/PPT…）+ 向量化入 ES service/core/deepdoc/

其中 /deep_research/ 这条 Agent 线（backend/app/service/agent/agent.py）是全文主线：它是一个单智能体，通过「规划 → 执行 → 反思 → 生成」四个模块自我驱动。我们顺着它的执行顺序逐层拆开。

2. 核心一：Plan → Act → Reflect → Generate 主循环

先看整体的「骨架」——final_answer()（agent.py）把整个 Agent 流程串了起来。我把流程抽成一张图：

                用户提问 user_query
                      │
                      ▼
   ┌─────────────────────────────────┐
   │ ① PLAN  规划模块  agent_plan()    │
   │   LLM(qwen-plus) 决定用哪些工具、  │
   │   把问题拆成 1-2+ 个子查询          │
   └───────────────┬─────────────────┘
                   │  返回 [{action_name, prompts}]
                   ▼
   ┌─────────────────────────────────┐
   │ ② ACT   执行模块  process_actions │
   │   遍历每个 action：               │
   │   · 本地文档搜索 → rag()          │
   │   · 网络搜索     → web_search()   │
   │   结果收集进 memory，做全局去重     │
   └───────────────┬─────────────────┘
                   │  memory（提问+结果）
                   ▼
   ┌─────────────────────────────────┐
   │ ③ REFLECT 反思  reflection()      │
   │   LLM 看已有信息，判断「还缺啥」，  │
   │   至多再扩展 3 个查询               │
   └───────────────┬─────────────────┘
                   │  补充后的 memory_global
                   ▼
   ┌─────────────────────────────────┐
   │ ④ GENERATE 生成  deepseek-r1      │
   │   带思考的销售话术，SSE 流式输出     │
   └───────────────┬─────────────────┘
                   ▼
            用户看到流式回答

对应到 final_answer 的真实代码，整个编排其实是「三段连招」：

def final_answer(user_query):
    # ── ① PLAN：让 qwen-plus 决定用哪些工具、扩展出哪些子查询
    action_tool = agent_plan(user_query)
    if action_tool:
        adjusted_tools = adjust_format(action_tool)   # 把 {action:[多prompt]} 拍平成 一对多
        actions = adjusted_tools
    else:
        actions = []                                  # 无需检索，直接生成

    # ── ② ACT：依次执行每个动作，把结果收集进 memory
    memory_new = process_actions(actions)
    memory_global = list(memory_new)[1:]              # 注意：真实代码会跳过第一项

    # ── ③ REFLECT：反思是否信息不足，不足则再补一轮
    action_reflect = reflection(user_query, memory_global)
    if action_reflect:
        print("回顾内容，进行反思...")
        memory_new = process_actions(actions)         # （见文末「工程观察」）
        memory_global.extend(memory_new)

    # ── ④ GENERATE：把收集到的信息喂给 deepseek-r1 流式生成话术
    final_prompt = f"...参考内容：{memory_global} 用户问题：{user_query}..."
    completion = client.chat.completions.create(model="deepseek-r1", ..., stream=True)
    for chunk in completion:
        ... # 按 thinking / content 分开 SSE 推送

知识点：主循环（Agent Loop）
一个 Agent 的本质是一个循环：感知当前状态 → 决定下一步行动 → 执行并观察结果 → 更新状态 → 再决定。SalesPilot 把它具象成 Plan/Act/Reflect/Generate 四个显式模块，用函数把认知步骤显式建模，好处是每一步都可单独测试、单独替换。很多成熟的 Agent（ReAct、Plan-and-Execute、Reflexion）都是这种「显式步骤」思路的变体。

3. 核心二：规划模块 —— 让 Agent 自己决定「用哪个工具、查什么」

agent_plan()（agent.py）是 Agent 的「大脑前置决策器」。它用一个 system prompt 教模型做两件事：

  1. 工具路由：根据查询内容判断该用「本地文档搜索」还是「网络搜索」；
  2. 查询扩展：把用户的一条原始问题，拆解 / 延伸成 1-2+ 个更细的子查询，覆盖信息死角。
def agent_plan(query):
    prompt = '''
    # 汽车销售助手Agent的Plan模块
    你是一个专业的汽车销售助手的规划模块。你的任务是：
    1. 分析用户的查询:{0}
    2. 基于已有的信息，决定使用哪个工具来查询以获得更多需要的信息（本地文档搜索或网络搜索）
    3. 将用户的原始查询拆解或延伸为1-2个相关问题
    ...
    ## 工具选择规则
    - 当查询明确涉及星辰电动ES9的具体信息、参数、功能或服务时，优先使用**本地文档搜索**
    - 当查询涉及以下情况时，使用**网络搜索**：
      · 与其他品牌车型的详细对比
      · 最新市场动态或新闻
      · 非官方的用户体验或评测
      · 需要实时数据（如当前市场价格波动等）
    ## 输出格式
    [{"action_name": "本地文档搜索", "prompts": ["原始查询", "延伸问题1", ...]}]
    '''
    result = middle_json_model(prompt)     # 强制 JSON 输出
    json_list = extract_json_content(result)
    structure_output = json.loads(json_list)
    return structure_output

为什么这很关键？ 规划模块相当于 Agent 的「手电筒」——它决定了后续 RAG / Web 搜索的查询质量。如果直接拿用户那句口语化问题去搜，ES 的 BM25 可能召回很差；而这里把「星辰电动ES9和特斯拉Model Y相比怎么样？」扩展成「ES9 的技术规格和配置」「Model Y 最新规格和价格」等检索友好的子查询，召回率立刻不同。

3.1 结构化输出的三层防御

规划模块的输出是 JSON，而大模型吐 JSON 常常是残缺的。这里做了三层防御（agent.py）：

result      = middle_json_model(prompt)          # ① 请求时声明 response_format="json_object"
json_list   = extract_json_content(result)       # ② 正则提取首个"["到末尾"]"之间的内容
structure_output = json.loads(json_list)         # ③ 正规 JSON 解析

其中 extract_json_content 用 r'(\[[\s\S]*\])' 把「模型多嘴输出的包裹文字」剥掉，只留 JSON 数组。而 middle_json_model 强制 response_format={"type": "json_object"}，用「请求端约束 + 响应端兜底」双保险压低解析失败率。

知识点：结构化输出的韧性（Robustness）
生产级 Agent 不能赌 LLM 每次都输出完美 JSON。标准套路是：请求约束（json_object / JSON Schema）+ 响应解析器（剥代码块 / 取最外层括号）+ 失败兜底（返回 None / 用 thought 补抽）。这一层防不住，Agent 就没法稳定地驱动工具。

3.2 一个值得品的小设计：adjust_format

规划模块返回的结构是「一个 action 配多个 prompts」，但执行时希望「每个 action 只干一件事」。于是 adjust_format 把它拍平成 [{action_name, prompt}] 的一对一列表：

def adjust_format(original_data):
    adjusted_data = []
    for item in original_data:
        for prompt in item['prompts']:
            adjusted_data.append({'action_name': item['action_name'], 'prompt': prompt})
    return adjusted_data

工程启示：数据契约的适配层。LLM 倾向于输出「分组」结构，而执行器更适合「扁平」结构，中间加一层无副作用的纯函数做转换，让上下游各用自己舒服的格式。这是 Agent 工程里被低估但极高频的模式。

4. 核心三：执行模块 —— 让 Agent 长出「手」，把工具结果收进记忆

process_actions()（agent.py）是执行器。它遍历规划好的每个动作，根据 action_name 派发到两个工具之一，并把结果结构化地收进 memory：

def process_actions(actions):
    memory = []
    for action in actions:
        action_name = action['action_name']; prompt = action['prompt']
        try:
            if action_name == '本地文档搜索':
                result = rag(prompt)                 # → RAG：ES 混合检索
            elif action_name == '网络搜索':
                result = web_search_answer(prompt)   # → Serper：Google 实时搜索
            else:
                result = f"未知的动作类型: {action_name}"
            memory.append({"提问": prompt, "结果": result})   # 工具结果进记忆
        except Exception as e:
            print(f"--------{action_name}检索失败: {e}-----------")   # 失败不中断
            continue
    deduplicated_memory = deduplicate_memory_global(memory)  # 全局去重
    return deduplicated_memory

这里的几个工程点很实在：

  • 单一入口的 try/except：单个工具失败只影响自身，不会让整条 Agent 链路崩掉，而是跳过继续。
  • 结果是「有结构」的：memory 里每条是 {"提问": prompt, "结果": result}，这形成了「这个查询 → 查到什么」的可追溯记忆，喂给反思和生成。
  • 执行与决策解耦：规划只产出「意图 + 查询词」，执行只负责「调工具、拿结果」，两层可以各自替换。

4.1 工具一：RAG —— Elasticsearch 混合检索

rag() 薄薄一层，真正干活的是 service/core/retrieval.py 里的 Dealer：

dealer = Dealer(dataStore=es_connection)
def retrieve_content(indexNames, question):
    results = dealer.retrieval(
        question=question,
        vector_similarity_weight=0.6,   # 向量与关键词的加权：0.6 偏向量
        page=1, page_size=5,            # 取 Top-5 片段
    )
    # 提取 content_with_weight 等字段

知识点：混合检索（Hybrid Search）
只用向量（语义）或只用关键词（BM25）都不够——vector_similarity_weight=0.6 表示最终得分是向量相似度与词项相似度的加权和。这样既懂「充电快不快」的语义，也保得住「最大功率 150kW」这种精确匹配。这是 RAG 召回质量的关键调参旋钮。

4.2 工具二：Web 搜索 —— Serper 接 Google

web_search_answer() 调 service/web_search/web_search.py，通过 http.client 打 Serper，把 organic 结果抽成 {title, url, content} 的 snippets：

def serper_search(q="apple inc", hl="zh-cn", num=20):
    return make_request(q, hl, "/search", num)

def process_search_results(search_results):
    snippets, questions = [], []
    for result in search_results['organic']:
        snippets.append({"title": result['title'],
                         "url": result['link'],
                         "content": result['snippet']})
    for q in search_results['peopleAlsoAsk']:
        questions.append(q['question'])
    return snippets, questions

知识点：Agent 的「双知识源」。RAG 管私有且静态的资料（自家车的参数/FAQ），Web 搜索管公有且动态的信息（竞品对比、最新价格、用户评测）。Agent 的价值之一就是把这两种互补的知识源，按查询场景自动分发给正确的工具——这是大模型「时效与私域」两个短板的同时解法。

5. 核心四：全局去重 —— 别把重复内容喂给模型

多轮、多查询检索后，memory 里很容易出现内容重复（同一个 ES chunk 被不同的扩展查询命中多次）。deduplicate_memory_global() 会基于 content_with_weight 字段做全局去重：

def deduplicate_memory_global(memory):
    seen_content = set()
    for memory_item in memory:
        for item in memory_item['结果']:
            content = item['content_with_weight'].strip()
            content_hash = hash(content)          # 用 hash 避免长字符串比较开销
            if content_hash not in seen_content:
                seen_content.add(content_hash)    # 首见 → 保留
            else:
                print(f"发现重复内容，已过滤: {content[:50]}")

知识点：上下文预算管理（Context Budget）
大模型的上下文窗口有限，而检索是「廉价的、大量的」。把重复 / 低价值内容在进上下文前清掉，等于给生成模型留出了更宝贵的「有效信息预算」，也直接降 token 成本。这是所有检索增强型 Agent 的必修课。

6. 核心五：反思模块 —— 让 Agent 自查「信息够不够」（Reflexion 味道）

一轮执行拿到 memory_global 后，Agent 并没有急着生成，而是先进入 reflection()——拿着「已有的信息」再问一次 LLM：还缺不缺、要不要再补查。这就是学术上 Reflexion（反思） 范式的工程化落地：

def reflection(user_query, memory_global):
    prompt = '''
    你是一个专业的汽车销售助手的规划模块。你的任务是：
    1. 分析用户的查询:{0}
    2. 基于已有的信息，是否还需要延伸再进行查询
    ## 目前已有的信息: {1}
    ## 重要！至多再扩展不超过3个查询，如果需要扩展则按格式输出，如果不需要则返回 None
    [{"action_name": "工具名称", "prompts":'一个扩展问题'}]
    '''.format(user_query, memory_global)
    result = middle_json_model(prompt)     # 强制 JSON
    return json.loads(extract_json_content(result))

三个关键点：

  • 把「评估信号」显式回写：memory_global 是上一轮行动的产出，反思模块读取它来决策，形成「行动 → 观察 → 反思 → 再行动」的闭环，而不是无脑重跑。
  • 有界迭代：prompt 里明确「至多再扩展不超过 3 个查询」，给循环一个硬性上限，防止 Agent 陷入无限补查。
  • 失败了不阻塞：即使反思输出的 JSON 解析失败，structure_output = None，主流程仍能继续走到生成——容错优先，绝不让反思环节卡死整个链路。

知识点：反思型循环（Reflexion）
关键词是把上一次行动的结果当作下一次决策的输入，并显式设定迭代上界。比起「一条路走到黑」的普通 ReAct，反思让 Agent 在信息不足时主动补齐；而 max_iterations 一类的定量，则是保证系统一定终止、不烧光预算的刹车。

6.1 一个真实的「工程观察」

在 final_answer 的反思分支里，有一处典型的『半成品』代码——它把反思的返回值 action_reflect 仅用于 if 判断，但内部补跑时用的仍是最初的那批 actions：

action_reflect = reflection(user_query, memory_global)
if action_reflect:
    memory_new = process_actions(actions)   # ← 跑的还是原始 actions，而非反思扩展出的新查询
    memory_global.extend(memory_new)

也就是说：「反思 → 扩展新查询」的意图已经在 prompt 里设计好了，但执行侧还没把反思输出的新查询真正接进去。这恰恰是很多 Agent Demo 会踩的中间态——规划/反思的 prompt 已经很丰满，落地执行却还差一步。

工程启示：读源码时，别只盯着「宣称的能力」，要看「实际的执行路径」。 对一个做 Agent 的人而言，能一眼识别这种「prompt 已设计、执行未接上」的断层，是很好的排障直觉。

7. 核心六：生成模块 —— 带思考的销售话术，SSE 流式输出

收集够信息后，final_answer 构造最终 prompt——一句很有「销售味」的系统设定：

final_prompt = f'''
你是一个星辰电动ES9的智能销售助手，负责根据用户的问题和提供的参考内容生成回答。
基于提供的参考内容进行回答，如果原文没有参考内容,根据你自己的知识进行回答。
你需要用有打动力的销售的语言进行输出，突出星辰电动的优势。
参考内容：{memory_global}
用户问题：{user_query}
'''

然后换用 deepseek-r1（一个带显式「思考链」的强模型）流式生成，并且把「思考过程」和「正式回答」分开推送：

completion = client.chat.completions.create(model="deepseek-r1", stream=True, ...)
for chunk in completion:
    delta = chunk.choices[0].delta
    if delta.content:                       # 正式回答
        yield sse("assistant", delta.content, thinking=False)
    else:
        yield sse("assistant", delta.reasoning_content, thinking=True)  # 思考过程

这里有个很妙的区分：delta.content 是给用户看的话术，delta.reasoning_content 是模型的内心推理。前端拿到 thinking: true/false 就能把「推理过程」和「正式回答」渲染成两种不同的气泡——这是让 Agent 看起来「真的在思考」的产品级细节。

知识点：异构模型路由（Model Routing）
规划/反思阶段用 qwen-plus（便宜、快，只需结构化 JSON 输出），生成阶段用 deepseek-r1（贵、强，长文本 + 会思考）。用「角色 × 模型」的矩阵做调度，是规模化 Agent 的成本结构核心：把便宜模型的活交给便宜模型，把聪明模型的活留给聪明模型。

8. 另一条线：Direct Answer —— RAG + Web 的「直答」管线

除了 Agent 线，项目还有一条更轻的 POST /ai_search/（router/ai_serarch_rt.py），它走的是经典 RAG 直答流程：

用户问题 → 知识库检索(retrieve_content)
        → Web 搜索摘要(store_and_query_snippets)
        → 拼 DirectAnswerPrompt（含历史上下文）
        → deepseek-r1 流式回答
        → 推荐问题 + 图片/视频搜索 + 落库

关键差异：

  • 无规划、无反思：直接「查一遍就答」，比 Agent 线快但浅。
  • 返回更丰富：除了正文，还流式回传 documents、web_search、recommended_questions、image_results、video_results，前端能渲染出「引用文档」「推荐问题」「相关图片视频」一整屏。
# get_chat_completion 里，按阶段 yield 不同事件
yield sse({"documents": retrieved_content})        # 知识库引用
yield sse({"web_search": snippets})                # 网页摘要
yield sse({"recommended_questions": related})      # 推荐问题
yield sse({"image_results": ...})                  # 图片
yield sse({"video_results": ...})                  # 视频
yield "event: end\ndata: [DONE]"                   # 结束

知识点：SSE 事件协议（Event Protocol）
一个健壮的大模型产品必须把「不同类型的内容」做成结构化事件流，而不是只吐一段纯文本。前端才能据此渲染引用卡片、推荐列表、富媒体。event: message / event: end 这套约定，让后端组装与前端渲染解耦。

9. 单智能体 vs 多智能体：为什么这个场景「一个 Agent 就够了」

如果你看过我上一篇文章（六专家协奏的多智能体系统），一定会问：SalesPilot 为什么不搞多智能体？

答案在任务复杂度：

维度 六专家系统 SalesPilot
任务形态 开放式长研究（规划/检索/分析/写作/审校） 单轮销售问答（查资料 → 说话术）
认知子任务 多个正交子任务，需分角色 一个线性闭环：查→反思→答
Agent 数 6 个角色分治 1 个（Plan/Act/Reflect 是同一 Agent 的四个步骤）
状态共享 多 Agent 共享大 ResearchState 单 Agent 内部 memory 传递
协作成本 高（交接契约、阶段路由） 低（无跨 Agent 通信）

判断标准很朴素：如果任务能被「一个 Agent 的多个顺序步骤」覆盖，就不值得引入多 Agent 的编排与通信成本。 多智能体不是银弹，它解决的是「并发 + 分治」问题；而单智能体擅长「顺序 + 聚焦」。SalesPilot 把 Plan/Act/Reflect 做进同一个函数里，已经足够支撑销售话术生成，反而更轻、更好调试。

知识点：单智能体 vs 多智能体

  • 单智能体：一个模型 + 一个工具集，靠循环自我驱动。优点：简单、便宜、易调试；缺点：无法并行、上下文单一。
  • 多智能体：多个角色各持一个模型/工具，共享状态协作。优点：可并行、认知负载分摊；缺点：编排与通信成本高。
    选型的核心是任务本身是不是「可拆分的多角色任务」。 起步永远先做单智能体，当任务确实需要「分工 + 并行」再拆多智能体。

10. 工程韧性：那些让 Agent 真正能用的「脏活」

聊了这么多「聪明的部分」，最后必须强调——真正拉开生产级与 Demo 差距的，都是不起眼的工程韧性：

10.1 坏 JSON 的层层兜底

  • 请求端：response_format="json_object" 强制。
  • 解析端：extract_json_content 用正则 r'(\[[\s\S]*\])' 剥掉模型多嘴的文字。
  • 失败端：try/except: structure_output = None，解析失败就让规划/反思返回 None，主流程继续。

10.2 单工具失败不拖垮全局

process_actions 里每个 action 独立 try/except，检索失败只打印堆栈、continue 跳下一个，绝不中断整条链路。

10.3 有界迭代

反思模块 prompt 明写「至多扩展 3 个查询」，加上 JSON 解析失败返回 None，从两个维度保证 Agent 一定有限步终止。

10.4 领域绑定的知识库

规划 / 反思的 prompt 里都枚举了「星辰电动ES9」的 18 个章节（产品概述 / 技术规格 / 驱动系统 / 电池与充电 / 智能座舱 / 智能驾驶 / 安全系统 / 竞品对比 / 用户评价……），把领域先验直接写进 prompt，让 Agent 的工具路由和查询扩展始终「围着车转」，而不是泛泛而谈。

11. 架构全景回顾

把 Agent 线 + 直答线 + 基础设施拼起来，整个系统的架构就是：

┌────────────────────────────── 前端（React + Vite，实时渲染 SSE 事件流） ──────────────────────────────┐
│  思考过程 · 正式回答 · 引用文档 · 推荐问题 · 图片/视频 · 会话历史                                    │
└──────────────────────────────────────────────────────────────────────────────────────────┘
                                      ▲  SSE: event: message / event: end
┌──────────────────────────────────────────────────────────────────────────────────────────┐
│                            FastAPI 后端（router/ai_serarch_rt.py）                          │
│                                                                                          │
│  /deep_research/  →  单智能体 Agent 循环（service/agent/agent.py）                          │
│     PLAN(agent_plan, qwen-plus) → ACT(process_actions, 多工具)                              │
│        → REFLECT(reflection, qwen-plus) → GENERATE(deepseek-r1, SSE)                      │
│  /ai_search/      →  Direct Answer（RAG + Web 直答管线）                                     │
└───────┬──────────────────┬─────────────────────┬──────────────────────────────────────────┘

   Elasticsearch      Serper / Google       PostgreSQL

   DeepDoc 文档解析   （+ 图片/视频搜索）      用户/知识库

12. Agent 工程师的几点心得

  1. 先用「主循环」把认知步骤显式建模。 Plan→Act→Reflect→Generate 四步拆开，每一步都可单独测、单独换，比一个糊在一起的「提示词调用」好维护一个数量级。
  2. 查询质量决定召回质量。 用户口语问题直接去检索往往很差；规划阶段让 LLM 拆子查询，是 RAG 型 Agent 最容易被忽略的提效点。
  3. 结构化输出要有三层防御。 请求约束 + 响应解析 + 失败兜底，缺一层，Agent 就没法稳定驱动工具。
  4. 按认知成本路由模型。 规划用便宜的 qwen、生成用会思考的 deepseek-r1，角色 × 模型矩阵是省钱又保质的关键。
  5. 永远有迭代上界。 反思 / 重试循环都要有「至多 N 次」的硬限制，否则灾难。
  6. 别迷信多智能体。 任务是「顺序 + 聚焦」就用单智能体，是「并发 + 分治」才拆多智能体。一个能自我驱动的 Agent，通常比一群不会接活的 Agent 强。
  7. 读源码要看执行路径，而非宣称能力。 SalesPilot 的反思 prompt 已设计得很丰满，但执行侧还没真正用上反思产出的新查询——能识别这种「断层」，是 Agent 排障的关键直觉。
