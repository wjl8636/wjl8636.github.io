🛠️ 手把手拆解：把 Agent 的诊断能力「训」进小模型 —— Cold Start SFT + GRPO 的工程实践

2026/9/10 Agent 工程实践 RL GRPO SFT veRL Qwen 后训练

🛠️ 手把手拆解：把 Agent 的诊断能力”训”进小模型 —— Cold Start SFT + GRPO 的工程实践

不再把 Agent 系统的决策底座吊死在一个外部闭源模型上，而是用开源小模型 + 后训练把它换下来、还撑得起同一套系统。本文从一名 AI Agent 开发工程师的视角，深度解析开源项目 aiops-agentic-rl（github.com/wjl8636/aiops-agentic-rl），凡是代码里真实存在的地方，我都会给出文件路径和关键实现，希望能帮你把「Agentic RL」从概念落到工程。

0. 本文你会收获什么

这篇文章不是训练报告，而是围绕一个真实项目梳理 Agentic RL 工程的核心知识图谱。我尽量把抽象的概念（两段式后训练、reward 工程、anti-hacking、veRL 适配、数据管线……）都对应到一段真实代码，让你看完能直接用。

涵盖的主题索引：

  • 路线选择：为什么是 Cold Start SFT + GRPO 两段式，而不是 RL from scratch
  • Reward 工程：零改造复用生产 hook，三层 reward 设计
  • Anti-hacking：四类结构性防线，不是事后 patch
  • veRL 系统工程：单卡 A800 跑通 15 epoch GRPO 的”同居”问题
  • SSH 反向隧道：云 GPU 怎么桥回真实 docker 环境
  • 数据管线：63 条轨迹 → 667 条样本的完整链路
  • 诚实标注：每个数字都有文件级证据链

1. 先看一眼：这个系统由什么组成

「aiops-agentic-rl」是上一篇文章那个 AIopsAgent 的后训练配套项目。它要回答一个现实拷问：生产系统总不能永远依赖一个外部闭源模型吧？成本、延迟、数据边界都是问题。

于是这个项目把 Qwen3.5-9B 从零训成能撑起同一套诊断系统的模型——不是拿 9B 去”超越” Opus，而是证明”开源小模型能撑同一套 Agent 系统”。

能力线 说明
两段式后训练 Cold Start SFT（LLaMA-Factory + LoRA）→ GRPO（veRL 0.6.0 + vLLM colocate + fsdp2）
Reward 工程 零改造复用生产 hook，三层 reward（step / credit / outcome）直接相加
Anti-hacking 双源覆盖门、evidence 可追溯、real-health-only、组方差降采样
veRL 适配层 verl_adapter/ 把 Agent 工具面注册成 BaseTool，SSH 反向隧道桥回真实环境
数据管线 四路合成种子 + 教师采集 + 拒绝采样 + 前缀拆分 + 双层去重
可复现 每个数字都有文件级证据链，YAML 里标 [VERIFIED] / [ASSUMED] / [JUDGMENT]

其中以 Reward 工程、Anti-hacking、veRL 系统工程 最具 Agentic RL 代表性，本文作为主线展开，最后补上数据管线与可复现。

2. 核心一：路线选择 —— 为什么是 Cold Start SFT + GRPO 两段式

一眼看过去，这个问题的表面答案是”Agentic RL 用 GRPO”。但直接 RL from scratch 是训不动的。

9B 底座直接跑 Agent 场景，工具调用格式（XML 还是 JSON？参数怎么写？）和白名单命中都不成熟——rollout 里绝大多数样本根本拿不到 hook 的正向 reward，一组 6 条 rollout 全失败，group advantage 接近零向量，GRPO 训不动。这是定性论断，来源是 Cold Start SFT 阶段观测到的底座工具调用完成率极低。

所以走学术界主流的单引擎两阶段路线（DeepSeek-R1、Qwen-Coder 都是这条）：

  1. Cold Start SFT：用 Opus 在真实环境采集通过轨迹，按 tool_call 边界前缀拆分，教会小模型”工具调用格式 + 白名单命中 + 能走完整条轨迹”；
  2. GRPO：在 SFT checkpoint 基础上做强化学习，学”决策质量”——什么该查、查到了什么信号、该不该下诊断。

选 Qwen3.5-9B 有三个理由：单卡 A800-80GB 塞得下（LoRA 只加 ~200MB 训练参数）；容量足够学诊断决策（4B 换显存但 route 判定天花板明显更低）；混合注意力架构（full + linear attention）给 LoRA 覆盖提出了一个硬约束——必须覆盖全部 12 个 Linear 层 proj（grpo/verl_config/aiops_grpo.yaml 里的 target_modules）：

target_modules: [q_proj, k_proj, v_proj, o_proj, gate_proj, up_proj, down_proj,
                 in_proj_qkv, in_proj_z, in_proj_b, in_proj_a, out_proj]

只挂 qkvo 等于半个模型不训——混合注意力架构下，GatedDeltaNet 那几条 in_proj_* 链路不参与训练，整个线性注意力分支就冻结了。

为什么不用 PPO？PPO 需要独立 critic 学价值函数，同规模 critic 多吃约 40% 显存，单卡塞不下 rollout + fsdp2 + critic 同时。GRPO 用组内相对优势 A_i = (R_i - μ) / σ，同 prompt 抽 6 条 candidate 天然算 baseline，省掉 critic。为什么不用 DPO？Agent 轨迹的”偏好”很难定义——“这条 5 步定位比那条 8 步好”到底好在哪一步？信号太糊，而我们的 reward 是 step-wise 的，天然适配 policy gradient。

知识点：Cold Start 是 Agentic RL 的必要前戏
工具调用格式都还没学会的底座，直接上 RL 只会得到”整组失败 → advantage 塌陷”。先用 SFT 把”格式 + 白名单命中 + 完整轨迹”教会，RL 才有可学的高质量决策空间。这是 R1 / Qwen-Coder 同款路线的工程本质。

3. 核心二：Reward 工程 —— 零改造复用生产 hook，是最有差异化的设计

Agentic RL 的 reward 常见做法都不好用：人工偏好标注成本极高，rule-based 易 hack，env-based 需要能跑真实环境。这个项目的答案是一个别处很少见的组合：env + rule，且零标注成本——真实环境用 AIops-agent 的 docker-compose，rule 部分完全复用生产 hook。

这个”零改造复用”贯穿整条链路，没有为训练重写一份规则：

  • 采集/数据端（data/cold_start/collect_trajectories.py）：_load_aiops_core() 直接加载 AIops-agent 的 config / remediation / schema / guard_diagnose_ops，用包装的 _make_recording_hook() 真实调用生产 guard_diagnose_ops，并把判定作为 hook_decision 记进轨迹；
  • rollout 端（verl_adapter/rollout_worker.py / mock_tools.py）：route_through_real_hook() 把每条采样工具调用送到真实的 guard_diagnose_ops（_repo_paths.load_real_hook_modules() 直接从 AIops-agent import），allow/deny/passthrough 原样进 Step.hook_decision；
  • reward 重算端（grpo/verl_reward_adapter.py）：重算 hook 判定时直接 import 生产 agent.core.remediation.classify_command——同一个纯函数，不复制逻辑。

生产 hook 迭代加了新 deny 规则，训练 reward 立即跟着走。这让训练/生产口径永远一致——训练时 policy 学到的”哪些命令合法”和生产部署后面对的是同一套规则。Agentic RL 领域大多数项目训练用一套 rule、生产用另一套，这个设计是稀缺的。

Reward 分三层，都是直接相加、没有 mixing 系数（grpo/reward_router.py 的 compute_trajectory_reward）：

第一层 step_reward（每步 7 条稠密信号，reward/step_reward.py）：

信号 幅度 含义
tool_call_schema_valid +0.05 这步工具调用 schema 合法
hook allow +0.10 命令命中白名单且目标授权
hook deny -0.15 命中但未授权 / 写变更被拦
observation_advances_diagnosis +0.10 这步覆盖到新的 signal_type
repeat_no_new_info -0.15 重复调用无新信息
evidence_fabrication（末步） -0.50 编造证据
schema_fallback_unrecovered（末步） -0.20 schema 兜底后仍未恢复 
def compute_step_rewards(traj: Trajectory) -> list[float]:
    """Per-step step-level reward, len(result) == len(traj.steps).
    Each step's reward = the four genuinely-per-step signals (schema valid,
    whitelist allow, whitelist deny, observation-advances, repeat-no-new-info);
    the two trajectory-wide penalties (evidence fabrication, unrecovered
    schema fallback) are added onto the LAST step only."""
    rewards: list[float] = []
    for i, step in enumerate(traj.steps):
        prior = traj.steps[:i]
        r = (
            tool_call_schema_valid_reward(step)
            + whitelist_allow_authorized_reward(step)
            + whitelist_deny_penalty(step)
            + observation_advances_diagnosis_reward(step, prior)
            + repeat_no_new_info_penalty(step)
        )
        ...

有两点很关键：负 reward 敢给（很多项目怕 value 塌陷不敢给负分）——evidence_fabrication 的 -0.50 显著大于任何单步正向信号（最高 +0.10），policy 一旦学会捏造证据，一次就把整条轨迹的正分吃光；以及 observation_advances_diagnosis 只在首次覆盖新 signal_type 时才给分，policy 想刷分就得开新证据源，不能反复调同一工具刷分。

第二层 credit_assignment（覆盖度加权求和，不是 λ 指数衰减，reward/credit_assignment.py）：

GRPO 是组内相对 advantage，训练早期成功率低时，λ 版 credit 只在成功轨迹给分，一组 6 条全失败就全 0、梯度塌陷。所以改成：截至当前步累计覆盖到的 distinct signal_type，按模型自己声明的 kind 差异化查权重表求和（SIGNAL_WEIGHTS_BY_KIND）：

SIGNAL_WEIGHTS_BY_KIND = {
    "dependency": {"jaeger": 1.5, "logs": 1.2, "prometheus": 1.0, "kubectl_status": 0.8, "rag_history": 0.8, "git_history": 0.6},
    "resource":   {"kubectl_status": 1.5, "prometheus": 1.3, "logs": 0.8, "rag_history": 0.8, "jaeger": 0.6, "git_history": 0.5},
    "deploy_regression": {"git_history": 1.5, "logs": 1.2, "kubectl_status": 1.0, "prometheus": 0.8, "jaeger": 0.8, "rag_history": 0.8},
    "config":     {"logs": 1.5, "rag_history": 1.2, "kubectl_status": 0.8, "prometheus": 0.7, "jaeger": 0.7, "git_history": 0.6},
}

覆盖度求和单调非降、成功失败都给梯度，天生适配 GRPO。关键在 evidence_value_reward 的边际计分——每个 signal type 只在其首次被覆盖的那一步付一次权重，后续重复覆盖记 0：

def evidence_value_reward(traj, step_index) -> float:
    kind = traj.final_diagnosis.get("kind")          # 模型自己声明的 kind
    weights = _weights_for_kind(kind)
    new_types = _newly_covered_signal_types(traj, step_index)  # 边际增量
    return sum((weights.get(t, 0.0) for t in new_types), 0.0)

用模型自己的 kind 而不是 ground truth 是刻意的——防止 label 泄漏进 reward，代价是 kind 声明错时 credit 会跑偏，但这个错会被 outcome 的 kind_match +0.1 端到端矫正。

第三层 outcome_reward（结构化五项 + tripwire，reward/outcome_reward.py）：stop_loss（60s 内真实健康检查通过 +0.5、触发 new_alert -0.3）、root_cause 三字段各 +0.1、route_match +0.2、handoff 三字段各 +0.05。

outcome 层最重要的一行其实是 _assert_no_fix_result_leak tripwire——运行时断言 final_diagnosis 和 ground_truth 里绝不出现 verified / fix_result / pr_passed_ci 几个键，把”误把修复 Agent 的结论接进诊断 reward”从静默 bug 变成响亮异常：

_FORBIDDEN_FIX_RESULT_KEYS = ("verified", "fix_result", "fixresult", "pr_passed_ci")

def _assert_no_fix_result_leak(traj) -> None:
    for bucket_name, bucket in (
        ("final_diagnosis", traj.final_diagnosis),
        ("ground_truth", traj.ground_truth),
    ):
        leaked = [k for k in _FORBIDDEN_FIX_RESULT_KEYS if k in bucket]
        if leaked:
            raise ValueError(
                f"outcome_reward: {bucket_name} contains fix-agent-result key(s) "
                f"{leaked} — FixResult.verified must NEVER be used as diagnosis-agent "
                f"outcome reward input (doc §7.2). Remove it before scoring."
            )

这个边界是架构级的：训练时有人尝试把 fix_success 塞进 outcome_reward 想拿”端到端”信号，tripwire 立刻 fail。后来评测里真的观察到修复 Agent 有 PR URL fabrication——没有这个 assert，训练极大概率被带偏。

知识点：reward 的”口径同一”与”边界硬化”
最省心的 reward 是从生产机制里长出来的——hook/白名单/schema 直接 import，训练与生产永远同一套规则。同时要用运行时断言把 reward 的读入边界硬化：哪些桶能读、哪些键绝不能出现，从”约定”变成”异常”。

4. 核心三：Anti-hacking —— 四类结构性防线，不是事后 patch

Reward hacking 是 policy 找 reward 漏洞拿高分但不做事。项目预判了四类真实 hack 手法，全部做成结构性防御（从数据流向上让作弊不可能），而不是训完发现 hack 再补惩罚项（reward/anti_hacking.py）：

  1. 双源覆盖门（-0.2）：整条轨迹 distinct signal_type < 2 就扣分，逼 policy 至少交叉验证两类证据——防”看一眼 logs 就下诊断”：
DUAL_SOURCE_GATE_PENALTY = -0.2
MIN_DISTINCT_SIGNAL_SOURCES = 2

def dual_source_coverage_penalty(traj, ...) -> float:
    covered = traj.all_signal_types_covered()
    if len(covered) < min_distinct_sources:
        return penalty
    return 0.0
  1. evidence 可追溯（-0.5）：final_diagnosis.evidence 里每条 claim 必须能在真实 observation 里做 normalize substring 匹配——防凭空编 service 名：
def is_evidence_traceable(evidence_claim: str, observations: list[str]) -> bool:
    needle = _normalize(evidence_claim)   # 折叠空白 + 小写
    for obs in observations:
        if needle in _normalize(obs):
            return True
    return False
  1. real-health-only：stop_loss 只读 traj.post_action_health（真实 kubectl/prometheus 信号），永远不读模型自报的 remediation_detail——物理上无法 fake（outcome_reward.py 的 stop_loss_reward 注释里明确写着”不要加读 remediation_detail 的 fallback，那正是要防的 hack 模式”）。
  2. 组方差降采样：连续 5 轮组内 reward 方差 ≤ 1e-4 就降采样这个 prompt——防”整组一起躺平拿保底分”：
DEFAULT_ZERO_VARIANCE_THRESHOLD = 1e-4
DEFAULT_CONSECUTIVE_ROUNDS = 5

def should_downsample(variance_history, threshold=..., n_consecutive=...) -> bool:
    if len(variance_history) < n_consecutive:
        return False
    return all(v <= threshold for v in variance_history[-n_consecutive:])

设计难点在提前预判 policy 会怎么”抖机灵”——比如为什么 evidence fabrication 给 -0.5 不是 -0.2：因为捏造证据是 SRE 场景不可容忍的 trust 破坏，惩罚必须显著大于”少调一个工具的机会成本”，policy 才不会赌一把。

知识点：结构性防 hack
与其训完发现 hack 再补惩罚项，不如从数据流向上让作弊不可能：双源覆盖门逼交叉验证、evidence 可追溯把”编造”变成”必然失败”、real-health-only 物理隔离自报文本、组方差降采样对付躺平。每一条防线都对应一个预判的 hack 手法。

5. 核心四：veRL 系统工程 —— 单卡 A800 跑通 15 epoch GRPO

这是整个项目工程含量最密的部分。GRPO 15 epoch × 74 prompt × 6 candidate = 6660 条 rollout，单卡 A800-80GB、wall-clock 约 12 小时。省掉 critic 只是第一步，真正的难点在于让 rollout + fsdp2 + LoRA 在单卡上”同居”：

  • 单卡 colocate（actor+ref FSDP 与 vLLM rollout 挤同一张 GPU）是硬前提：update_weights 阶段 load_fsdp_model_to_gpu 把 CPU-offload 的 actor 权重整个搬回 GPU 会跟 vLLM 常驻显存撞车（实测卡在”还差 834MiB”这种量级），靠 PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True + fsdp_config.param_offload=True + gpu_memory_utilization=0.3 + max_model_len=16384 四方配合压住。
  • gpu_memory_utilization=0.3 不是调出来的，是撞出来的——0.6 是照抄 doc 的两卡经济档算的，单卡 colocate 时 FSDP 模型一加载完 79.25GB 只剩 ~44GB，0.35 能启动 vLLM 但 update_weights 还是会 OOM 几百 MiB，降到 0.25 又让 vLLM 的 KV cache 只剩 0.88GiB 直接启动失败。三个 OOM 在不同阶段触发，不能只调一个值互相覆盖——加 MAX_MODEL_LEN=16384 显式压住 KV cache 预算后 0.3 才两边都留出余量。
  • veRL 4 个默认值坑（读源码 + 真机落地才定位到）：① default_agent_loop 默认是 single_turn_agent，只生成一次就结束，完全不看 multi_turn/tools 配置——必须显式设 tool_agent（否则 num_turns 恒为 2.0 还在那”空转”）；② multi_turn.format 默认 hermes（只认 <tool_call>{json}</tool_call>），而 SFT 用的 Qwen3.5 模板产出的是原生嵌套语法——必须显式设 qwen3_coder（veRL 自带 parser 与 Qwen 语法逐字节匹配）；③ tensor_model_parallel_size 默认 2，单卡会报 “world_size 1 is not divisible by infer_world_size 2”——必须显式设 1；④ fsdp_config.model_dtype 默认 fp32（9B 常驻 36GB 而非 bf16 的 18GB）——必须显式设 bfloat16，这才是 update_weights 阶段 ~60GB 内存的真实来源。

rollout 怎么桥回真实环境是另一个大坑：GRPO rollout 跑在 AutoDL 云 GPU 上，那是嵌套容器、没有 CAP_NET_ADMIN，根本跑不了 docker-compose 故障环境。方案是 SSH 反向隧道——Mac 侧 ssh -N -R 2222:localhost:22 <gpu>，GPU 侧经 localhost:2222 反向 SSH 回 Mac 执行真实 kubectl/docker 命令（verl_adapter/rollout_worker.py 的 ssh_tunnel_bash_executor）：

def ssh_tunnel_bash_executor(command, cwd=None, timeout_s=30.0):
    """Execute command on the environment host (the Mac) through the reverse
    SSH tunnel — same signature as default_subprocess_bash_executor, so it
    drops into the same bash_executor seam."""
    remote_command = f"cd {shlex.quote(cwd)} && {command}" if cwd else command
    argv = [*tunnel_ssh_argv(), remote_command]
    proc = subprocess.run(argv, capture_output=True, text=True, timeout=timeout_s)
    return proc.stdout, proc.stderr, proc.returncode

踩过的坑：AutoDL NAT 表 60 秒 idle 会清端口通道但 SSH 主 session 还活着，表现是”进程在但端口不通”，必须 ServerAliveInterval=30 + ExitOnForwardFailure=yes（后者保证反向端口建立失败立刻退出，否则 SSH 会假成功但端口是死的）。

verl_adapter/ 注册的是 Bash / Read / Grep / Glob + RAG 检索五类通用工具（不是每类环境一个独立客户端）。Read/Grep/Glob 映射成本地命令后走同一个 bash_executor seam——一个 seam 同时把四类工具全接进隧道（rollout_worker.py）：

def _read_remote_command(tool_input):
    file_path = str(tool_input.get("file_path", ""))
    return f"cat {shlex.quote(file_path)}"

def _grep_remote_command(tool_input):
    pattern = str(tool_input.get("pattern", ""))
    path = tool_input.get("path")
    target = shlex.quote(str(path)) if path else "."
    return f"grep -rE -- {shlex.quote(pattern)} {target}"

def _glob_remote_command(tool_input):
    pattern = str(tool_input.get("pattern", ""))
    normalized = pattern[2:] if pattern.startswith("./") else pattern
    return f"find . -path {shlex.quote('./' + normalized)} -print"

_READ_GREP_GLOB_COMMAND_BUILDERS = {
    "Read": _read_remote_command, "Grep": _grep_remote_command, "Glob": _glob_remote_command,
}

RAG 服务用 threading.Lock 常驻串行化 + 启动时真实非空查询预热，消掉首请求冷启 spike。

还有一个很典型的”真机才暴露”的坑：cwd 必须显式穿透。一个没有 cwd 的 Glob（find . -path ...）会从远程登录默认目录——Mac 的整个 $HOME——开始扫，直接超时。cwd 因此从 execute_tool_call/RealHookRoutedTool/run_real_rollout 一路穿透到 executor。

知识点：单卡跑 Agentic RL 是系统工程
“同居”问题是真正的工程活：actor+ref 与 vLLM 挤同一张 GPU、内存碎片管理、rollout 与训练权重换进换出、veRL 的默认值连环坑（agent_loop / format / TP / model_dtype 一个不对就不跑）、云 GPU 无法跑 docker 时用 SSH 反向隧道桥回真实环境。每一个”小参数”背后都是一次 OOM 或一次端口假活的踩坑。

6. 核心五：数据 —— 怎么把 63 条轨迹变成 667 条样本

数据侧的完整链路（真实口径，data/cold_start/）：

四路合成种子（OTel 场景参数化 + flagd 组合 + 历史工单反演 + 手写兜底）
  + v9 定点行为增强（A 反幻觉 / B 信号贫乏 / C 效率 / D code_fix 四家族，47 条）
→ 教师模型采集（Claude Opus 真调 API，47 seed × 76 次调用，验收率 74%）
→ 拒绝采样（v9 新采 35 条 + v8_base 保留 28 条 = 63 条通过轨迹，实花 $58.77）
→ 前缀拆分（63 条轨迹 → 667 条工具级 SFT 样本：604 tool_call + 63 diagnosis）
→ 双层去重（MD5 精确 + BGE 语义 cosine≥0.92）
→ 分层切分（train 74 / held_out 22，与 SFT 有 3 个源 ID 重叠）

前缀拆分（data/cold_start/prefix_split.py）是整个数据侧的核心机制：一条 N 步轨迹拆成 N 条子样本——前 N-1 条”上下文 = 前 i-1 步，目标 = 第 i 步的工具调用”，最后一条”上下文 = 全部 N 步，目标 = 最终 Diagnosis”：

def split_trajectory(traj) -> list[dict]:
    steps = [s for s in (traj.get("steps") or []) if not _is_malformed_step(s)]
    n = len(steps)
    for i in range(1, n + 1):
        if i < n:
            prefix_steps = steps[0 : i - 1]
            target_type = "tool_call"
            target = {"tool_name": steps[i-1]["tool_name"], "tool_input": steps[i-1]["tool_input"]}
        else:
            prefix_steps = steps[0:n]
            target_type = "diagnosis"
            target = traj.get("final_diagnosis")
        subsamples.append({...})

每个子样本只对「目标」这一项计算 loss——这正是解决”反复调 kubectl 不收敛”问题的关键：模型在每一个中间节点都单独学一次「现在证据够不够收敛」，而不是只在整条轨迹的最后一步学一次。malformed 步骤（__unparsedToolInput）在拆分前先整步剔除，防止把”输出不合法 JSON”教给模型。

两个机制层面的论断有消融证明：

  • eval/ablations/no_prefix_split.py：不做前缀拆分，SFT 收敛样本从 5 掉到 0——前缀展开是撑起 SFT 最小训练规模的必要机制。直觉也简单：9B 要做的是学会”每个 tool_call 边界处的下一步动作”，把 63 条整轨迹喂进去，9B 能从中拿到的训练信号太稀疏。
  • eval/ablations/no_credit_assignment.py：去掉 credit assignment，GRPO 组内方差 20.83 vs 0.0——稀疏的 outcome 信号被组内均值抹平，advantage 全零，policy 学不到东西。

一个重要的边界交代：训练侧的 mock harness（eval/run_baseline_comparison.py）只做 reward 调参期的快速迭代（一条 ~10 秒 vs 真环境 3 分钟），从未接过真 checkpoint。所有对外披露的三档数字，全部跑在 AIops-agent 自己的 eval/run.py + 13 个真实 docker-compose 故障栈上——训练侧不重造评测轮子、直接用生产 harness，是另一个关键决策。

知识点：Agent SFT 数据的前缀拆分
让模型学会”在每个工具调用边界决定下一步”，而不是只学”最后输出个诊断”——前缀拆分把一条轨迹摊成 N 个决策点，每个决策点单独算 loss。这是小模型能收敛的必要机制，也是有消融证明的。

7. 聊聊”可复现”这件事

这个项目最打动我的一个细节，是它对每个数字都给了文件级的证据链：$58.77 对应 data/cold_start/_collection_v9_progress.md 里的原始账单；三档数字对应 AIops-agent/reports/ 下三个独立目录的原始轨迹；checkpoint 走 save_freq=20 / max_actor_ckpt_to_keep=2 的落盘策略（grpo/verl_config/aiops_grpo.yaml），训完用 step15 起 vLLM 可重跑评测；grpo/verl_config/aiops_grpo.yaml 里每个字段都标了 [VERIFIED] / [ASSUMED] / [JUDGMENT]：

# 校验状态（本会话没有安装 veRL、没有 GPU，全部离线核对）:
#   - 字段名前标 [VERIFIED]  : 字段名和默认值经真实源码/配置文件核实存在。
#   - 字段名前标 [ASSUMED]   : 字段名本身未直接核实到，是按 veRL 命名习惯或
#     设计文档要求推断的，需要有 veRL 环境的人再核实。
#   - 数值前标 [JUDGMENT]   : 字段名是 [VERIFIED] 的，但数值是设计文档没给出
#     精确数字、需要工程判断的（只给了方向，例如"小幅扣分"）。

哪些是核实过源码的、哪些是按命名习惯推断的、哪些是工程判断的数值，清清楚楚。这种”诚实标注未知区”的习惯，在个人项目里很少见，但正是它能经得起面试官逐条追问的原因。

知识点：把”未知”也写进配置
训练配置里区分 [VERIFIED] / [ASSUMED] / [JUDGMENT]——哪些字段核实过、哪些只是推断、哪些数值是拍脑袋的。诚实标注未知区，既方便后继者，也让每个数字可追溯。

9. Agent 工程师的几点心得

  1. 先 SFT 教会”格式”，再 RL 学”决策”。 RL from scratch 在工具调用都成问题时会整组失败、advantage 塌陷。两段式不是学术偏好，是工程必要。
  2. Reward 从生产机制里长出来。 hook/白名单/schema 零改造 import，训练与生产永远同一套规则——这是训练口径和生产口径永远一致的最省心路径。
  3. 负 reward 敢给，且要”一票否决”。 evidence fabrication -0.5 显著大于任何单步正信号，policy 不会赌一把。惩罚必须大于机会成本。
  4. Anti-hacking 要预判，做结构性防御。 双源覆盖门、evidence 可追溯、real-health-only、组方差降采样——从数据流向上让作弊不可能，而不是事后补罚。
  5. 用运行时断言硬化 reward 边界。 _assert_no_fix_result_leak 把”误把修复结论接进诊断 reward”从静默 bug 变成响亮异常。
  6. 单卡跑 Agentic RL 是系统工程。 单卡 colocate、内存碎片、默认值连环坑（agent_loop / format / TP / model_dtype）、SSH 反向隧道、cwd 穿透……每一个参数背后都是一次踩坑。
  7. 数据要能拆成决策点。 前缀拆分让模型在每个 tool_call 边界学”下一步”，消融证明不做就训不动。
  8. 诚实标注未知区。 [VERIFIED] / [ASSUMED] / [JUDGMENT]，每个数字都有文件级证据链——这是经得起追问的底气。

结语

这个项目的价值在于它是**”应用工程做深”到”后训练纵深”之间最短的一条桥**：不重新发明一个玩具环境，而是把生产系统里现成的安全机制（hook、白名单、schema）零改造变成训练信号；不在评测上自嗨，而是直接用生产 harness 的三档对比说话。

几个诚实的结论，也是这个项目最重要的收获：

  • 9B 没有追平 Opus（service 0.80 vs 0.913，route 0.64 vs 0.913），这恰恰是正确目标定位的证据——要证明的是”开源小模型能撑同一套 Agent 系统”，不是”超越闭源大模型”；
  • Agentic RL 训完的模型上生产从来不是原地替换——10% 流量 shadow 灰度、观察 fabrication/hook_deny 率变化、稳定 2-4 周再全量，这是 SOP；
  • 80% 的时间花在把异构组件糊起来：大模型训练、分布式框架、云资源管理、网络隧道、向量库、docker 编排糅在一起，reward 设计反而是相对顺利的部分。写在简历上的一句”实现 GRPO 训练”背后是三周的踩坑史。
