1. 先看一眼：这个系统由什么组成

「金融研报 RAG」是一整套基于 RAG（Retrieval-Augmented Generation） 技术的智能文档问答平台。它不只有「检索 + 生成」一段简单链路，而是有两条独立的 RAG 流水线协作：

流水线 说明
知识库 RAG（全量链） 文档解析 → 切片 → 向量化 → 入 ES 知识库；问答时全文检索 → 重排 → 生成
快速解析 RAG（轻量链） 小文档（≤4 页 PDF / ≤4000 字符）直接解析入 Redis，问答时按会话取回整段内容

其中知识库全量链是 RAG 工程的核心，本文作为主线展开，最后补上轻量链、推荐问题、前端引用渲染等支线。

整套系统的工程形态是 FastAPI 后端 + React 前端，基础设施用 Docker Compose 编排了 4 个服务：

┌────────────┐     HTTP/SSE      ┌─────────────┐
│  React 前端  │ ────────────────▶ │  swxy_api   │    FastAPI + Uvicorn (:8000)
│  (Vite 5181)│ ◀──────────────── │  (后端引擎)   │
└────────────┘     流式响应       └──────┬──────┘
                                        │
                    ┌───────────────────┼───────────────────┐
               ┌────▼─────┐       ┌─────▼────┐         ┌────▼────┐
               │   ES 8   │       │ PostgreSQL │         │  Redis  │
               │ 检索+向量 │       │ 用户/会话/消息│         │ 快速解析缓存 │
               └──────────┘       └──────────┘         └─────────┘

知识点：RAG = 检索增强生成
核心思想是把「让大模型背下所有知识」替换成「每次提问时从私有知识库里检索最相关的片段，拼进上下文再生成」。既缓解了 LLM 的幻觉与知识截断，又让回答可溯源、可更新（改库即可改答案，无需重训模型）。这个项目把这条链路的每个环节都做到了工程级实现。

2. 核心一：文档解析 —— 金融研报为何难啃

RAG 的质量上限在入口：文档没解析好，后面检索、生成都是空中楼阁。金融研报（PDF / DOCX / Excel）恰恰是文档解析里最「脏」的一类——大段文字、密集表格、图表、公式混排。这个项目复用 RAGFlow 的 DeepDoc 深度解析引擎，代码在 backend/app/service/core/deepdoc/。

单个入口函数统一调度，按扩展名路由（service/core/rag/app/naive.py 的 chunk()）：

def chunk(filename, binary=None, from_page=0, to_page=100000,

        "chunk_token_num": 128, "delimiter": "\n!?。；！？",
        "layout_recognize": "DeepDOC"})

    elif re.search(r"\.xlsx?$", filename, re.IGNORECASE):

    # ... txt / md / html / json / doc

2.1 PDF：版面分析 + 表格识别 + OCR（DeepDoc）

对研报最关键的 PDF，Pdf 解析器（deepdoc/parser/pdf_parser.py）走的是重流程，顺序在 naive.py 里看得一清二楚：

class Pdf(PdfParser):
    def __call__(self, filename, binary, from_page=0, to_page=100000, zoomin=3, callback=None):
        self.__images__(...)          # 1. 页面栅格化/OCR
        callback(msg="OCR finished")
        self._layouts_rec(zoomin)     # 2. 版面分析（标题/正文/图/表区域识别）
        callback(0.63, "Layout analysis")
        self._table_transformer_job(zoomin)   # 3. 表格结构识别（还原行列）
        self._text_merge()            # 4. 文本合并
        tbls = self._extract_table_figure(...)  # 5. 抽取表格与图表

知识点：版面分析（Layout Analysis）
直接按「坐标顺序」抽 PDF 文本，会把页眉、页脚、图表标注、两栏正文搅在一起。DeepDoc 用深度学习模型先识别出每个区域是「标题 / 正文 / 表格 / 图」再重组，这样切片后每段语义才完整。layout_recognize 可切到 "Plain Text" 走轻量解析，是「精度 vs 速度」的开关。

2.2 Excel 表格：转 HTML 保结构

研报里的财务数据多在 Excel，excel_parser.py 把表格直接转为 HTML 表格串，避免检索时丢失行列关系：

def html(self, fnm, chunk_rows=256):
    tb_chunks = []
    for rows in chunks_of(rows, chunk_rows):
        html = rows.to_html(...)   # DataFrame → <table>
        tb_chunks.append(html)
    return tb_chunks

知识点：表格结构化
对强结构的表格数据，直接存「平文本」会丧失语义（「营收」「同比」各自离散）。转成 HTML 表格后，向量化和关键词检索都能把整行作为检索单元，召回质量明显更高。

3. 核心二：切片策略 —— 不要一刀切

解析出 (文本, 图片/标签) 后，下一步是切片。这里用的是 RAGFlow 的 naive_merge 策略（同理 naive_merge_docx、tokenize_chunks）：

  • 默认切片 token 数：chunk_token_num = 128
  • 切分符：delimiter = "\n!?。；！？"（中英文句号、问号、分号、换行）
  • 逻辑：先按分隔符把长文切碎成「句」，再贪心合并进不超过 128 token 的 chunk，并保留相邻关系。
chunks = naive_merge(sections, int(parser_config.get("chunk_token_num", 128)),
                     parser_config.get("delimiter", "\n!?。；！？"))
res.extend(tokenize_chunks(chunks, doc, is_english, pdf_parser))

tokenize_chunks 对每个 chunk 产出多份表示（rag/nlp/__init__.py）：content_ltks（轻量分词）、content_sm_ltks（细粒度/去除停用词）、content_with_weight（原文本 + 权重标记）——后面检索时它们各司其职。

知识点：为什么是 128 token，不是越长越好
chunk 太短召回不全、太长噪声多且稀释向量语义。研究类文档通常选 128~256 token 的「中分块」，并配合下一节的稠密/稀疏双表示来召回。工程里这个值是可调的超参，parser_config 处处可覆盖，调优时应结合真实问题的命中率来做 A/B，而不是拍脑袋。

4. 核心三：向量化与入库 —— 批量、定维、Dense 字段

切片完成后进入入库链：service/core/file_parse.py 的 execute_insert_process 串起「解析 → 向量化 → 写 ES」：

def execute_insert_process(file_path, file_name, index_name):
    documents = parse(file_path)                  # 1. 解析 + 切片
    processed_documents = process_items(documents, file_name, index_name)  # 2. embedding
    es_connection.insert(documents=processed_documents, indexName=index_name)  # 3. 入库

4.1 批量 embedding（DashScope text-embedding-v3）

向量化在 model.py 与 file_parse.py 里有两个工程细节：

def batch_generate_embeddings(texts, batch_size=10):
    embeddings = generate_embedding(texts)   # 批量，DashScope 限制一次 ≤10
    ...

def generate_embedding(text, model_name="text-embedding-v3",
                       dimensions=1024, encoding_format="float"):
    completion = client.embeddings.create(
        model=model_name, input=text,
        dimensions=dimensions, encoding_format=encoding_format)
    return completion.data[0].embedding
  • 定维 1024：dimensions=1024 让所有向量维度一致，才能存在同一个 ES 字段并做余弦相似度。
  • 批量 ≤10：DashScope 单次请求上限，工程上写死 batch_size=10。

4.2 Schema 设计：向量存进「动态稠密字段」

process_items 里最关键的一行是把向量写进一个以维度命名的字段 q_1024_vec：

d[f"q_{len(embedding)}_vec"] = embedding   # q_1024_vec → 1024 维 dense_vector

同时记录文档元信息：docnm_kwd、doc_id、kb_id、chunk_id（用 xxhash 生成，可去重）：

chunck_id = xxhash.xxh64((item["content_with_weight"] + index_name).encode()).hexdigest()
d["doc_id"] = xxhash.xxh64(file_name.encode()).hexdigest()

知识点：Dense 字段的动态映射
ES 通过 mapping.json 里的 dynamic_templates 自动把 q_*_vec 识别为 dense_vector 字段，而 *_ltks/*_tks 这类被映射为可分词的文本（keyword/term）字段。这样一份 chunk 同时具备向量表示 + 关键词表示，为混合检索打下基础。这比「只存向量」的插件式方案更可控、更节省额外组件。

5. 核心四：混合检索 —— 关键词 + 向量 + 相似度

这是本项目 RAG 工程味道最浓的一块。检索走 service/core/retrieval.py → Dealer.retrieval（rag/nlp/search_v2.py）。入口把 vector_similarity_weight 设为 0.6：

def retrieve_content(indexNames, question):
    results = dealer.retrieval(question=question, embd_mdl=None,
                               tenant_ids=indexNames, kb_ids=None,
                               vector_similarity_weight=0.6,   # ← 核心超参
                               page=1, page_size=5)

而 Dealer.retrieval（search_v2.py:336）内部有两级排序：

  1. 先重排候选：把 top 结果取到 RERANK_PAGE_LIMIT * page_size（≥128 条）
  2. 再按混合相似度排序挑前 N：rerank_by_model（有重排模型）或 rerank（无模型）

5.1 混合相似度公式

核心计算在 query.py:200：

def hybrid_similarity(self, avec, bvecs, atks, btkss, tkweight=0.3, vtweight=0.7):
    tksim   = self.token_similarity(atks, btkss)      # 关键词(BM25风格)相似度
    vtsim   = cosine_similarity(avec, bvecs)           # 向量余弦相似度
    return tkweight * tksim + vtweight * vtsim

两路权重默认 30% 关键词 + 70% 向量，与 vector_similarity_weight=0.6 呼应（在 rerank 中 vtweight = vector_similarity_weight）。

知识点：为什么向量检索需要混合（Hybrid Search）
只走向量检索，精确数字、专有名词（如「世运电路」「CAGR」）容易被语义漂移；只走关键词检索，同义改写、长问句则召回不到。混合检索让两路互相补位，用加权融合分数统一排序。vector_similarity_weight 是最值得调的旋钮：研报问答里术语精确度高，可保持较高的关键词权重。

5.2 阈值裁剪，保证「回答有据可依」

retrieval 最后按 similarity 阈值和 page_size 裁剪：

for i in idx:
    if sim[i] < similarity_threshold:  # 相似度低于阈值的直接丢弃
        break
    if len(ranks["chunks"]) >= page_size: break
    ...

doc_aggs：按文档聚合，返回每个文档的命中片段数

知识点：召回阈值 = 幻觉防护第一道闸
检索不是召回越多越好。低于阈值的低相关片段拼进 prompt，反而会诱导模型「编」。设定 similarity_threshold 让弱召回直接不进入上下文，是 RAG 工程用「数据」而非「prompt 恐吓」来控幻觉的做法。

6. 核心五：重排序 —— 让检索结果更「贴题」

初级召回用的是快速的（近似）向量 + 关键词并查，精度一般。前 N 条里往往混着不太相关的片段。这里再用一个重排模型精排（search_v2.py 的 rerank_by_model）：

vtsim, _ = rerank_similarity(query, [rmSpace(" ".join(tks)) for tks in ins_tw])
return tkweight * (np.array(tksim) + rank_fea) + vtweight * vtsim

rerank_similarity（model.py:45）基于 llama-index 的 DashScopeRerank：

def rerank_similarity(query, texts):
    nodes = [NodeWithScore(node=Node(text=text), score=1.0) for text in texts]
    dashscope_rerank = DashScopeRerank(top_n=len(texts), api_key=api_key)
    results = dashscope_rerank.postprocess_nodes(nodes, query_str=query)
    scores = np.array([res.score for res in results])
    return scores, None

知识点：召回(Recall) vs 精排(Rerank)
「召回要广、精排要准」。第一阶段用便宜的向量/关键词并查把候选从海量文档中捞出上百条，第二阶段用更强的交叉编码器（Cross-Encoder）逐条对「问题×片段」打分，只留最相关的前 N 条进 prompt。这比「直接取 top-k 向量」质量高一个量级，尤其在金融术语场景里。检索是两级架构，不是一次完成。

7. 核心六：RAG 生成 —— 让回答「带出处」

检索到的片段最终要拼进 prompt，并强制模型逐句标注出处编号。这是 service/core/chat.py 的 get_chat_completion 最核心的工程设定。

7.1 上下文组织：双来源合并编号

# 1. 知识库检索内容
reference_id = 1
for ref in retrieved_content:
    knowledge_base_refs.append(f"[{reference_id}] {ref['content_with_weight']}")
    reference_id += 1

# 2. 当前会话快速解析文档内容（超长会截断）
quick_content_paragraphs = [p for p in quick_parse_content.split('\n') if p.strip()]
truncated_content = quick_parse_content[:4000]   # 防止 prompt 过长

7.2 引用溯源 Prompt

prompt = f"""
你是一个专业的智能助手，擅长基于提供的参考资料回答用户问题。

**回答要求：**
1. 优先基于参考内容回答，确保答案准确可靠
2. 在回答中，每一块内容都必须标注引用的来源，格式为：##引用编号$$。
   例如：##1$$ 表示引用自第1条参考内容。
3. 如果参考内容不足以完全回答问题，可以结合常识补充，但需明确区分
4. 回答要条理清晰、语言自然流畅
5. 如果没有相关参考内容，请诚实说明并提供一般性建议

**参考内容：**
{formatted_references}

**用户问题：**

"""

知识点：引用溯源（Citation）是 RAG 的生产力所在
一行「必须标注 ##编号$$」的约定，把「黑盒回答」变成了「可审计回答」。前端据此渲染引用卡片（文档名 + 页码 + 片段），用户能点进原文核对——这正是金融研报场景做可信问答的命门。Prompt 约定是 RAG 与「直接把文档丢给 LLM」的本质区别。

8. 核心七：SSE 流式输出 —— 三种事件类型

生成用 DashScope 的流式接口 stream=True，模型 deepseek-r1，通过 SSE（Server-Sent Events） 实时推给前端。整个响应拆成三类事件，顺序清晰：

① 先发「文档」事件 —— 一次性把检索到的引用先给前端

message = {"documents": all_documents}
json_message = json.dumps(message, ensure_ascii=False)
yield f"event: message\ndata: {json_message}\n\n"

② 再流式发「正文 + 思考」事件

for chunk in completion:
    delta = chunk.choices[0].delta
    if delta.content:
        model_answer += delta.content
        yield f"event: message\ndata: {json.dumps({'role':'assistant','content':delta.content, 'thinking':False})}\n\n"
    else:
        think += delta.reasoning_content   # 思考过程单独累加，未推到前端

这里有个细节：reasoning_content（思考链）被累进 think 变量却不实时推送，把「思考」和「答案」解耦——用户看到的是顺滑的答案流。

③ 完成时发「推荐问题 + [DONE]」

if chunk.choices[0].finish_reason == "stop":
    recommended_questions = generate_recommended_questions(question, retrieved_content, session_id)
    message = {"recommended_questions": recommended_questions}
    yield f"event: message\ndata: {json.dumps(message)}\n\n"

    yield "event: end\ndata: [DONE]\n\n"   # 结束标记
    write_chat_to_db(session_id, question, model_answer, all_documents, recommended_questions, think)

知识点：SSE 事件协议让流式对话变得可控
不用 WebSocket 而是 SSE，前端 fetch + ReadableStream 逐行解析即可，兼容性好。把「引用文档」「生成中」「已完成」拆成不同事件，前端才能在恰当节点渲染引用卡片、思考态、推荐问题。事件即协议，是前后端协作的关键契约。

9. 核心八：双通道策略 —— 全量链 vs 轻量链

这个系统很聪明的一点是：不把所有文档都塞进知识库。针对「单次会话小文档」走快速解析链，service/quick_parse_service.py：

通道 文档限制 存储 用途
知识库全量链 任意（推荐大文档/多文档） ES（切片+向量） 跨文档、长文档、可长期复用
快速解析链 PDF ≤4 页，docx/txt ≤4000 字符 Redis（整段原文，TTL 2h） 单会话临时问题，秒级响应 
# quick_parse_service.py —— 轻量解析直入 Redis
self.max_pages = 4
self.max_characters = 4000
self.redis_expire_seconds = 7200   # 缓存 2 小时

在 chat.py 中，两条通道的结果被合并成同一份 references（第 7.1 节），共用一套引用溯源 prompt——前端视角完全一致，后端按文档规模自动分流。

知识点：RAG 流水线的弹性设计
不是所有问题都值得走完整向量检索链。对小文档、单会话场景，省去「切片/向量化/建索引」直接用原文生成，延迟和成本都更低。把最重的计算留给真正需要的场景，是 RAG 架构里常被忽略的成本优化。两条链共用下游生成与引用协议，是「可插拔流水线」的体现。

10. 核心九：推荐问题 —— 生成时的「事后抠图」

回答结束后，系统再让模型基于「当前问题 + 已引用文档名」生成 3 个推荐问题，形成追问闭环（chat.py 的 generate_recommended_questions）：

prompt = f"""
你是一个智能助手，请基于用户的问题生成3个相关的推荐问题。
用户问题：{user_question}
如果文档上下文：基于这些文档：{', '.join(document_topics)}

要求：问题要具体、有价值，能引导用户更深入
返回JSON格式：{{"recommended_questions": ["问题1", "问题2", "问题3"]}}
"""

知识点：追问引导把单次问答做成对话
金融研报问答往往是「一问不够，要深挖」。回答后自动补 3 个相关问题，既提升留存，又暗示系统「已理解你关心的维度」。推荐问题用 JSON 强制格式返回，是「结构化输出」在轻量生成任务里的应用。

11. 前端引用渲染 —— 溯源闭环的最后一块

后端把 documents 字段推给前端后，pages/chat/component/citations.tsx 把它渲染成可交互的引用卡片：

<div className={styles['name']}>{item.document_name}</div>
<div className={styles['desc']}>{content}</div>              {/* 片段原文 */}
<div className={styles['footer-desc']}>页码 {item.positions?.[0]?.[0] ?? '-'}</div>
<Button onClick={onRead}>阅读</Button>                        {/* 点进原文 */}

并带搜索 + 过滤能力，让用户在长回答里快速定位某一处引用的原文片段。

知识点：RAG 的可信闭环 = 检索 → 生成 → 引用 → 可溯源
只有前端能「回到原文」的 RAG 才是可信的 RAG。positions（页码）的透传让研报问答真正做到「点引用/看原文/核数据」，这是面向专业金融用户的硬需求。

12. 架构全景回顾

把两条链路拼起来，整个 RAG 系统就是：

┌─────────────────────────────── 前端 (React, :5181) ───────────────────────────────┐
│  流式对话 · 引用卡片 · 原文定位 · 推荐问题 · 知识库文档管理                          │
└──────────────────────────────────────▲────────────────────────────────────────────┘
                                       │ SSE 事件流
┌──────────────────────────────────────┴────────────────────────────────────────────┐
│                           RAG 引擎（FastAPI + DashScope）                          │
│                                                                                    │
│   【入库链】 文档 → DeepDoc解析(版面/表格/OCR) → naive切片(128token)                  │
│             → DashScope批量向量化(1024维) → 写入 ES(kb_id + q_1024_vec)              │
│                                                                                    │
│   【检索链】 问题 → jieba分词 + 向量化 → 混合检索(0.6向量+0.4关键词)                  │
│             → 阈值裁剪 → DashScope重排 → top5 chunks                                 │
│                                                                                    │
│   【生成链】 merge引用 + 快速解析内容 → 引用溯源Prompt(##id$$) → stream=True           │
│             → SSE 流式 → 推荐问题 → 会话/消息落库                                    │
│                                                                                    │
│   【轻量链】 小文档 → Redis(2h TTL) → 合并进引用                                      │
└──────┬──────────┬──────────┬──────────┬────────────────────────────────────────────┘
       ▼          ▼          ▼          ▼
   Elasticsearch  PostgreSQL   Redis   DashScope
   (向量+关键词)  (会话/消息)   (快速解析)  (embedding+qwen+rerank)

13. RAG 工程师的几点心得

  1. 入口决定上限，解析决定了 RAG 的「视力」。 金融研报的表格、版面、图表不处理好，向量和关键词都建立在噪声上。先在一套好的 DeepDoc 解析上花力气，再谈检索优化。

  2. 检索永远是多级架构。 是「向量/关键词并查召回 + 交叉编码器重排精排」，不是「一次 top-k」。vector_similarity_weight、similarity_threshold、page_size 是你最该调的三个旋钮。

  3. 引用溯源不是加分项，是可信问答的命门。 一行 prompt 约定 ##编号$$ + 前端可点回原文 = 面向专业用户的产品力。没有溯源，RAG 和「随便聊」没有本质区别。

  4. Prompt 决定「能用」，检索 + 数据决定「好用」。 引用溯源、流式、批量 embedding、fail-soft（检索失败不崩、直接无库回答）这些工程韧性，比换模型更能拉开体验差距。

  5. 弹性设计双通道。 不是所有问题都值得完整检索链。小文档走轻量 Redis 链，省延迟省成本，下游协议统一。让流水线可插拔，是 RAG 架构的进阶题。

  6. 可控性 > 性能。 用占位符 ??、动态字段 q_1024_vec、固定 batch=10，处处「显式优于魔法」，好排查、好调参、好扩展。
