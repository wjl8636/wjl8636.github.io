🛠️ 手把手拆解：一个「AIOps 故障诊断自愈 Agent」的工程实现

2026/8/29 Agent AIOps SRE Claude Agent SDK 工具调用 工程实践

🛠️ 手把手拆解：一个「AIOps 故障诊断自愈 Agent」的工程实现

不再是把大模型当成一个「会聊天的 API」，而是让它像 SRE 一样在终端里自己敲 kubectl 查故障、定位根因、甚至直接改代码修 bug——而且是真机跑通，不是”假装调用工具”的 demo。本文从一名 AI Agent 开发工程师的视角，深度解析开源项目 AIopsAgent（github.com/wjl8636/AIopsAgent），凡是代码里真实存在的地方，我都会给出文件路径和关键实现，希望能帮你把「Agent」从概念落到工程。

0. 本文你会收获什么

这篇文章不是功能清单，而是围绕一个真实项目梳理 Agent 工程的核心知识图谱。我尽量把抽象的概念（双 Agent 编排、结构化输出、安全边界、Agentic RAG、优雅降级……）都对应到一段真实代码，让你看完能直接用。

涵盖的主题索引：

  • 单引擎双 Agent：一个 query() 引擎跑两趟，按处置类型分流
  • 结构化输出：pydantic + 手写 JSON Schema 双重约束，错误回灌重试
  • 可枚举白名单安全：LowRiskAction 正则锚定 + 目标授权集合
  • PreToolUse Hook 硬拦截：提示词只是软约束，hook 才是硬保证
  • 执行台账：信 hook 放行那一刻的记录，不信模型自述
  • Agentic RAG：in-process MCP 工具 + Milvus 向量库，模型自主决定何时检索
  • 优雅降级：流程永不崩溃的主线
  • 真机闭环：一次完整自愈过程的三方一致性

1. 先看一眼：这个系统由什么组成

「AIopsAgent」是一套基于 Claude Agent SDK 的 AIOps 故障诊断与代码修复 Agent。它的输入是一份告警 JSON，输出是一份带路由结论的报告——中间的故障排查、根因定位、自动止血、改码提 PR 全部由 Agent 自主完成。

能力线 说明
双 Agent 编排 诊断处置 Agent 定位根因 + 修复 Agent 改码提 PR，单引擎跑两趟
结构化输出 pydantic + 手写 JSON Schema，把整条路由押在一份 Diagnosis JSON 上
安全边界 可枚举白名单 + PreToolUse hook 硬拦截 + 执行台账，三层兜底
排查 Skill 四类经典故障的 SRE 排查手册，按需加载不进提示词
Agentic RAG in-process MCP 工具 + Milvus 向量库 + BGE embedding，诊断完沉淀工单
优雅降级 任何失败都不上抛异常，核心诊断闭环永不崩
双后端 AIOPS_BACKEND 一键切换 k8s / docker，安全语义一致

其中以 单引擎双 Agent、可枚举白名单安全、Agentic RAG 最具 Agent 工程代表性，本文作为主线展开，最后补上降级与真机闭环。

2. 核心一：单引擎、两趟、按处置分流

很多双 Agent 项目会写两套框架。但这个项目的核心洞察是：诊断 Agent 和修复 Agent 的差异本质上只有三点——给什么工具、什么工作目录、什么安全约束（agent/run.py）。

于是整个系统只有一个 Agent 引擎（Claude Agent SDK 的 query()），被封装成一个函数 run_sdk()，跑两趟：

故障诊断处置 Agent 代码修复 Agent
工具 Bash, Read, Grep, Glob（只读 + 低风险白名单） clone/改码/推分支（可写代码）
安全 hook guard_diagnose_ops：只读 + 低风险白名单放行 deny_online_ops：禁线上变更、禁推 master
工作目录 诊断工作区 clone 下来的代码仓
系统提示词 排查方法论 + 输出 schema 修复流程 + 验证门禁

串起两趟的编排层是普通的 async Python，没有任何 Agent 框架的魔法，就是朴素的 if/await/return（agent/run.py 的 _run_inner()）：

async def _run_inner(alert, ...):
    # 1. 去重（指纹判断这条告警是否见过）
    # 2. 诊断：第一趟 Agent → Diagnosis（结构化输出）
    # 3. 低置信度逃生口：confidence < 阈值 → 不信任，转人工
    # 4. 分流：按 remediation_type 走 online_op / code_fix / info_only

这是刻意的：Agent 负责”不确定的智能部分”（怎么查、查什么、怎么判断），编排层负责”确定的流程控制”（去重、分流、降级、存工单）。把不确定和确定分开，系统才可控、可测、可讲。

知识点：单引擎双 Agent
两个 Agent 角色共享同一个引擎，差异只是「工具 + 工作目录 + 安全约束」三件装备。新增一个 Agent 角色（比如专门写测试的），就是传一套新参数的事——Agent = 通用引擎 + 可插拔装备，装备决定了它的能力和边界。

_run_inner() 里有两个设计细节值得一提：

  • 低置信度逃生口放在所有分流判断的最前面——不管诊断说该 online_op 还是 code_fix，只要 confidence 不够就不信任它，直接转人工。顺序体现优先级：可信度是处置的前提。
  • 混合根因用可选布尔而不是扩枚举——also_code_fix: true 表示”既线上止血、又要改码根治”（agent/core/schema.py）。选加法不选改法：加一个默认 false 的布尔对旧路径零影响，扩枚举则要动所有分支的判定逻辑。

3. 核心二：结构化输出 —— 整条路由押在一份 JSON 上

Agent 的诊断结论是整个系统的路由依据，所以输出必须绝对结构化。项目在 agent/core/schema.py 里用 pydantic + 手写 JSON Schema 做了双重约束：

class Diagnosis(BaseModel):
    summary: str
    kind: Literal["dependency", "resource", "deploy_regression", "config"]
    suspect_service: str
    suspect_repo: Optional[str] = None          # code_fix 时的定位线索
    suspect_commit_hint: Optional[str] = None
    suspect_file_hint: Optional[str] = None
    remediation_type: Literal["online_op", "code_fix", "info_only"]
    remediation_detail: str
    confidence: float = Field(ge=0.0, le=1.0)
    evidence: list[str] = Field(min_length=1)   # 强制可追溯
    also_code_fix: bool = False                 # 混合根因用加法不用改法

几个关键工程决策：

  • 手写 schema 而非 model_json_schema() 自动生成，是为了精确控制 additionalProperties: False（禁止模型多塞字段），以及避开 time_window.from 这种 Python 保留字的别名坑（TimeWindow 用 Field(alias="from")）。
  • schema 校验失败不是直接重跑，而是错误回灌——把”你上次错在哪”拼进新提示词喂回去，让模型带明确反馈修正（默认重试 2 次）。
  • 再失败就走兜底：合成一个 confidence=0 的 fallback 诊断（Diagnosis.fallback()），它一定低于阈值 0.6，被低置信度逃生口自动路由到人工。最坏情况只是转人工，主流程不会崩。

知识点：结构化输出 + 错误回灌
让 Agent 输出决策类结论时，schema 校验失败不要裸重跑，而要把错误信息回灌进提示词——模型带着”上次错在哪”的反馈修正，成功率远高于冷启动重试。反复失败则合成”最低置信度兜底”，把失败也变成可控路由，而不是异常。

还有一个用 schema”反向引导行为”的例子：evidence 字段 min_length=1 强制非空，逼模型每条诊断结论都必须附上可追溯的证据（哪条 PromQL、哪个 trace id、哪行日志）——既提升诊断质量，又让人工复核有据可查。

4. 核心三：安全边界 —— 给会写代码的 Agent 上三道锁

这是项目最花心思的部分，也是最有工程说服力的部分。

原则：提示词只负责”告知”有哪些手段，真正决定”这条命令能不能跑”的是代码层。

诊断 Agent 不只是只读——它能自动执行低风险线上操作止血（真的 kubectl rollout restart deploy/<svc>）。但”能执行哪些操作、作用到哪些工作负载”不是靠提示词说的，而是 agent/core/remediation.py 里一份可枚举的白名单：

# 目标授权集合：只放 demo 栈里无状态、可安全重启/扩容的业务容器
# （绝不包含有状态组件 kafka/valkey/milvus/etcd/minio/数据库）
ALLOWED_TARGETS: set[str] = {
    t.strip() for t in config.REMEDIATION_ALLOWED_TARGETS.split(",") if t.strip()
}

class LowRiskAction:
    """一条可枚举的低风险线上操作。"""
    def __init__(self, action: str, pattern: str, description: str) -> None:
        self.action = action
        self.description = description
        self._re = re.compile(pattern)

    def match(self, command: str) -> Optional[str]:
        """命令若命中本操作，返回被操作的目标实例名；否则返回 None。"""
        m = self._re.match(command.strip())
        if not m:
            return None
        return m.group("target")

# 示例：滚动重启单实例。**从头到尾锚定 ^…$**，目标名限定在 _TARGET 安全字符集，
# 可选 -n <ns> 命名空间限定在 _NS 合法字符集（`_NS_OPT` 同时覆盖 -n / --namespace 两种写法）。
_NS_OPT = rf"(?:-n\s+{_NS}\s+|--namespace\s+{_NS}\s+)?"
LowRiskAction(
    "restart_instance",
    rf"^kubectl\s+{_NS_OPT}rollout\s+restart\s+(?:deployment|deploy)/(?P<target>{_TARGET})$",
    "滚动重启工作负载：kubectl rollout restart deploy/<svc>（逐个换 Pod 止血，如清掉泄漏进程的内存、重置卡死状态）。",
)

目标是否授权由 classify_command()（同一个文件）判定，不在正则本身里——两条规则分层：正则圈定合法形态，ALLOWED_TARGETS 圈定可动的工作负载：

def classify_command(command: str) -> dict[str, Any]:
    for act in LOW_RISK_ACTIONS:
        target = act.match(cmd)          # 形态不合法 → None，继续下一条
        if target is None:
            continue
        if target not in ALLOWED_TARGETS:            # 目标未授权（如想动 kafka/db）
            return {"decision": "deny", "action": act.action, "target": target, ...}
        return {"decision": "allow", "action": act.action, "target": target}
    return {"decision": "passthrough"}               # 不是处置命令 → 交给下一层规则

几个关键细节：

  • 正则锚定 ^…$ 是”圈定唯一合法形态”，不是”找危险词”。kubectl rollout restart deploy/ad 能匹配，但 kubectl rollout restart deploy/ad && rm -rf / 因为多了 && 那段就匹配不上，落到 passthrough，再被写变更规则拦下。黑名单思路永远防不全（总有新的危险词），白名单思路只有长得一模一样才放行。
  • flag 取值也锚死在安全字符集——命名空间只允许小写字母数字连字符，把注入藏进 -n <ns> 参数的花招也匹配不上。
  • 执行记录信”hook 放行那一刻写的台账”，不信模型自述。诊断跑完，编排层把台账回填进 Diagnosis 的 executed_actions 字段（schema.py），而这个字段故意不放进 JSON schema——模型哪怕在 JSON 里吹牛说重启了 kafka，台账里没有，报告里就不会有。
  • 风险分级：低风险（k8s 滚动重启/删 Pod 重建/抬资源上限，docker 重启/迁移/扩容单实例）自动执行 + 事后卡片知会；高风险（动 redis/db、删除、改集群、缩容）一定被拦，只发卡交人工。

白名单做了 k8s 和 docker 两套等价实现（滚动重启↔重启、删 Pod↔删容器、抬 limits↔docker update），AIOPS_BACKEND 一个环境变量切换，安全语义完全一致（remediation.py 的 LOW_RISK_ACTIONS 按后端选定）。k8s 是生产主线，docker 是让零门槛本地复现的默认后端。

修复 Agent 的防御是另一套：可改代码但禁止线上变更、禁止强推、禁止推 master（hooks.py 的 deny_online_ops），把”是否提 PR”死死绑在”build+test 是否通过”上——FixResult.verified 是总闸门（schema.py），解析失败一律按未验证处理，任何意外都往最保守的方向倒。

知识点：Agent 的工具护栏（Guardrails）
让 Agent 拥有写文件、跑命令的能力，就必须有分层护栏：可枚举白名单只放行”长得一模一样”的命令、hook 硬拦截、执行台账记录实况。真正面向用户的产品，Agent 的「权力」永远是受约束的、可解释的、可被否决的。

hooks.py 的 guard_diagnose_ops 判定顺序值得单独展示——这是整个安全体系的落点：

async def guard_diagnose_ops(input_data, tool_use_id, context):
    command = _extract_command(input_data)          # 非 Bash 工具直接放行
    if not command:
        return {}
    verdict = remediation.classify_command(command) # 白名单判定（唯一依据）
    if verdict["decision"] == "allow":
        remediation.record_execution(...)           # 放行那一刻记台账
        return _allow(...)                          # 显式放行
    if verdict["decision"] == "deny":
        return _deny(...)                           # 目标越权 → 拦截
    hit = _match(command, _READONLY_DENY)           # 白名单外的一切写/变更 → 拦截
    if hit:
        return _deny(...)
    return {}                                       # 只读查询 → 放行

5. 核心四：Skill 排查手册 —— 按需加载，而不是全塞进提示词

四类经典故障的 SRE 排查方法论被沉淀为 4 份 Agent Skills（.claude/skills/）：memory-oom、dependency-error、resource-cpu、queue-backlog。每份 SKILL.md 的 frontmatter 写”什么时候用这份手册”，body 是起手式查询清单和判定规则。

区别在于按需加载：诊断 Agent 启动时开 skills="all"，SDK 根据告警语义自动选择加载——一条内存告警进来只加载 memory-oom 手册，其余三份不加载。对比全塞进系统提示词，既给了专业排查指引又省了 token。

更妙的是，每份手册结尾的”判定”段直接对应到诊断输出的 remediation_type 与 confidence——把”怎么查”和”结构化产出”串成一条主线：

Skill（怎么查）→ 结构化输出（判定落字段）→ 编排分流（字段驱动路由）

知识点：技能的按需加载
排查方法论是 Agent 的「程序记忆」。与其把四份手册全文塞进提示词，不如按告警语义按需加载——既保证专业指引在场，又不烧上下文。把”怎么查”与”判定字段”挂钩，方法论才能真正驱动决策。

6. 核心五：Agentic RAG —— 让诊断 Agent 会”攒经验”

普通 RAG 是编排层在调模型前先检索一批历史文档强行拼进提示词——检索时机和内容都是写死的。这个项目做的是真正的 Agentic RAG：

  • 每次诊断完，编排层在单点把工单（摘要 + 处置详情 + 证据）用 BGE 中文 embedding 向量化存入 Milvus（agent/run.py 的 run() 最外层，memory.store_ticket）。
  • 历史工单检索被封装成一个 in-process MCP 工具 mcp__aiops_rag__search_past_incidents 挂给诊断 Agent，由模型自主决定何时检索、用什么 query。

在真实运行的 transcript 里能看到：模型查完指标发现是内存问题后，会主动调这个工具查”以前有没有遇到过类似泄漏”，query 是它自己组织的语义串。检索成了模型推理链条里的一步，而不是被外部强喂的。

两个工程决策值得展开：

  • 写入放在编排层而不是给 Agent 写工具——诊断 Agent 严格只读，写 Milvus 虽然不碰线上状态，但只读边界一旦松口就不干净了。而且放在 run() 最外层单点调用，一口气覆盖所有 return 分支，不管走哪条路由工单都会被存。
  • embedding 抓的是故障模式而非服务名——实测用”payment 内存泄漏”能召回”recommendation 无界 list 泄漏”的工单，跨服务迁移有效，这是关键词/SQL 检索做不到的。

知识点：Agentic RAG vs 普通 RAG
普通 RAG 是”检索→拼提示词”的固定管线；Agentic RAG 把检索封装成工具交给模型自主调度——何时查、查什么、怎么用，都成为推理链条中的一步。写入点收敛在编排层单点，保证「只读 Agent」的边界不被突破。

7. 流程永不崩溃：优雅降级是一条主线

底层 SDK 封装里有一条铁律：遇到任何失败都不往上抛异常，而是返回带 degraded 标记的结果。这条铁律的诞生源于一个真实踩坑——Claude Agent SDK 命中 max_turns 上限时不是优雅返回错误消息，而是直接抛异常，不 catch 整个诊断就崩了。

降级贯彻在每一层：

  • SDK 封装层：失败转 degraded 结果；
  • schema 校验层：反复失败兜底 confidence=0 转人工；
  • 记忆/RAG 层：Milvus 或 embedding 不可用就静默 no-op，还有 AIOPS_RAG_ENABLED 一键总开关；
  • 飞书层：webhook 发送失败 catch 住只打日志。

核心思想是分清”核心”和”附加”：诊断闭环是核心，绝不能崩；记忆、RAG、飞书是附加能力，挂了就降级，绝不拖垮核心。

知识点：优雅降级的主线设计
把「流程永不崩溃」当成一条设计主线，而不是零散的 try/except。每一层都想清楚”挂了会怎样”，附加能力降级、核心闭环兜底。最坏情况永远是可预测的转人工，而不是裸奔的异常。

8. 真机闭环：一次完整的自愈过程

项目用自带内存泄漏的 recommendation 服务做了完整闭环验证——不是 mock，是活的：

  1. 工作负载（docker --memory=128m / k8s 128Mi limit）跑起来内存单调爬升；
  2. 诊断 Agent 用 docker stats/kubectl top 实地观测到内存逼近上限 → OOMKilled → 重启（RestartCount=1）；
  3. 结合镜像 tag + deploys.log + git show 定位到泄漏的发版 commit（confidence 0.9，全程只读）；
  4. 代码修复 Agent clone 仓、把无界 list 改成有界 deque、pytest 从 1 failed 转 2 passed；
  5. 提出一条推不上 master 的 PR（verified=true，附 build+test 验证摘要）。

关键是 seed 脚本保证三方一致：GitHub 仓里代码修复 Agent 要改的代码、运行的工作负载里跑的代码、修复目标，是同一段代码——“观测一个东西、改另一个东西”的假闭环，和逻辑自洽的真实闭环，含金量完全不同。

知识点：真机闭环的三方一致性
验证 Agent 系统最忌讳 mock。让”要改的代码 = 在跑的代码 = 修复目标”三方严格一致，闭环才真实。这份一致性靠 seed 脚本保证，而不是靠口头承诺。

9. 效果与评测

在自建 13 场景告警回归集（覆盖 9 条业务路由，含重复告警/低置信度/混合根因/修复失败/三条独立代码定位场景）上做多轮评测，7 条指标：服务定位（service）、类型识别（kind）、路由（route）、修复成功率（fix）、代码定位（code_loc）、MTTR（p50）、PR 提交率。完整配置（Sonnet 4.5）23 次运行：

指标 service kind route fix code_loc MTTR p50
数值 0.8696 0.8261 0.7826 1.0 1.0 3.26 min

修复成功率 fix=1.0，PR 提交率随其联动（只有 build+test 通过才提 PR）。

对标 Google SRE Book / DORA 报告中位数（人工 30–60 分钟，明确标注为行业引用而非本项目内对照实验），MTTR 加速约 9–18×。评测还做了三组消融：关 Skill 后 MTTR 升到 5.90 分钟（Skill 的价值是缩短排查路径）；关指纹去重后路由准确率降 8.69 个百分点；降级 Haiku 后 MTTR 降到 1.80 分钟但准确率全面下滑。

11. Agent 工程师的几点心得

  1. 把不确定和确定分开。 Agent 负责”不确定的智能”（怎么查、怎么判断），编排层负责”确定的流程”（去重、分流、降级）。系统因此可控、可测、可讲。
  2. 安全不靠提示词承诺。 “你只能做这些”只是软约束；真正决定命令能不能跑的是代码层——可枚举白名单 + hook 硬拦截 + 执行台账。
  3. 白名单锚定形态，黑名单永远防不全。 正则 ^…$ 圈定唯一合法形态，只有长得一模一样才放行；flag 取值锚死安全字符集，堵住注入。
  4. 信台账，不信模型自述。 执行记录由 hook 在放行那一刻写，故意不放进 JSON schema——模型吹牛也没用。
  5. 输出契约决定路由质量。 整条路由押在一份 JSON 上，就值得花双倍力气做 schema 校验、错误回灌、最低置信度兜底。
  6. Agentic RAG 让 Agent 攒经验。 检索时机和 query 交给模型自主决定，写入点收敛在编排层单点——只读边界不破。
  7. 流程永不崩溃是一条主线。 分清核心与附加，附加挂了降级、核心兜底转人工。最坏情况永远是可控的。
  8. 真机闭环验证。 seed 脚本保证”要改的代码 = 在跑的代码 = 修复目标”三方一致，假闭环没有含金量。

结语

这个项目最大的收获不是”Agent 能修 bug”，而是一套把 Agent 系统做可控、可测、可讲的方法论：不确定的智能交给模型、确定的流程交给代码；自动化授权收敛成可枚举白名单而非提示词承诺；一切意外往最保守的方向倒。

下一步的方向也已经清楚：接入 Alertmanager 真实告警源、去重状态持久化（Redis TTL 替代内存字典）、失败诊断自动重试，以及——把决策底座从 Claude Opus 换成自训小模型。后者正是配套项目 aiops-agentic-rl 做的事：Cold Start SFT + GRPO 后训练，把同一套系统的诊断能力迁移到 Qwen3.5-9B 上。见那篇博客。
