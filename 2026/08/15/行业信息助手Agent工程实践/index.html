🧠 手把手拆解：一个「六专家协奏 + 可验证纠错」的多智能体领域分析系统

不再是把大模型当成一个「会聊天的 API」，而是把它拆成六个各司其职的虚拟专家，用一个精心设计的共享状态机让他们像一支投研团队一样协作；再给这支团队装上证据链路、对抗审核、引用校验、预算降级和量化评测，让「研究完成」升级为「带证据、把关后才完成」。本文从一名 AI Agent 开发工程师的视角，深度解析开源项目 领域信息分析系统（DeepResearch V2.0），凡是代码里真实存在的地方，我都会给出文件路径和关键实现，希望能帮你把「多智能体」从概念落到工程。

1. 先看一眼：这个系统由什么组成

「领域信息分析系统」是一整套基于 AI Agent 的行业研究与信息监控平台。它不止有一个「深研大模型」，而是由多条 Agent 能力线协同：

能力线 说明
DeepResearch 深度研究 六个 Agent 协作 + 证据链路 + 对抗审核，产出带图表、知识图谱、引用来源、经过门禁的研究报告
智能问答（Chat） ReAct 控制器 + 工具调用，流式对话
知识库 RAG 文档切片向量化（Milvus），检索增强问答
行业资讯 / 招投标监控 APScheduler 定时采集，Agent 汇总分析
数据库 Text2SQL 用自然语言查询结构化表
长期记忆 对话压缩、向量记忆检索

其中以 DeepResearch V2.0 的多智能体编排 + 可验证纠错最为精华，本文作为主线展开，最后补上 ReAct 问答、RAG、记忆等支线。

2. 核心一：多智能体的「角色分治」

「多智能体」不是把任务扔给一个 LLM 反复催，而是让不同角色的 Agent 承担不同认知子任务。这个系统定义了一支「虚拟投研团队」，代码在 backend/app/service/deep_research_v2/agents/：

Agent 角色绰号 认知职责 对应文件
ChiefArchitect 📐 总架构师 意图解码、知识图谱初始化、动态大纲、进度监控 architect.py
DeepScout 🕵️ 深度侦探 全网穿透搜索、递归追线索、信源评级、交叉验证、增强去重 scout.py
DataAnalyst 📊 数据分析师 从文本抽取结构化数据、构建实体关系图、生成图表配置 data_analyst.py
CodeWizard 🛠️ 数据极客 写 Python 洗数、算指标、画图，且能自我纠错 wizard.py
LeadWriter ✍️ 首席笔杆 串接信息为逻辑严密的 Markdown 报告、规范引用、输出 claims 证据绑定 writer.py
CriticMaster 🔍 毒舌评论家 对抗式质检、四维评分、智能路由补搜/修订 critic.py
Verifier ✅ 独立核验员 逐条核验 claims 的证据支撑，产出 grounding 覆盖率 verifier.py

知识点：角色分治（Role Decomposition）
把「写研究报告」这个开放式大任务，拆成规划、检索、分析、写作、审核、核验等彼此正交的子任务，各配一个精心设计的 system prompt。好处是：每个 prompt 聚焦单一职责，行为更可控、更可测试；坏处是：Agent 之间需要清晰的交接契约——这就引出下一个知识点。

所有 Agent 继承同一个基类 BaseAgent（base.py），它有固定骨架：

class BaseAgent(ABC):
    def __init__(self, name, role, llm_api_key, llm_base_url, model):
        self.client = OpenAI(api_key=..., base_url=...)   # 每个 Agent 各自持有一个 LLM 客户端
        ...
    @abstractmethod
    async def process(self, state: ResearchState) -> ResearchState: ...

关键点：

  • 子类只做一件事——实现 process(state)，入参出参都是同一个 ResearchState。
  • 基类封装了 call_llm（带 JSON 强制模式、可调 temperature、异步线程化，并统一挂载预算记账与失败降级，见 §8）、parse_json_response（容错解析）、add_message（推送 SSE）、add_log（记日志）。
  • 用 AgentRegistry 做轻量注册表，方便按名称取 Agent。

3. 核心二：全局「工作记忆」—— 多智能体的共享大脑

智能体协作最大的设计难题是：每个 Agent 怎么「记住」别的 Agent 干过什么？

很多 Demo 的做法是把大段文本来回拼接，但这里选择了结构化共享状态：定义一份 ResearchState（state.py），用 TypedDict 描述，所有 Agent 读写的是同一块工作记忆。

class ResearchState(TypedDict):
    query: str                    # 用户原始问题
    outline: List[Dict]           # 动态大纲（章节，含 section_type/status）
    facts: List[Dict]             # 结构化事实库（含 credibility_score 可信度）
    data_points: List[Dict]       # 数据点
    charts: List[Dict]            # 图表
    draft_sections: Dict[str,str] # 分章节草稿
    final_report: str
    critic_feedback: List[Dict]   # 评论家反馈
    unresolved_issues: int
    knowledge_graph: Dict         # {nodes, edges}
    pending_search_queries: List  # 审核后待补搜的查询
    # ---- 演进新增：可验证纠错 / 评测字段 ----
    review_dimensions: Dict       # 四维质量评分 {factual_consistency, logic_completeness, research_coverage, citation_quality}
    grounding: List[GroundingRecord]   # claim-evidence 绑定记录
    grounding_coverage: float     # supported claims / total claims
    revision_history: Dict[str, Any]   # 章节修订历史 {section_id: [RevisionRecord]}
    rolled_back_sections: List[str]   # 被自动回滚的章节 id
    citation_validation: Dict     # 引用校验 {valid, invalid, orphan, total}
    grounding_gate: Dict          # 最终门禁 {grounding_coverage, gate_passed, reason}
    ...

其中 Fact 还新增了 canonical_url（规范化 URL），供去重 / 引用校验 / 回源使用（state.py:57）。

3.1 为什么「结构化」比「文本拼接」更优

  • 事实带元数据。每条 Fact 带 source_url、source_type、credibility_score、canonical_url。这让后续「引用回溯」和「审核查幻觉」有据可依——报告里每个结论都能回溯到来源。
  • 大纲是「可执行计划」。不是一串文字，而是带 status（pending/drafted/reviewed）的章节对象。DeepScout 只处理 status == "pending" 的章节，天然形成规划-执行闭环。
  • 可序列化、可持久化。整个 state 能被存进数据库做断点续跑（见 §12）——这是「文本拼接」方案做不到的。

3.2 状态机：阶段驱动切换

ResearchPhase 是个枚举状态机（state.py），定义了完整生命周期：

INIT → PLANNING → RESEARCHING → ANALYZING → WRITING
     → REVIEWING → (RE_RESEARCHING | REVISING) → COMPLETED

每个阶段本质是一组状态不变量：比如 REVIEWING 阶段只能由 Critic 处理，process() 开头会做前置断言：

if state["phase"] != ResearchPhase.REVIEWING.value:
    return state   # 不是我的阶段，我不碰

知识点：基于状态的 Agent 路由
用 phase 字段而非 if-else 硬编码来驱动流程，好处是新增 Agent 只需新增一个 phase 分支，耦合度低、可扩展。

4. 核心三：LangGraph 编排 vs 自研执行器

4.1 为什么会用到 LangGraph

DeepResearchGraph（graph.py）一开始用 LangGraph 建模——把 Agent 定义为节点，把流程定义为有向图：

workflow = StateGraph(ResearchState)          # 用状态定义图
workflow.add_node("plan", self._plan_node)
workflow.add_node("research", self._research_node)
...
workflow.set_entry_point("plan")
workflow.add_edge("plan", "research")
workflow.add_edge("write", "review")
# 关键是"条件边"：审核后决定下一步
workflow.add_conditional_edges("review", self._should_revise,
    {"revise": "revise", "complete": END})
workflow.add_edge("revise", "review")         # 修订后再审，形成环

LangGraph 的卖点是天然支持循环、条件分支和状态注入，非常适合「计划-执行-评估-重做」这类非线形流程。

4.2 为什么最终没有用它做实时执行

代码注释里写得非常坦诚：

LangGraph 版本会批量处理消息，无法实现实时流式输出。

深研这活，用户最想看到的恰恰是过程——搜到了什么、写到哪一章、图表出来了没、审核过了没。如果研究全程：思考……思考……（1 分钟后）……完成，观感是灾难级的。

所以最终执行走的是手写版 _run_simplified：维护一份与 LangGraph 节点一一对应的 plan/research/analyze/write/review/revise/verify 若干 async 步骤，再用 asyncio.Queue 做消息通道。LangGraph 版本保留了，但被注释掉作为备选。

message_queue = asyncio.Queue()
state["_message_queue"] = message_queue

async def run_agent_with_streaming(agent):
    task = asyncio.create_task(agent.process(state))   # 后台跑 Agent
    while not task.done():
        msg = await asyncio.wait_for(message_queue.get(), timeout=0.5)
        yield msg                                       # 逐条流式推给前端
    await task

工程启示：图为纪律，执行为体验。 LangGraph 负责表达「该走哪条路」的语义；但在需要细粒度流式、即时取消、可控重试的交互场景，手写一个轻量驱动循环往往更务实。这是「编排框架 vs 真实需求」之间很常见的一次权衡。

5. 核心四：工具调用 —— 让 Agent 长出「手」

一个只会「说话」的 Agent 写不了行业报告。系统用一套 工具集 让 Agent 能真正拿到事实。这部分在 react_controller.py 定义了明确工具枚举：

class ToolType(Enum):
    WEB_SEARCH = "web_search"         # 全网搜索
    KNOWLEDGE_SEARCH = "knowledge_search"  # 本地知识库检索
    TEXT2SQL = "text2sql"             # 自然语言查库
    DATA_ANALYZER = "data_analyzer"   # 智能数据分析
    CHART_GENERATOR = "chart_generator" # 图表生成
    STOCK_QUERY = "stock_query"       # 股票实时行情
    BIDDING_SEARCH = "bidding_search" # 招投标检索
    FINISH = "finish"                 # 结束研究，汇总生成报告

知识点：ReAct 范式
ReAct = Reasoning + Acting。模型不直接给出最终答案，而是交替产出 Thought（我要干什么）→ Action（调用哪个工具、传什么参数）→ 得到 Observation（工具结果）→ 再 Thought…… 直到拿到 Finish。

ReActContext 负责在回合间累积上下文：

class ReActContext:
    def __init__(self, query):
        ...
    def add_step(self, step): ...        # 记录每一步
    def add_observation(self, obs): ...  # 记录工具观测
    def get_history_summary(self, max_items=10): ...  # 压缩历史供提示词使用
    def get_collected_data_summary(self, max_items=20): ...  # 已收集数据汇总

笔记里还有一个很实在的设计：_validate_and_fix_params（react_controller.py）——模型生成的工具参数可能缺字段或格式不对，系统会在真正调用前做参数校验与纠偏，比如从 thought 里兜底抽取搜索词：

def _validate_and_fix_params(self, tool_name, params, thought, context):
    if tool_name == ToolType.WEB_SEARCH.value:
        # 参数不完整就从 thought 里补一个搜索词，而不是直接报错
        ...
    def _extract_search_query_from_thought(self, thought, context): ...

知识点：结构化输出的韧性
大模型返回的「工具调用/JSON」经常残缺。单靠 response_format=json_object 不够——工程上要用解析器 + 校验器 + 兜底抽取三层防御。这是把 Agent 从「演示」推进到「生产」的分水岭。

5.1 搜索缓存：省钱的关键

工具执行层（tool_executor.py）还做了一层结果缓存：

SEARCH_CACHE_TTL = 3600                      # 缓存 1 小时
_search_cache: Dict[str, Tuple[List, float]] = {}

def get_query_hash(query): return hashlib.md5(query.lower().encode()).hexdigest()

def get_cached_search(query): ...            # 命中缓存直接返回

多智能体多次围绕同一问题挖掘时，相同检索词直接命中缓存，省 API 配额也省延迟。

6. 核心五：代码生成 Agent + 自愈执行（Self-Repair）

CodeWizard 是本项目最有「Agent 味」的模块：它不只是让 LLM 分析，而是真的写 Python 代码去执行——算 CAGR、做同比、画 matplotlib 图，每张图都是一段可执行代码。

执行并不是「跑一次，失败算了」，而是带自愈闭环（wizard.py）：

async def _execute_with_self_correction(self, code, state, max_retries=3):
    current_code = code
    for retries in range(max_retries + 1):
        result = await self._execute_code(current_code)
        if result.get("success"):
            return {..., "final_code": current_code}   # 成功即返回
        # 失败 → 把错误喂回 LLM 让它修
        fixed = await self._fix_code(current_code, result.get("error"), result.get("output"))
        if fixed and fixed.get("fixed_code"):
            current_code = fixed["fixed_code"]
    ...

其内部 _fix_code 会用专门的「Python 调试专家」prompt，把错误堆栈和 stdout 喂回去要一段修复后的代码。

安全双保险（wizard.py::_execute_in_sandbox）：

  • 入口：正则黑名单拦截 os/sys/subprocess/open/eval/requests 等危险模式。
  • 运行：自定义 safe_import + 受限 __builtins__（open=None 禁用文件 IO），只放行 pandas/numpy/matplotlib/seaborn 等数据分析模块。

知识点：Agent 代码执行的两大难点
① 沙箱隔离：绝不直接 eval/exec 用户或模型生成的代码，必须限制文件系统、网络、CPU 时长。② 自愈循环（Self-Repair）：把报错反馈进上下文再生成一次，是「让 Agent 学会运行」的实用手段。CodeWizard 正是把这两件事都处理了的范例。已知边界：当前是轻量沙箱（正则 + 受限 exec），生产环境应升级为容器级隔离——代码注释里明确标注了这一点。

7. 核心六：可验证纠错 —— 从「Reflexion」升级为「证据链路 + 对抗审核 + 门禁」

写完全部内容还远没结束。系统用一个对抗式审核闭环保证质量，并在此基础上叠加了逐句证据核验与最终门禁，让「自纠错」可追踪、可审计、可量化。

7.1 对抗审核 + 四维评分（CriticMaster）

CriticMaster 扮演永不满意的审稿人（critic.py）。审核输出结构化结果：quality_score（1-10）+ 四维评分 dimension_scores + issues 列表（含 issue_type、严重级别、修改建议）：

"dimension_scores": {
    "factual_consistency": 1-10,   # 事实一致性
    "logic_completeness": 1-10,    # 逻辑完整性
    "research_coverage": 1-10,     # 研究覆盖度
    "citation_quality": 1-10       # 引用质量
}

四维分写入 state["review_dimensions"]（critic.py:188），既用于驱动修订，也直接对齐评测判分器口径——审查说的问题和评测打的分能对上。

7.2 智能路由：补搜还是纯修订

research_needed_types = {"missing_source", "incomplete", "outdated"}  # 需要重新搜索
  • 问题类型是 missing_source / incomplete / outdated → 说明信息不够，回退到 RE_RESEARCHING，派 DeepScout 补搜（收集 pending_search_queries）。
  • 问题类型是逻辑/表述 → 信息够了但表达差，走 REVISING 直接让 Writer 改文字。
  • 严重问题中需搜索的占比过低则不整流程回检索，避免小题大做重跑全搜索。

7.3 独立 Verifier：逐句证据核验（Claim-Evidence 链路）

审查角色管「报告整体质量 + 路由」，核验角色专管「每一句主张有没有证据」——两道把关线独立运行：

Step 1｜写作绑定：LeadWriter 写每个章节时，输出结构化 claims（含 evidence_fact_ids，绑定事实库中的事实 id），写入 state["grounding"]（writer.py）。

Step 2｜独立判定：VerifierAgent（verifier.py）逐条判定 verdict：

supported    → 有明确证据（引用的事实与 claim 一致）
unsupported  → 无证据绑定或证据与 claim 不符
ambiguous    → 证据存在但语义模糊
contradicted → 证据与 claim 互相矛盾

Step 3｜算覆盖率：grounding_coverage = supported claims / total claims，写回 state["grounding_coverage"]（verifier.py:167）。

7.4 章节级修订 + 自动回滚

  • 只重写问题章节：_revise_sections（writer.py:558）按审核反馈的 target_section 定位，只重写被点名的章节，其它章节原样保留；_reassemble_final_report 重组报告。
  • 自动回滚：_auto_rollback（writer.py:791）记录 revision_history[section_id]，复检后若综合分低于修订前基线，回退到历史最高分版本——改坏了能反悔。
  • 整合兜底：_synthesize_report 失败时用 draft_sections 组装 fallback 报告，保证不产出空报告（这是本轮评测暴露并修复的真实 bug，见 §13）。

7.5 引用校验 + 最终 Grounding 门禁

报告放行前，graph.py completion 段做两道最终把关：

  1. 引用校验（citation_validator.py::validate_report）：把报告行内链接与来源池（references + facts + raw_sources 的 canonical URL）比对，判 valid / invalid / orphan；evidence_link.py::normalize_url 先做 URL 规范化（去 tracking 参数）保证比对准确。
  2. Grounding 门禁：grounding_coverage ≥ 0.9 且无 contradicted 才放行，否则拦截在完成之前，并通过 SSE 事件 grounding_gate 让前端可见（graph.py:756-775）。
if cov < 0.9 or contradicted:
    gate_passed = False
    state["grounding_gate"] = {
        "grounding_coverage": cov, "gate_passed": False,
        "reason": f"grounding_coverage={cov:.2f}<0.9 或存在 {len(contradicted)} 条矛盾 claim",
    }
    yield {"type": "grounding_gate", "content": state["grounding_gate"]}

知识点：反思型循环（Reflexion）进阶
关键洞察是把「评估信号」写回共享状态（critic_feedback、unresolved_issues、review_dimensions、grounding），让下一轮基于反馈改进。比起盲目重跑，基于结构化反馈、按需补搜/修订的成本更低、收敛更快。再加 独立核验 + 覆盖率门禁，把「自纠错」从「改了没有」升级为「有没有证据支撑、证据够不够」，可追踪、可量化。max_iterations 仍保证系统一定终止。

8. 模型路由与预算控制：省钱又保质、失败不崩流程

8.1 异构模型路由

一个被很多人忽略、但直接影响成本与质量的设计——每个 Agent 模型独立配置（llm_config.py）：

# 演进后：多智能体统一走中转 OpenAI 兼容端点，Agent 模型全部 qwen3.7-plus
MA_LLM_BASE_URL = "https://llm.goaichat.top/v1"
MA_LLM_MODEL    = "qwen3.7-plus"   # MA_LLM_* 优先于 DASHSCOPE_*

知识点：异构模型路由 / 模型分层
认知负载低的子任务（搜索）用便宜快速的模型，认知负载高、输出长的子任务（写作）用强模型。同时每个 Agent 可独立调节 temperature（规划/写作偏高利于发散，数据提取/代码偏低利于精确）。用「模型 × 角色 × 温度」的多维矩阵做调度，是规模化 Agent 的成本结构核心。

8.2 预算控制与失败分类降级（BudgetController）

多智能体一次研究几十次模型调用，单个失败直接抛异常会中断整篇研究。budget_controller.py 做了两件事：

class BudgetController:
    def before_call(self) -> None: ...        # 调用前记账
    def after_call(self, tokens_used): ...    # 调用后记账
    def check_token(...) / check_call(...): ... # 超限抛 BudgetError
    def classify_error(exc) -> str: ...       # rate_limit / timeout / transient / other
    async def handle_failure(exc, stage) -> str: ...  # retry / degraded / fatal
  • 预算记账：在统一调用出口 agents/base.py::call_llm 挂载，记录 token 与调用次数，设上限。
  • 失败分类降级：rate_limit → 退避重试；timeout/transient → 重试一次后降级（跳过该步产出或占位）；超预算 → 抛 BudgetError 触发降级。单点失败不崩流程。

知识点：长流程可靠性
这不是「加个 try/except」——而是把「失败」建模成有分类、有重试预算、有降级路径的受控状态。降级会牺牲部分产出，但换来「长流程不脆弱」。实测：评测跑动时中转端点多次 Connection error，正是这套降级让流程一次次挺过来、没有因为单个角色失败整篇作废。

9. 实时感知：多智能体怎么把「过程」流式给用户

前面提到用 asyncio.Queue 做消息管道。BaseAgent.add_message 是所有 Agent 向外界发声的统一出口：

def add_message(self, state, event_type, content):
    message = {"type": event_type, "agent": self.name,
               "timestamp": ..., "content": content}
    state["messages"].append(message)
    if "_message_queue" in state and state["_message_queue"]:
        state["_message_queue"].put_nowait(message)   # 立即推给 SSE

于是前端能收到统一的事件类型流：

research_start → phase(planning) → thought(架构师) → research_step...
→ phase(researching) → action(search) → research_step(completed)
→ phase(analyzing) → code_fix → phase(writing) → review...
→ grounding_gate → research_complete

演进后新增了 grounding_gate 等事件，让前端能看到最终放行前的最后一道把关。

知识点：Agent 的可观测性 / 事件协议
一个健壮的多智能体系统必须把「它在想什么、在做什么」变成可观测的事件流，而不是只知道一个最终结果。定一套统一事件协议（阶段/思考/行动/步骤/反馈/门禁），前端才有东西可渲染，用户也才有「它在干活」的信任感。

10. 断点续跑：状态持久化（含序列化踩坑）

深研可能很长、浏览器可能刷新。系统用一个 CheckpointService（checkpoint_service.py）在每个阶段结束保存检查点，把后端状态 + UI 状态都落库到 research_checkpoints 表：

self._save_checkpoint(session_id, state, ui_state)   # graph.py 中每阶段调一次
# 恢复
state = self._load_checkpoint(session_id)            # resume=True 时
if state: yield {"type": "research_resumed", ...}

知识点：Agent 的持久化（Checkpointing）
开放式长任务一定有中断风险（会话过期、刷新、超时）。把结构化的状态做成可恢复的快照，让 Agent 能从中断处继续，而不是推倒重来——这是从「玩具」走向「可用产品」的关键能力。

踩坑实录（本轮评测暴露的真实 bug）：ResearchState 里存了运行期对象 _message_queue（asyncio.Queue），直接塞进 state_json 落库会报 Object of type Queue is not JSON serializable。正确做法是落库前剔除运行期字段（_message_queue/message_queue），只持久化可序列化的业务字段。这提醒我们：能落库的 state 和能运行的 state 之间，要做「可序列化边界」。

11. 对话线：ReAct 智能问答 —— 让 Agent 会「查」

除了深研，系统还有一条独立的对话型 Agent 线：ReActController（react_controller.py）+ ToolExecutor（tool_executor.py）。逻辑很典型：

  1. Think：根据用户问题 + 历史上下文，由 LLM 决定下一步该干嘛（用哪个工具）。
  2. Act：调用工具（搜索 / 查库 / 分析 / 画图），拿到 Observation。
  3. Loop：把 Observation 再喂回，重复 Think-Act，直到 LLM 判断 Finish。
  4. 汇总后生成回答。

这里的技术细节是——单轮内可以是多工具接力：比如「智慧交通最新政策有哪些？」→ 先 web_search 找新闻 → 再 text2sql 查行业数据表 → 用 data_analyzer 算近三年增速 → 汇总结论。工具之间通过 ReActContext 累积的 collected data 串联。

知识点：Plan-and-Execute vs ReAct
深研用的是更狠的 Plan-and-Execute（先规划再并行执行），对话问答则用 ReAct（边想边做）。两者适用场景不同：开放式长研究适合先规划，交互式问答适合即时推理。一个成熟系统往往同时混用多种 Agent 模式。

12. 记忆与检索：让 Agent 有「长期记忆」和「知识库」

12.1 Long-Term Memory（memory_service.py）

对话型 Agent 的记忆不只靠上下文窗口硬塞，而是做摘要压缩 + 向量化存库 + 按需召回：

  • should_compress(messages)：消息太多就触发压缩。
  • summarize_conversation(messages)：让 LLM 把冗长对话压成要点。
  • _store_memory_vectors(...)：压缩后的记忆向量化存进 Milvus。
  • retrieve_memories(...)：新一轮对话先用语义检索召回相关历史记忆。
  • build_memory_context(...)：把召回的旧记忆拼进提示词，Agent 才「记得你」。

知识点：Agent 记忆分级
记忆分为：工作记忆（当前 window）、长期记忆（跨 session 存 Postgres + 向量）、程序记忆（技能/工具/策略）。本项目把长期记忆做了摘要压缩 + 向量检索，是比「全量塞上下文」更省 token 且更有关联性的做法。

12.2 RAG 检索（retrieval_service.py）

query_vectors = generate_embedding([question])   # 问题 embedding
results = milvus.search(...)                     # 向量检索（本地知识库）
# 可选：走 rerank 精排，提高命中准确率

完整链路：DocMind（可选）解析文档 → 切片 → embedding → Milvus 存向量 → 相似度召回 → rerank 精排 → 拼入上下文。这让 Agent 既能「搜全网」（web_search）也能「查私有资料」（knowledge_search）。

13. 工程韧性：那些让 Agent 真正能用的「脏活」

聊了这么多华丽的 Agent 能力，最后必须强调——真正拉开生产级与 Demo 差距的，都是不起眼的工程韧性：

13.1 容错 JSON 解析（base.py）

LLM 的 JSON 输出经常出 bug，parse_json_response 打了一套组合拳：

def parse_json_response(self, response):
    # 1. 直接解析；2. 抽 markdown ```json 代码块
    # 3. 找最外层花括号；4. ast.literal_eval 兜底
    # 并内置修复：无引号 key、尾随逗号、无效转义（\[ \]）、注释、缺逗号...

（还对 code 字段特殊处理：不破坏代码里的 \n 转义——这是很多人会踩的坑。）

13.2 中途取消（graph.py）

async def check_cancelled():
    if is_research_cancelled(session_id): return True
# 每个 Agent 启动前、执行中都检查
task.cancel(); await task    # 用户点「取消」→ 干净地中断

取消标志放 Redis（带有效期），即使多实例部署也能全局读到。

13.3 强制定量：防死循环

max_iterations、max_searches_per_section、max_charts、quality_threshold 处处封顶，保证系统一定在有限步内终止，不会烧光预算。

13.4 报告为空兜底（本轮评测暴露并修复）

writer.py::_write_section 的 call_llm + JSON 解析失败时，不再让异常中断整个写作阶段——改为用素材摘要兜底，保证 draft_sections 每个章节至少非空，_synthesize_report 永远能拼出有内容的报告。这是把「降级不崩流程」落实到产出层面的关键。

13.5 搜索事实增强去重

fact_dedup.py + evidence_link.py：URL 规范化（同源判重）+ 内容指纹（精确去重）+ 语义相似度（同义去重，embedding 不可用时熔断降级回前两层），防止事实库被同源信息灌水。

14. Direct vs Multi-Agent 配对量化评测

多智能体多了编排与 token 开销，价值若没有量化就难自证。项目搭了一条配对评测流水线（backend/app/eval/）：

环节 实现
评测集 公开 Deep Research Bench（DRB）中文子集 id 1-5（dataset/cn_drb_5.jsonl）
Direct 基座 runners/direct_llm.py：用生成模型（qwen3.7-plus）直接出报告，带退避重试
Multi-Agent runners/multi_agent.py：跑完整流水线，采集 quality/grounding_gate 等评测字段
判分器 judge.py：RACE 四维（comprehensiveness/depth/instruction-following/readability）+ FACT 引用，temperature=0 保证可复现，双判取均值压随机性
编排与聚合 run_comparison.py 配对逐题跑；aggregate.py 输出 Direct/Multi 均值、维度 Δ、配对差

关键设计：生成模型与评测模型分离。Direct 和 Multi-Agent 都用同一个生成模型（qwen3.7-plus），判分用独立的强模型（deepseek-v4-pro）——对照组与实验组只差「有没有多智能体编排」，不差模型，这样 Δ 才是编排本身的贡献。

cd backend && python app/eval/run_comparison.py   # 5 题配对，1.5-3h

知识点：Agent 系统的量化评测
评测不是跑几个数就完事。要点：① 对照基线（Direct 直出）与实验组（Multi-Agent）用同一生成模型；② 判分器独立于生成、低温、多次取均值；③ 标注口径（题源、判分器、题数），只做内部可复现对比，不与外部 leaderboard 直接比；④ 如实记录失败（本轮 Direct 曾因网络 Connection error 失败 3/5、Multi-Agent 曾报告为空——修复后重跑），不编造数字。多智能体相对直出的增量主要落在 depth（研究深度）——这正是编排该补的维度。

16. Agent 工程师的几点心得

  1. 先定契约，再谈 Agent。 七个 Agent 能协作，靠的不是聪明，而是 ResearchState 这份结构化契约。先画好 Agent 之间的数据流图，再逐个实现 Agent。
  2. 模型是下限，工程是上限。 真正拉开体验的，是坏 JSON 兜底、代码自愈、中途取消、断点续跑、报告空兜底这些脏活。大模型负责「聪明」，工程负责「可靠」。
  3. 自纠错要可追踪、可量化。 光说「我让 AI 审 AI」没用——把审查结构化（四维分）、把主张绑定证据（claims→facts）、把放行变成门槛（grounding≥0.9），纠错才有据可依、可回溯、可测量。
  4. 按认知成本路由模型，但生成/评测要分离。 对照组和实验组用同一生成模型，判分用独立强模型——否则你比较不出来「多智能体」的价值，只比较出「模型不同」。
  5. 预算与降级是长流程的刚需。 一次研究几十次调用，不做预算记账和失败分类降级，任何一次网络抖动都可能整篇作废。
  6. 过程比结果更值得做可观测。 一个长时间无反馈的 Agent，用户早跑了。用统一事件协议 + 流式输出，把「它在思考」变成产品体验。
  7. 永远有终止条件。 任何反思/重试循环都要有 max_iterations 这样的硬限制定量，否则灾难。
