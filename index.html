🧠 手把手拆解：一个「六专家协奏」的多智能体行业研究系统

不再是把大模型当成一个「会聊天的 API」，而是把它拆成六个各司其职的虚拟专家，用一个精心设计的共享状态机让他们像一支投研团队一样协作。本文从一名 AI Agent 开发工程师的视角，深度解析开源项目 行业信息助手（github.com/wjl8636/Industry-Information-Assistant），凡是代码里真实存在的地方，我都会给出文件路径和关键实现，希望能帮你把「多智能体」从概念落到工程。

0. 本文你会收获什么

这篇文章不是功能清单，而是围绕一个真实项目梳理 Agent 工程的核心知识图谱。我尽量把抽象的概念（多智能体、工作记忆、ReAct、Reflexion、工具调用、状态持久化、模型路由、流式输出……）都对应到一段真实代码，让你看完能直接用。

涵盖的主题索引：

  • 多智能体的角色分治与流水线组织
  • LangGraph 与自研执行器的取舍
  • 全局共享状态设计
  • ReAct 循环与 工具调用体系
  • Reflexion 式对抗审校闭环

  • SSE 实时流式的实现

  • 工程韧性：坏 JSON 解析、取消机制、缓存

1. 先看一眼：这个系统由什么组成

「行业信息助手」是一整套基于 AI Agent 的行业研究与信息监控平台。它不止有一个「深研大模型」，而是由多条 Agent 能力线协同：

能力线 说明
DeepResearch 深度研究 六个 Agent 协作产出带图表、知识图谱、引用来源的研究报告
智能问答（Chat） ReAct 控制器 + 工具调用，流式对话
知识库 RAG 文档切片向量化（Milvus），检索增强问答
行业资讯 / 招投标监控 APScheduler 定时采集，Agent 汇总分析
数据库 Text2SQL 用自然语言查询结构化表
长期记忆 对话压缩、向量记忆检索

其中以 DeepResearch V2.0 的多智能体编排最为精华，本文作为主线展开，最后补上 ReAct 问答、RAG、记忆等支线。

2. 核心一：多智能体的「角色分治」

「多智能体」不是把任务扔给一个 LLM 反复催，而是让不同角色的 Agent 承担不同认知子任务。这个系统定义了一支「虚拟投研团队」，代码在 backend/app/service/deep_research_v2/agents/：

Agent 角色绰号 认知职责 对应文件
ChiefArchitect 📐 总架构师 意图解码、知识图谱初始化、动态大纲、进度监控 architect.py
DeepScout 🕵️ 深度侦探 全网穿透搜索、递归追线索、信源评级、交叉验证 scout.py
DataAnalyst 📊 数据分析师 从文本抽取结构化数据、构建实体关系图、生成图表配置 data_analyst.py
CodeWizard 🛠️ 数据极客 写 Python 洗数、算指标、画图，且能自我纠错 wizard.py
LeadWriter ✍️ 首席笔杆 串接信息为逻辑严密的 Markdown 报告、规范引用 writer.py
CriticMaster 🔍 毒舌评论家 对抗式质检、逻辑漏洞检测、幻觉查杀、偏见识别 critic.py

知识点：角色分治（Role Decomposition）
把「写研究报告」这个开放式大任务，拆成规划、检索、分析、写作、审核等彼此正交的子任务，各配一个精心设计的 system prompt。好处是：每个 prompt 聚焦单一职责，行为更可控、更可测试；坏处是：Agent 之间需要清晰的交接契约——这就引出下一个知识点。

所有 Agent 继承同一个基类 BaseAgent（base.py），它有固定骨架：

class BaseAgent(ABC):
    def __init__(self, name, role, llm_api_key, llm_base_url, model):
        self.client = OpenAI(api_key=..., base_url=...)   # 每个 Agent 各自持有一个 LLM 客户端
        ...
    @abstractmethod
    async def process(self, state: ResearchState) -> ResearchState: ...

关键点：

  • 子类只做一件事——实现 process(state)，入参出参都是同一个 ResearchState。
  • 基类封装了 call_llm（带 JSON 强制模式、可调 temperature、异步线程化）、parse_json_response（容错解析）、add_message（推送 SSE）、add_log（记日志）。
  • 用 AgentRegistry 做轻量注册表，方便按名称取 Agent。

3. 核心二：全局「工作记忆」—— 多智能体的共享大脑

智能体协作最大的设计难题是：每个 Agent 怎么「记住」别的 Agent 干过什么？

很多 Demo 的做法是把大段文本来回拼接，但这里选择了结构化共享状态：定义一份 ResearchState（state.py），用 TypedDict 描述，所有 Agent 读写的是同一块工作记忆。

class ResearchState(TypedDict):
    query: str                    # 用户原始问题
    outline: List[Dict]           # 动态大纲（章节，含 section_type/status）
    facts: List[Dict]             # 结构化事实库（含 credibility_score 可信度）
    data_points: List[Dict]       # 数据点
    charts: List[Dict]            # 图表
    draft_sections: Dict[str,str] # 分章节草稿
    final_report: str
    critic_feedback: List[Dict]   # 评论家反馈
    unresolved_issues: int
    knowledge_graph: Dict         # {nodes, edges}
    pending_search_queries: List  # 审核后待补搜的查询
    ...

3.1 为什么「结构化」比「文本拼接」更优

  • 事实带元数据。每条 Fact 带 source_url、source_type、credibility_score。这让后续「引用回溯」和「审核查幻觉」有据可依——报告里每个结论都能 tắtaback 到来源。
  • 大纲是「可执行计划」。不是一串文字，而是带 status（pending/drafted/reviewed）的章节对象。DeepScout 只处理 status == "pending" 的章节，天然形成规划-执行闭环。
  • 可序列化、可持久化。整个 state 能被存进数据库做断点续跑（见第 10 节）——这是「文本拼接」方案做不到的。

3.2 状态机：阶段驱动切换

ResearchPhase 是个枚举状态机（state.py），定义了完整生命周期：

INIT → PLANNING → RESEARCHING → ANALYZING → WRITING
     → REVIEWING → (RE_RESEARCHING | REVISING) → COMPLETED

每个阶段本质是一组状态不变量：比如 REVIEWING 阶段只能由 Critic 处理，process() 开头会做前置断言：

if state["phase"] != ResearchPhase.REVIEWING.value:
    return state   # 不是我的阶段，我不碰

知识点：基于状态的 Agent 路由
用 phase 字段而非 if-else 硬编码来驱动流程，好处是新增 Agent 只需新增一个 phase 分支，耦合度低、可扩展。

4. 核心三：LangGraph 编排 vs 自研执行器

4.1 为什么会用到 LangGraph

DeepResearchGraph（graph.py）一开始用 LangGraph 建模——把 Agent 定义为节点，把流程定义为有向图：

workflow = StateGraph(ResearchState)          # 用状态定义图
workflow.add_node("plan", self._plan_node)
workflow.add_node("research", self._research_node)
...
workflow.set_entry_point("plan")
workflow.add_edge("plan", "research")
workflow.add_edge("write", "review")
# 关键是"条件边"：审核后决定下一步
workflow.add_conditional_edges("review", self._should_revise,
    {"revise": "revise", "complete": END})
workflow.add_edge("revise", "review")         # 修订后再审，形成环

LangGraph 的卖点是天然支持循环、条件分支和状态注入，非常适合「计划-执行-评估-重做」这类非线形流程。

4.2 为什么最终没有用它做实时执行

代码注释里写得非常坦诚（graph.py:349）：

LangGraph 版本会批量处理消息，无法实现实时流式输出。

深研这活，用户最想看到的恰恰是过程——搜到了什么、写到哪一章、图表出来了没。如果研究全程：思考……思考……（1 分钟后）……完成，观感是灾难级的。

所以最终执行走的是手写版 _run_simplified：维护一份与 LangGraph 节点一一对应的 plan/research/analyze/write/review/revise 六个 async 步骤，再用 asyncio.Queue 做消息通道。LangGraph 版本保留了，但被注释掉作为备选。

message_queue = asyncio.Queue()
state["_message_queue"] = message_queue

async def run_agent_with_streaming(agent):
    task = asyncio.create_task(agent.process(state))   # 后台跑 Agent
    while not task.done():
        msg = await asyncio.wait_for(message_queue.get(), timeout=0.5)
        yield msg                                       # 逐条流式推给前端
    await task

工程启示：图为纪律，执行为体验。 LangGraph 负责表达「该走哪条路」的语义；但在需要细粒度流式、即时取消、可控重试的交互场景，手写一个轻量驱动循环往往更务实。这是「编排框架 vs 真实需求」之间很常见的一次权衡。

5. 核心四：工具调用 —— 让 Agent 长出「手」

一个只会「说话」的 Agent 写不了行业报告。系统用一套 工具集 让 Agent 能真正拿到事实。这部分在 react_controller.py 定义了明确工具枚举：

class ToolType(Enum):
    WEB_SEARCH = "web_search"         # 全网搜索
    KNOWLEDGE_SEARCH = "knowledge_search"  # 本地知识库检索
    TEXT2SQL = "text2sql"             # 自然语言查库
    DATA_ANALYZER = "data_analyzer"   # 智能数据分析
    CHART_GENERATOR = "chart_generator" # 图表生成
    BIDDING_SEARCH = "bidding_search" # 招投标检索

知识点：ReAct 范式
ReAct = Reasoning + Acting。模型不直接给出最终答案，而是交替产出 Thought（我要干什么）→ Action（调用哪个工具、传什么参数）→ 得到 Observation（工具结果）→ 再 Thought…… 直到拿到 Finish。

ReActContext 负责在回合间累积上下文：

class ReActContext:
    def __init__(self, query):
        ...
    def add_step(self, step): ...        # 记录每一步
    def add_observation(self, obs): ...  # 记录工具观测
    def get_history_summary(self, max_items=10): ...  # 压缩历史供提示词使用
    def get_collected_data_summary(self, max_items=20): ...  # 已收集数据汇总

笔记里还有一个很实在的设计：_validate_and_fix_params（react_controller.py:454）——模型生成的工具参数可能缺字段或格式不对，系统会在真正调用前做参数校验与纠偏，比如从 thought 里兜底抽取搜索词：

def _validate_and_fix_params(self, tool_name, params, thought, context):
    if tool_name == ToolType.WEB_SEARCH.value:
        # 参数不完整就从 thought 里补一个搜索词，而不是直接报错
        ...
    def _extract_search_query_from_thought(self, thought, context): ...

知识点：结构化输出的韧性
大模型返回的「工具调用/JSON」经常残缺。单靠 response_format=json_object 不够——工程上要用解析器 + 校验器 + 兜底抽取三层防御。这是把 Agent 从「演示」推进到「生产」的分水岭。

5.1 搜索缓存：省钱的关键

工具执行层（tool_executor.py）还做了一层结果缓存：

SEARCH_CACHE_TTL = 3600                      # 缓存 1 小时
_search_cache: Dict[str, Tuple[List, float]] = {}

def get_query_hash(query): return hashlib.md5(query.lower().encode()).hexdigest()

def get_cached_search(query): ...            # 命中缓存直接返回

多智能体多次围绕同一问题挖掘时，相同检索词直接命中缓存，省 API 配额也省延迟。

6. 核心五：代码生成 Agent + 自愈执行（Self-Repair）

CodeWizard 是本项目最有「Agent 味」的模块：它不只是让 LLM 分析，而是真的写 Python 代码去执行——算 CAGR、做同比、画 ECharts，每张图都是一段可执行代码。

执行并不是「跑一次，失败算了」，而是带自愈闭环（wizard.py:524）：

async def _execute_with_self_correction(self, code, state, max_retries=3):
    current_code = code
    for retries in range(max_retries + 1):
        result = await self._execute_code(current_code)
        if result.get("success"):
            return {..., "final_code": current_code}   # 成功即返回
        # 失败 → 把错误喂回 LLM 让它修
        fixed = await self._fix_code(current_code, result.get("error"), result.get("output"))
        if fixed and fixed.get("fixed_code"):
            current_code = fixed["fixed_code"]
    ...

其内部 _fix_code 会用专门的「Python 调试专家」prompt，把错误堆栈和 stdout 喂回去要一段修复后的代码。

知识点：Agent 代码执行的两大难点
① 沙箱隔离：绝不直接 eval/exec 用户或模型生成的代码，必须限制文件系统、网络、CPU 时长。② 自愈循环（Self-Repair）：把报错反馈进上下文再生成一次，是「让 Agent 学会运行」的实用手段。CodeWizard 正是把这两件事都处理了的范例。

7. 核心六：Reflexion —— 让 Agent 学会「打回去重做」

写完全部内容还远没结束。系统用一个对抗式审核闭环来保证质量，这在学术上接近 Reflexion（反思）范式。

CriticMaster 扮演永不满意的审稿人（critic.py:151）：

# 更新质量分数 & 未解决问题数
state["quality_score"] = review_result["overall_assessment"]["quality_score"]
state["unresolved_issues"] = len([i for i in issues if i["severity"] in ["critical", "major"]])

# 智能路由：决定下一步
verdict = review_result["overall_assessment"]["verdict"]
if verdict == "pass":                      state["phase"] = COMPLETED
elif iteration >= max_iterations:          state["phase"] = COMPLETED  # 硬性兜底
else:
    needs_search = self._analyze_issues_for_routing(review_result)
    if needs_search["should_research"]:    state["phase"] = RE_RESEARCHING
    else:                                  state["phase"] = REVISING
    state["iteration"] += 1

这里的聪明之处在 按问题类型做「智能路由」（critic.py:236）：

research_needed_types = {"missing_source", "incomplete", "outdated"}  # 需要重新搜索
# 否则 → 只需要文字修订
  • 问题类型是 missing_source / incomplete / outdated → 说明信息不够，回退到 RE_RESEARCHING，派 DeepScout 补搜。
  • 问题类型是逻辑/表述 → 信息够了但表达差，走 REVISING 直接让 Writer 改文字。

知识点：反思型循环（Reflexion）
关键洞察是把「评估信号」写回共享状态（critic_feedback、unresolved_issues、pending_search_queries），让下一轮基于反馈改进。比起盲目重跑，基于结构化反馈、按需补搜/修订的成本更低、收敛更快。同时用 max_iterations 防止死循环，保证系统一定终止。

8. 模型路由：不同 Agent 用不同模型

一个被很多人忽略、但直接影响成本与质量的设计——每个 Agent 模型独立配置（llm_config.py）：

# 规划师（强但贵）：分析问题、生成大纲
architect = AgentModelConfig(model="deepseek-v3.2", temperature=0.7, max_tokens=4000)
# 侦察员（快且省）：搜索阶段大量调用
scout     = AgentModelConfig(model="qwen-plus",      temperature=0.5, max_tokens=4000)
# 写手（最强，长输出）：报告撰写，拉满 token
writer    = AgentModelConfig(model="deepseek-v3.2",  temperature=0.7, max_tokens=16000)

知识点：异构模型路由 / 模型分层
认知负载低的子任务（搜索）用便宜快速的模型，认知负载高、输出长的子任务（写作）用强模型。同时每个 Agent 可独立调节 temperature（规划/写作偏高利于发散，数据提取/代码偏低利于精确）。用「模型 × 角色 × 温度」的多维矩阵做调度，是规模化 Agent 的成本结构核心。

9. 实时感知：多智能体怎么把「过程」流式给用户

前面提到用 asyncio.Queue 做消息管道。BaseAgent.add_message 是所有 Agent 向外界发声的统一出口：

def add_message(self, state, event_type, content):
    message = {"type": event_type, "agent": self.name,
               "timestamp": ..., "content": content}
    state["messages"].append(message)
    if "_message_queue" in state and state["_message_queue"]:
        state["_message_queue"].put_nowait(message)   # 立即推给 SSE

于是前端能收到统一的事件类型流：

research_start → phase(planning) → thought(架构师) → research_step...
→ phase(researching) → action(search) → research_step(completed)
→ phase(analyzing) → code_fix → phase(writing) → review...
→ research_complete

知识点：Agent 的可观测性 / 事件协议
一个健壮的多智能体系统必须把「它在想什么、在做什么」变成可观测的事件流，而不是只知道一个最终结果。定一套统一事件协议（阶段/思考/行动/步骤/反馈），前端才有东西可渲染（步骤条、搜索结果、图表、知识图谱），用户也才有「它在干活」的信任感。

10. 断点续跑：状态持久化

深研可能很长、浏览器可能刷新。系统用一个 CheckpointService（checkpoint_service.py）在每个阶段结束保存检查点，把后端状态 + UI 状态都落库到 research_checkpoints 表：

self._save_checkpoint(session_id, state, ui_state)   # graph.py 中每阶段调一次
# 恢复
state = self._load_checkpoint(session_id)            # resume=True 时
if state: yield {"type": "research_resumed", ...}

知识点：Agent 的持久化（Checkpointing）
开放式长任务一定有中断风险（会话过期、刷新、超时）。把结构化的状态做成可恢复的快照，让 Agent 能从中断处继续，而不是推倒重来——这是从「玩具」走向「可用产品」的关键能力。

除了研究流程，CheckpointService 还负责把运行状态标为 completed / failed，异常时也能记录错误原因，方便排障。

11. 对话线：ReAct 智能问答 —— 让 Agent 会「查」

除了深研，系统还有一条独立的对话型 Agent 线：ReActController（react_controller.py:191）+ ToolExecutor（tool_executor.py）。逻辑很典型：

  1. Think：根据用户问题 + 历史上下文，由 LLM 决定下一步该干嘛（用哪个工具）。
  2. Act：调用工具（搜索 / 查库 / 分析 / 画图），拿到 Observation。
  3. Loop：把 Observation 再喂回，重复 Think-Act，直到 LLM 判断 Finish。
  4. 汇总后生成回答。

这里的技术细节是——单轮内可以是多工具接力：比如「智慧交通最新政策有哪些？」→ 先 web_search 找新闻 → 再 text2sql 查行业数据表 → 用 data_analyzer 算近三年增速 → 汇总结论。工具之间通过 ReActContext 累积的 collected data 串联。

知识点：Plan-and-Execute vs ReAct
深研用的是更狠的 Plan-and-Execute（先规划再并行执行），对话问答则用 ReAct（边想边做）。两者适用场景不同：开放式长研究适合先规划，交互式问答适合即时推理。一个成熟系统往往同时混用多种 Agent 模式。

12. 记忆与检索：让 Agent 有「长期记忆」和「知识库」

12.1 Long-Term Memory（memory_service.py）

对话型 Agent 的记忆不只靠上下文窗口硬塞，而是做摘要压缩 + 向量化存库 + 按需召回：

  • should_compress(messages)：消息太多就触发压缩。
  • summarize_conversation(messages)：让 LLM 把冗长对话压成要点。
  • _store_memory_vectors(...)：压缩后的记忆向量化存进 Milvus。
  • retrieve_memories(...)：新一轮对话先用语义检索召回相关历史记忆。
  • build_memory_context(...)：把召回的旧记忆拼进提示词，Agent 才「记得你」。

知识点：Agent 记忆分级
记忆分为：工作记忆（当前 window）、长期记忆（跨 session 存 Postgres + 向量）、程序记忆（技能/工具/策略）。本项目把长期记忆做了摘要压缩 + 向量检索，是比「全量塞上下文」更省 token 且更有关联性的做法。

12.2 RAG 检索（retrieval_service.py）

query_vectors = generate_embedding([question])   # 问题 embedding
results = milvus.search(...)                     # 向量检索（本地知识库）
# 可选：走 rerank 精排，提高命中准确率

完整链路：DocMind（可选）解析文档 → 切片 → embedding → Milvus 存向量 → 相似度召回 → rerank 精排 → 拼入上下文。这让 Agent 既能「搜全网」（web_search）也能「查私有资料」（knowledge_search）。

15. Agent 工程师的几点心得

  1. 先定契约，再谈 Agent。 六个 Agent 能协作，靠的不是聪明，而是 ResearchState 这份结构化契约。先画好 Agent 之间的数据流图，再逐个实现 Agent。
  2. 模型是下限，工程是上限。 真正拉开体验的，是坏 JSON 兜底、代码自愈、中途取消、断点续跑这些脏活。大模型负责「聪明」，工程负责「可靠」。
  3. 按认知成本路由模型。 不是所有 Agent 都用最贵的模型。角色 × 模型 × 温度的多维矩阵，是省钱又保质的关键。
  4. 过程比结果更值得做可观测。 一个长时间无反馈的 Agent，用户早跑了。用统一事件协议 + 流式输出，把「它在思考」变成产品体验。
  5. 永远有终止条件。 任何反思/重试循环都要有 max_iterations 这样的硬限制定量，否则灾难。

1. 先看一眼：这个系统由什么组成

「AI 电商客服 Agent」不是「一个 prompt + 一把梭」，它是一条围绕用户问句的双轨流水线，由两类节点配合：

轨道 说明
确定性前缀链 消解指代 → 判意图 → 按意图强制分流到五条出口（投诉/闲聊/知识/退款/业务）
主力 Agent（ReAct 环） 只在真正需要自由度的路线上启环：查订单、探物流、判退款，捏着工具边想边做
知识子链 商品咨询 → 强制检索（RAG） → 生成前证据闸 → 才进 Agent
退款子链（确定性 + 人机协作） 取单 → 强制检索政策 → 交 Agent 判能否退 → interrupt 让用户选单/确认
工具体系（ch08） 内置 @tool + MCP Server 动态接入，统一执行引擎 + 审计
观测与进化（ch09） Langfuse 自部署 + 数据飞轮：低置信落池 → 人工审核 → 回填知识库
专用分类器（ch10） RoBERTa-wwm-ext 微调 → ONNX，17 类目旁路归类

其中「先分流、再选择模型自由度」的编排思想最精华，作为主线展开；最后补上工具引擎、置信度、记忆、飞轮等支线。

2. 核心一：先把流程「画成一张图」，再谈让模型干活

「Agent」不是把任务扔给一个 LLM 反复催，而是先想清楚哪条路不能走，再决定哪条路让模型自由发挥。这个系统的骨架是一张 LangGraph 图（app/graph/build.py）：

关键的设计在条件边上（build.py）：

知识点：分流优于自由发挥
投诉就该安抚+转人工，闲聊就该零模型固定话术，商品咨询就该强制检索——这类决策用代码定死，不让模型猜。模型只被放行到需要聪明的地方（主 Agent），其余路径全是确定性的。

那「该定死的规则表」长什么样？在 app/graph/routing.py，九类意图 → 五条出口是一份写死的表，单一来源、不漂移：

    "投诉": "escalate",    "闲聊": "fallback_script",  "其他": "fallback_script",

3. 核心二：共享「会话状态」—— 一支团队共用的工作记忆

让分流、检索、游戏环、兜底互相衔接，靠的不是把一段段文本传来传去，而是一份结构化状态。ConversationState（app/graph/state.py）用 TypedDict 描述，所有节点读写同一块状态：

class ConversationState(TypedDict, total=False):
    messages: Annotated[list[AnyMessage], add_messages]  # 跨轮历史,checkpointer 续接
    summary: str              # ch07 滚动摘要
    intent: str               # 九类之一(ch08 增「人工」)
    resolved_query: str       # 指代消解+改写后的完整问句
    evidence: str             # 知识路编号证据文本
    citations: list           # 引用 chunk(前端可点)
    evidence_strong: bool     # 生成前证据闸信号
    evidence_confidence: float  # ch09 四信号加权总分(0-1)
    route: str                # knowledge|business|complaint|chitchat
    steps: int                # ReAct 步数(停止条件)
    suggested_actions: list   # 转人工/建工单/退款表单 等可选项
    trace: Annotated[dict, merge_dict]  # 留痕

3.1 为什么「结构化」比「文本拼接」更优

  • 意图、证据、订单是各自的字段，互不污染。intent 一路决定走哪条边，evidence 一路注入模型、order_data 只服务退款链——各干各的，读代码的人一眼看得懂。
  • trace 用 reducer 累加留痕。注意这个细节（state.py 的 merge_dict）：入口每轮传 trace=None 清零本轮，None 是重置哨兵——因为 merge(旧,{}) 清不掉，得靠 None 触发重置，杜绝上一轮的条件键跨轮残留。

3.2 状态即「可断点续跑」

messages 用 LangGraph 的 add_messages reducer + SQLite checkpointer 跨轮续接。历史不是塞在 model 上下文里，而是存进状态、由 checkpointer 持久化，重启/刷新不丢。这为后面讲记忆工程埋了伏笔。

4. 核心三：RAG 的「强制检索」与生成前证据闸 —— 客服正确性的地基

客服最怕模型编造政策。这里的做法不是「配个 RAG 让它能检索」，而是「商品咨询必须走检索，且检索结果必须先过闸、闸过了才放模型作答」。

知识节点 retrieve_knowledge（app/graph/nodes.py）在进 Agent 之前就把证据备好：

hits = await retrieval.search_knowledge(query, strategy="hybrid_rerank", bm25_text=bm25_text)
conf = compute_evidence_confidence(hits)                     # 四信号置信度
if conf.score < settings.evidence_confidence_threshold:      # 证据弱 → 拒答
    return {**base, "evidence_strong": False,
            "fallback_source": "retrieval_low_conf", ...}    # 落低置信池
# 语义自评:证据够不够
chk = await selfcheck.check_sufficient(query, ev_texts)
if not chk["useful"]:
    return {**base, "evidence_strong": False, "fallback_source": "self_check", ...}

然后用条件边走向 main_agent（闸过）或 fallback_reply（闸拦、转人工）：

b.add_conditional_edges("confidence_check", confidence_gate, {
    "strong": "main_agent", "weak": "fallback_reply"})

知识点：生成前拦，而非生成后救
证据闸放在「检索后、进 Agent 前」，而不是最终答复上。因为编造通常发生在「模型凭记忆自由发挥」那一瞬——早点拦，比事后检测省事得多。

4.1 四信号置信度：不额外花钱的证据质检

compute_evidence_confidence（app/core/confidence.py）的妙处在于——零额外模型调用。信号全部来自检索/精排结果，固定权重线性加权归一到 0-1：

W_TOP1, W_VALID, W_MARGIN, W_KEY = 0.5, 0.2, 0.2, 0.1
# top1_score  Top1 精排分(最强证据多强)
# valid_count 有效证据数(孤证还是成群)
# margin      Top1-Top2 分差(证据聚焦度)
# key_clause_hit 命中关键条款词(shipping/退货/保修…)

阈值（settings.evidence_confidence_threshold）不是拍脑袋，是用评估集 make calibrate-confidence 跑 Youden 最优出来的，并偏保守设 0.30（宁可多转人工，不放编造，实测应拒放行率 0%）。

5. 核心四：ReAct 环 —— 让 Agent 长出「手」，并且知道何时停下

商品咨询之外，主力 Agent 走的是经典 ReAct 循环（app/graph/nodes.py 的 main_agent / agent_tools）：

  1. Think：main_agent 用 bind_tools 把工具喂给模型，让它决定下一步（app/core/llm.py 统一收口模型，streaming=True）。
  2. Act：agent_tools 把 tool_calls 交给统一执行引擎执行，拿到结果回灌成 ToolMessage。
  3. Loop：should_continue 决定继续还是收敛。

图上的环（build.py）：

b.add_conditional_edges("main_agent", should_continue, {
    "continue": "agent_tools", "stop": "log"})
b.add_edge("agent_tools", "main_agent")

5.1 停止条件：为什么我只用「步数」去卡

should_continue（app/graph/routing.py）是我刻意想拿出来讲的地方。我没有用 token 预算卡死循环，理由在代码注释里写得很直白：

token 花销是另一件事——它管的是烧钱和撑爆上下文，不是死循环，阈值要按真实用量分布标定，归第 9 章的成本控制一起讲。混在这里卡，一次估偏就把工具链整条掐断，而且掐在模型已经决定调工具之后，用户只看到半句「我这就去查」。

last = state["messages"][-1]
has_tool_calls = isinstance(last, AIMessage) and bool(last.tool_calls)
if not has_tool_calls: return "stop"                     # 无 tool_calls → 收敛
if state.get("steps", 0) >= settings.max_agent_steps: return "stop"  # 步数封顶
return "continue"

知识点：行为问题 vs 成本问题，用不同的闸
死循环是行为问题，一步=一次模型调用、数得清，用 max_agent_steps 封顶；token 是成本问题，要按真实用量分布标定，归观测报表一起看。把两类问题混在一个闸里，是最常见的翻车点。

6. 核心五：统一工具引擎 —— 校验 / 权限 / 超时重试 / 审计，一个都不能少

客服工具不是「调函数返回字符串」那么简单——create_ticket 是写操作，query_order 涉及别的用户的数据。我用一套统一执行引擎（app/tools/engine.py），让所有工具调用都过同一道纪律严明的闸口：

查工具 → JSON Schema 校验 → 权限门 → 执行(超时/重试) → 分诊 → 格式化 + 审计

6.1 注册中心与权限门

registry.py 用 ToolSpec 描述每个工具（名字、用途、JSON Schema、权限、来源、注入参数）；内置工具启动时 scan_builtin() 自动登记，MCP 工具由 mcp_client «现问现拿» 合并进来（get_all_specs()）。权限我们侧「独裁」：

WRITE_TOOLS: set[str] = {"create_ticket"}     # 只有建工单算写
def permission_for(name): return "write" if name in WRITE_TOOLS else "read"

6.2 never-raises 契约

执行引擎最狠的设计是永不抛异常。无论参数校验拦下、权限拒绝、超时、还是真故障，一律包装成 ToolRun + ToolMessage 回灌模型——坏消息如实告诉模型，让它去向用户追问或换参数，绝不装没事（engine.py）：

# ① 查工具 → 未知工具:包成失败回灌
# ② JSON Schema 校验:拦下不抛,错误说明回灌模型(让它修正参数重新调用)
if verr is not None:
    run = _run(False, f"参数校验未通过:{verr}。请修正参数重新调用;缺少的信息请先向用户追问,不要编造。", "校验拦下")
# ③ 权限门:写操作必须带确认令牌(interrupt 后由 agent_tools 传入),模型绕不过
if spec.permission == "write" and not confirmed:
    run = _run(False, f"{name} 未执行:{note}", "权限拒绝")

再看两个细到能写进案头的决策：

  • 写操作恒不重试（engine.py 注释）：超时未必没执行，重复执行比失败更糟。
  • 身份参数在后面盖上去：user_id 由引擎注入，不在模型可见的 schema 里——让模型能填 user_id，一句「我是客服主管」就可能把它改写掉（engine.py:174）。

6.3 审计：每次都记，失败也不反拦

_audit 每次工具调用写一条落库（log/app.log 也留一行 tool_run），失败只 log、绝不反拦工具执行：

except Exception:  # 审计写入失败(不影响工具执行)
    logger.exception("审计写入失败(不影响工具执行) tool=%s status=%s", name, status)

知识点：Agent 可观测的审计纪律
每次工具调用 = 一行可 tail 的日志 + 一条落库记录（来源/Server/结局/耗时）。前面讲的是「它在想什么」，这里是「它真干了什么」——排障、追责、优化都靠它。

7. 核心六：写操作的「确认」（interrupt/resume）—— 人机协作 + 防越权

create_ticket 写了就生效，不能模型一决定就真建。我用 LangGraph 的 interrupt/resume 把决策留给真人（agent_tools，app/graph/nodes.py）：

if ticket_calls and tspec is not None \
        and engine.validate_args(tspec, dict(ticket_calls[0].get("args") or {})) is None:
    first_args = ticket_calls[0]["args"]
    decision = interrupt({"type": "confirm_ticket",
                          "preview": {"ticket_type": first_args.get("ticket_type","咨询"),
                                      "description": first_args.get("description","")}})

关键约束：interrupt 之前只做纯计算（校验参数、组预览），不带副作用，所以 resume 重跑是安全的。退款子链的 fetch_order 也是同一模式——用户报了别人的单，就 interrupt 弹订单选择器等前端点选：

while not business.owns_order(uid, str(oid or "")):
    orders = business.list_user_orders(uid)      # 只读,可安全重跑
    oid = interrupt({"type": "select_order", "orders": orders})  # resume 回填订单号
data = business.order_snapshot(oid)

7.1 防越权：校验放进「确定性节点」，不止放在工具里

owns_order 这一道校验，我在工具内部和退款子链入口各设一道。为什么？代码注释写得很实在：

退款子流程是确定性节点,不经 agent_tools,工具那道校验够不着。
不然退款入口就成了绕过校验的后门。

还有 submit_refund——模型即便发起退款，也会被 agent_tools 拦成「前端退款表单」，工具内部的归属校验对它不生效，得在拦截前先判一次（nodes.py:365）。

读到这你会发现：项目的安全不是靠一个点，而是「工具层校验 + 确定性链入口校验 + interrupt 人工确认 + 权限门」四层堆出来的。

8. 核心七：上下文管理 —— 滑窗 / 摘要 / 前缀缓存 / 上下文预算

长会话是 Agent 记忆工程的试金石。粗暴裁历史，用户说「最开始那个订单」就听不懂了。app/core/memory.py 把历史建成三层，节点每次只现拼精简版：

  • 层 3：早期轮次进异步摘要（summary），一条浓缩行「钉住」整段过去；
  • 层 1 / 层 2：滑窗内近的留原文、远的压成半形态（保首句）；
  • 前缀缓存：把 system + 工具 schema + 本轮材料 稳定前缀排前，命中上游 cache（省钱）。

组装顺序在 _agent_messages（app/graph/nodes.py）里写死——这里的讲究得展开：

8.1 全列表只能有一条 SystemMessage

上游的 chat template 会把列表里所有 system 消息上提、合并成一个头部块渲染，所以「摘要单独放第二条 system」等于把它拼在了 AGENT_SYSTEM 后面，工具 schema 被挤到可变内容之后 —— 而 prompt caching 按渲染后的前缀精确匹配，于是整段前缀全 miss。实测:无摘要的会话 cache_read=2048,摘要一进 system 就掉到 0。

所以摘要跟证据一起，走用户侧那条消息。这是「前缀缓存」这个性能优化逼出来的一个很反直觉的正确做法。

8.2 上下文预算：启动自检一次，不比运行时撞墙

app/core/budget.py 按「模型窗口 − 固定开销 − 单轮 ReAct 峰值」提前算好预算，main.py 启动时自检：

b = budget.compute()
if b.healthy: logger.info("上下文预算 %s", budget.describe(b))
else: logger.error("上下文预算不足:窗口 %s 装不下 固定开销 %s + 单轮 ReAct 峰值 %s...",
                   b.window, b.fixed, b.peak)

窗口按块分配（system / 检索证据 / 输出 / 滑窗），装不下就报警而不是用户被卡死才发现。还有个中文细节：zh_chars_per_token=1.2——count_tokens 默认按英文 4 chars/token 估，会把中文语料估低，这里单独校准。

9. 核心八：可观测 + 数据飞轮 —— 让 Agent「自己变聪明」

9.1 把「它在想什么」变可观测

每一轮的 intent / route / trace / resolved_query 都被 log_node 打出来并落 MySQL（app/graph/nodes.py）：

logger.info("turn conv=%s intent=%s route=%s resolved=%r trace=%s",
            state.get("conversation_id"), state.get("intent"), state.get("route"),
            state.get("resolved_query"), state.get("trace", {}))

配合 Langfuse 自部署（make langfuse-up，数据不出门），意图进 trace 的 tag，能做「按意图分堆的 token 成本账」、评估趋势可视化。

9.2 数据飞轮：答不上的问题，喂回知识库

最有产品味的设计在这。每次「证据弱拒答 / 用户差评」都落进低置信池（repository.insert_low_confidence），且随行存召回快照（Top3 原文+得分）给审核页看。人工在 /review 页审核、补标准答案后回写知识库（MySQL 双写字段 + Milvus 向量）。闭环是：

模型答不上(低置信/差评) → 落池 + 召回快照 → /review 人工审核补答
   → 回填知识库(双写) → 下次被检索到、答对

工程启示：问题不是终态，是进料。
fallback_reply 里对快照三态的处理尤其克制：走了检索且有召回 = 列表；走了检索但零命中 = []（这是「真缺知识」的强信号）；没走检索 = NULL。把「没走检索」和「走了但没搜到」区分开，是审核页能不能精准补缺的分水岭。

10. 核心九：从「通用 Agent」到「专属小模型」—— 把高频贵活剥出去

当你发现意图/主题识别这种高频、简单、模式固定的活，每次都让大模型跑太贵，自然会想到：用专用模型替换掉 Agent 里最贵的一段。ch10 是一条完整的 MLOps 流水线（scripts/ch10/）：

11. 工程韧性：那些让 Agent 真正能用的「脏活」

聊了一堆华丽的 Agent 能力，最后必须强调——拉开生产级与 Demo 差距的，都是不起眼的工程韧性：

11.1 容错的参数校验（engine.py）

模型给的 tool_calls JSON 常残缺。引擎不靠 response_format 一把梭，而是 jsonschema best_match 给出人类可读错误、回灌模型纠偏，并把中文 ensure_ascii=False 不打乱。校验器本身可能炸也不让它炸穿（MCP 工具的 schema 是外部给的、不可信）：

    run = _run(False, f"工具暂时不可用:参数定义异常({type(e).__name__})...", "失败")

11.2 强制定量：处处封顶，保证终止

max_agent_steps、tool_result_max_tokens、max_output_tokens、max_user_input_tokens、tool_result_max_tokens 处处有上限。工具结果超长也不静默撑爆，而是在行边界截断（_cap_tokens，别把一条记录劈两半）。

11.3 中文环境的坑：UTF-8

仓库里中文 markdown/jsonl 很多，Windows 默认 GBK 会 UnicodeDecodeError。所以 PYTHONUTF8=1 在 Makefile 和 dev.sh 里**、于 Python 启动前**设好——写进 .env 已经太晚。

13. Agent 工程师的几点心得

  1. 先定契约，再谈 Agent。 十几号节点能协作，靠的不是各自聪明，而是 ConversationState 这份结构化契约。先画好节点之间的状态流，再逐点实现。
  2. 该定死的用代码定死。 意图分流、强制检索、话术兜底都走确定性路径，模型只在主 Agent 里有自由度——确定性优先，是客服正确性的来源。
  3. 模型是下限，工程是上限。 真正拉开体验的，是校验回灌、写操作确认、超时重试、审计落库、UTF-8 这些脏活。大模型负责「聪明」，工程负责「可靠」。
  4. 诚实靠「生成前拦」。 证据闸、四信号置信度都放在进 Agent 之前；宁可多转人工，不放编造。
  5. 永远有终止与封顶。 ReAct 靠步数、结果靠 token 截断、反思靠阈值——但记得把成本问题和死循环问题拆开，用不同的闸各管各的。
  6. 答不上的问题是进料，不是终态。 数据飞轮把每次拒答变成一次知识更新，Agent 才谈得上「自我进化」。

2. 核心一：Agent 主循环 —— 一个事件驱动的 ReAct 引擎

整个系统的核心在 personalcode/agent.py 的 Agent 类。它没有把「让大模型干活」藏进一个黑盒函数，而是显式地跑一个 事件驱动的 ReAct 循环：

while True:
    iteration += 1
    if self.max_iterations > 0 and iteration > self.max_iterations:
        yield ErrorEvent(...)          # 强制终止上限
        break
    # 1. 注入环境、长期记忆、工具清单、协调/权限 reminder
    # 2. 流式读取 LLM 输出（StreamCollector）
    # 3. 模型一旦发出 tool_use，立刻提交执行（StreamingExecutor）
    # 4. 把 ToolResult 回填进对话历史 → 下一轮循环

关键点：Agent.run() 是异步生成器，它 yield 的是一系列 AgentEvent。所有对外的「声音」都被建模成了事件类型联合（agent.py:161）：

AgentEvent = (
    StreamText | ThinkingText | RetryEvent
    | ToolUseEvent | ToolResultEvent
    | TurnComplete | LoopComplete | UsageEvent
    | ErrorEvent | PermissionRequest
    | CompactNotification | HookEvent
)

知识点：事件驱动主循环
把「Agent 在干什么」从内部状态变成可被消费的事件流，是 Agent 工程的第一性原理。主循环只管 yield 事件，至于上层是 TUI、-p 非交互、还是 WebSocket 远程——都由调用方按需消费。这保证了同一套 Agent 内核能挂到不同的前端。

__main__.py 里就体现了这种解耦：同一个 Agent.run()，TUI 模式消费它渲染界面，-p 模式用 stream-json 把事件序列化成 NDJSON 喂给脚本。

3. 核心二：工具抽象 —— Agent 长出「手」

一个只会「说话」的 Agent 改不了代码。系统用一套统一的 Tool 抽象（personalcode/tools/base.py）让 Agent 真正拿到外部世界的能力：

class Tool(ABC):
    name: str
    description: str
    params_model: type[BaseModel]      # 用 pydantic 描述参数 schema
    category: ToolCategory             # "read" | "write" | "command"

    def is_concurrency_safe(self, args):  # 按本次调用的实际参数判断能否并发
        return self.is_read_only

    @abstractmethod
    async def execute(self, params: BaseModel) -> ToolResult: ...

内置工具用 create_default_registry()（tools/__init__.py:182）装配：ReadFile、WriteFile、EditFile、Bash、Glob、Grep，再加上 Agent（派子 Agent）、ToolSearch、mcp_call、SendMessage、TaskCreate 等高级工具。

知识点：工具是 Agent 的「外设总线」
把每个能力封装成 name + description + params_model + execute() 四件套，params_model 直接用 pydantic——schema 和校验二合一。新增一个工具 = 新增一个类注册进去，Agent 就会在下一轮自动看到它的 schema 并学会调用。

一个被代码注释反复强调的细节是 is_concurrency_safe 不看类别、看实际参数：ls 和 rm 都是 Bash，前者可以并发、后者必须独占（tools/base.py:56）。这是后面并发分批的决策依据。

4. 核心三：流式工具执行 + 并发分批

Agent 一轮可能同时发出好几个工具调用。这里有个很微妙的工程问题：要不要等整个 LLM 响应流结束再执行工具？ 如果等，用户会看到「思考思考……（十几秒）……刷地一下全干完」；如果不等、收到就跑，又会破坏模型给出的执行顺序（比如 WriteFile 之后紧跟一条依赖它的 Bash）。

PersonalCode 的解法是 StreamingExecutor（agent.py:280）：在 LLM 流式输出期间就收集工具调用，等流结束后再按「并发安全的批」统一执行。

def partition_tool_calls(tool_calls, registry) -> list[ToolBatch]:
    # 相邻的并发安全调用归到同一批并发跑，其余各自独占一个串行批
    for tc in tool_calls:
        safe = tool.is_concurrency_safe(tc.arguments)
        if safe and batches and batches[-1].concurrent:
            batches[-1].calls.append(tc)      # 并入当前并发批
        else:
            batches.append(ToolBatch(concurrent=safe, calls=[tc]))

只读批用 asyncio.gather 并发执行，写/命令批严格串行，批内有序、批间有序，所以拼回来的结果顺序就是模型给出的顺序。

知识点：工具调度的并发安全
工具调度不是「全并发」也不是「全串行」，而是按数据依赖分批：只读不互扰的并发，会改状态的串行。既保住吞吐，又保住语义，这是生产级 Agent 的标配取舍。

5. 核心四：人在回路（HITL）—— 六层权限决策管线

PersonalCode 最鲜明的工程特质是把控制权交还给人。默认权限模式下，写文件和跑命令前都会先征求你的同意。这套逻辑在 personalcode/permissions/checker.py 的 PermissionChecker.check() 里，是一条 6 层决策管线：

def check(self, tool, arguments) -> Decision:
    # Layer 0: Plan 模式例外放行（只允许 Agent/ToolSearch/AskUserQuestion/ExitPlanMode）
    # Layer 1: 安全的只读命令自动放行
    # Layer 1b: 危险命令黑名单（危险命令拦截，直接 deny）
    # Layer 1c: OS 沙箱开启时命令自动放行（内核兜底）
    # Layer 2: 路径沙箱（只读/写文件，受保护路径一律拒绝）
    # Layer 3: 规则引擎匹配（allow/ask/deny）
    # Layer 4: 权限模式兜底判定（default / acceptEdits / plan / bypassPermissions）
    # Layer 5: 触发人工确认（HITL）→ 弹 PermissionRequest

配合 permissions/modes.py 的四模式矩阵：

模式 读 写 命令
default 自动 ask ask
acceptEdits 自动 自动 ask
plan 自动 ask ask
bypassPermissions 自动 自动 自动

这里有两个非常「Agent 味」的设计：

① 拒绝也带反馈。 用户拒绝时还能附一句话（PermissionReply.feedback），这句反馈会被拼进拒绝结果交给模型，让它按你的要求换个做法——而不是简单地说「不行」（agent.py:144、conversation_pairing.py 的 rejected_tool_result）。

② 允许则落地为规则。 选了 ALLOW_ALWAYS 时，系统把这次操作写进本地规则文件（agent.py:1023），规则引擎每次评估现读现匹配——这一轮之后即刻生效，从此这条命令免确认。

知识点：Agent 的工具护栏（Guardrails）
让 Agent 拥有写文件、跑命令的能力，就必须有分层护栏：危险命令黑名单、路径沙箱、规则引擎、权限模式、最终人工确认，一层层收敛。真正面向用户的产品，Agent 的「权力」永远是受约束的、可解释的、可被否决的。

6. 核心五：上下文管理 —— auto-compact 与工具结果溢写

长会话最大的敌人是上下文窗口。PersonalCode 做了两层防御（context/）：

Layer 1：工具结果溢写落盘。 单条工具输出超过 MAX_OUTPUT_CHARS = 50000 字符时，完整内容写盘，对话历史里只保留预览和文件路径（tools/base.py:23、agent.py:1387 的 _maybe_persist_or_truncate）。模型要全文就自己再 ReadFile——既保住上下文，又不丢信息。

Layer 2：auto-compact 自动压缩。 接近 context window 上限时，用一次 LLM 调用把对话压成摘要（agent.py:645、context 的 auto_compact）。压缩不是裸丢历史，而是保存一个 RecoveryState——把最近读过的文件和调过的 skill 快照下来，压缩后能重建工作上下文：

def _snapshot_for_recovery(self, tc, result):   # agent.py:1063
    if tc.tool_name != "ReadFile": return       # 只快照 ReadFile
    self.recovery_state.record_file_read(path, content)

知识点：Agent 的上下文管理策略
上下文不是「满了就完蛋」，而是可以分层治理：超大的工具结果溢写落盘、过长的历史摘要压缩、关键工作上下文做恢复快照。这三点合起来，才能让一个 Agent 在一轮几百次工具调用的长任务里不「失忆」。

7. 核心六：文件级长期记忆 —— 用户级 / 项目级双层

PersonalCode 的记忆不是塞在数据库向量里，而是用普通 Markdown 文件组织（personalcode/memory/auto_memory.py）。每条记忆一个 .md，带 frontmatter：

---
name: my-kebab-case-name
description: 一句话描述
type: user | feedback | project | reference   # 类型决定存到哪个目录
---
正文内容…
  • 用户级（~/.personalcode/memory/）：user / feedback 类型，跨项目跟随你。
  • 项目级（<project>/.personalcode/memory/）：project / reference 类型，可提交进 git 团队共享。

两个目录各自维护一份 MEMORY.md 索引（ENTRYPOINT_NAME），且带截断保护（auto_memory.py:156）：超过 200 行或 25KB 就截断并加 WARNING——索引太长会占掉大量上下文。

自动提取也做了 去重：MemoryManager.extract()（auto_memory.py:410）每次提取前先扫描已有记忆生成 manifest 喂给 LLM，「能更新已有文件就别新建重复的」。提取由主循环定期触发（agent.py:747 每轮检查），并且有合并策略防止并发重复提取。

知识点：Agent 记忆分级
记忆分三类：工作记忆（当前上下文窗口）、长期记忆（跨 session 的文件）、程序记忆（技能/工具/策略）。文件级记忆的妙处是人可读、可 diff、可 git 提交——记忆不是玄学，而是仓库里普通的管理文件。

8. 核心七：多智能体 Teams —— Lead–Worker 协调模式

这是本项目「最有 Agent 味」的能力。PersonalCode 支持把一次编码任务组织成一支团队：Lead 负责调度、拆解、汇总，Worker 负责并行研究 / 实现 / 验证。整套编排逻辑写在 teams/coordinator.py 的 get_coordinator_system_prompt() 里——它本身就是给 Lead 的 system prompt，把「怎么当好一个调度者」讲得非常细：

  • Worker 看不到你的对话，所以每条子任务 prompt 必须自包含（含文件路径、行号、要改成什么）。
  • 绝不让实现 Worker 验证自己的工作，必须另派一个只读的 Verification Worker 用「fresh eyes」查 bug。
  • 按上下文重叠决定 continue vs spawn：研究已覆盖目标文件就 SendMessage 续写，探索过宽就新派一个干净的。

还专门处理了长会话漂移问题（coordinator.py:211）：那份 8KB 的调度指引首轮全文注入，之后每 5 轮才复述一次全文，中间轮只发精简版 COORDINATOR_SPARSE_REMINDER，避免重复内容把省下来的上下文又填回去。

def get_coordinator_reminder(iteration, agent_catalog=None):
    if iteration <= 1 or (iteration - 1) % REMINDER_INTERVAL == 0:
        return get_coordinator_system_prompt(agent_catalog=agent_catalog)  # 全文
    return COORDINATOR_SPARSE_REMINDER                                     # 精简版

Worker 之间的通信走邮箱 + 共享任务板：Lead 派活写入邮箱，Worker 主循环用 _consume_mailbox（agent.py:893）在每轮迭代开始时消费；队员通过 TaskCreate/TaskGet/TaskUpdate 读写团队共享的 tasks.json。多 Agent 后端支持 in-process / tmux / iTerm2 三种 spawn 方式（teams/models.py 的 BackendType）。

知识点：协调者模式（Coordinator）
处理复杂长任务时，「一个超大 Agent」不如「一个调度者 + 多个专职 Worker」：调度者上下文里只放任务分解、Worker 状态、汇总，具体脏活分给专用 Worker。代价是交接契约要极其清晰（自包含 prompt、结构化通知、按名寻址），这正是 Lead prompt 花大篇幅写「怎么写好 Worker prompt」的原因。

9. 核心八：子 Agent 与 Verification —— Reflexion 式对抗质检

除了平级的 Teams，PersonalCode 还有父子子 Agent：主 Agent 可以通过 Agent 工具派子 Agent。子 Agent 定义也是 Markdown 文件（agents/loader.py），按 项目级 → 用户级 → 内置 三层加载，支持热重载。

内置了 Verification 这种只读质检型 Agent（agents/builtins/verification.md），由 enable_verification_agent 配置控制是否启用（agents/loader.py:83）。它「cannot edit files, focuses on finding bugs」——专门用 fresh eyes 挑毛病，这正接近 Reflexion（反思） 范式：不让干活的 Agent 自己验收自己，而是让一个独立的、只读的审查者去攻击结果。

配合 /review 命令，能把当前代码变更丢给模型做对抗式代码审查。子 Agent 的调用关系被完整记录下来（见第 11 节的 trace 树），可通过 /trace 查看父子追踪。

知识点：独立验证者（Verification）
实现者对自己代码天然有「锚定偏见」，会 rubber-stamp。把验证拆成独立的、只读的、专门找茬的 Agent，用 fresh eyes 去看同一份代码，是提升 Agent 产出质量最高性价比的手段之一。

10. 核心九：技能 Skill（程序记忆）与 MCP 工具扩展

Agent 的「程序记忆」——怎么做一件特定的事——被建模成了 Skill 技能包（skills/）：一个带 YAML frontmatter 的 SKILL.md，项目级（.personalcode/skills）、用户级、内置三层加载，用 /skill 命令管理。内置了 frontend-design、skill-creator 示例。

而外部工具的扩展走 MCP（Model Context Protocol）：可插拔的服务器可以是 stdio 子进程，也可以是 Streamable HTTP（mcp/）。MCP 服务器动辄几十个工具、schema 又长，所以 PersonalCode 引入 ToolSearch 延迟加载（tools/__init__.py 的 ToolRegistry、mcp/loading_strategy.py）：

  • 默认不把全部 MCP 工具塞进初始 tools[]（会占掉一大块上下文）。
  • 模型需要用哪个工具，先调 ToolSearch 把对应 schema「捞」出来，再通过 mcp_call 真正调用。
  • 何时暴露检索/分发工具、以何种加载模式（eager / native / dispatch）适配不同端点，由 loading_strategy.py 按上下文窗口与 schema 总量决策。

知识点：工具的按需加载（Lazy Loading）
工具 schema 本身也占 token。与其把几百个工具的 schema 全塞进上下文，不如按需检索、按需加载——这是长上下文 + 大规模工具集并存时的关键优化。

11. 可观测性：生命周期 Hooks 与父子 Trace 树

一个健壮的 Agent 系统必须把「它在想什么、在做什么」变成可观测的事件流。PersonalCode 从两个维度做可观测：

① Hooks 事件协议（hooks/events.py）。 定义了五层生命周期事件：

class LifecycleEvent(StrEnum):
    SESSION_START / SESSION_END      # 会话级
    TURN_START / TURN_END            # 轮次级
    PRE_TOOL_USE / POST_TOOL_USE     # 工具级
    PRE_SEND / POST_RECEIVE          # 消息级
    STARTUP / SHUTDOWN / ERROR / COMPACT / PERMISSION_REQUEST / FILE_CHANGE / COMMAND_EXECUTE  # 系统级

主循环在这些节点 yield HookEvent，HookEngine 可接自定义执行器，钩子的输出还会被注入回对话上下文——实现了「钩子既是观察点，又是干预点」。

② Trace 树（agents/trace.py）。 每个 Agent 实例都有 agent_id，子 Agent 记录 parent_id，归属同一 trace_id，形成一棵父子调用树：

class TraceNode:
    agent_id: str
    parent_id: str | None
    trace_id: str
    input_tokens: int; output_tokens: int
    tool_call_count: int; status: str

TraceManager.get_tree(trace_id) 能聚合整棵树的 token 消耗——/trace 命令把它渲染出来，让你看清「这一轮任务是谁派给谁、谁烧了多少 token」。

知识点：Agent 的可观测性
主循环事件流 = 实时「它在干嘛」；trace 树 = 事后「它是怎么派生的、烧了多少」。两者配合，一个多智能体系统才不是黑盒——这是排障、计费、调优的地基。

12. 工程韧性：那些让 Agent 真正能用的「脏活」

华丽的能力之外，拉开生产级与 Demo 差距的，都是不起眼的工程韧性：

  • 强制迭代上限。主循环 max_iterations > 0 and iteration > max_iterations（agent.py:584）保证系统一定在有限步内终止，不会烧光预算。
  • max_tokens 自愈。stop_reason == "max_tokens" 时先升级输出上限（MAX_TOKENS_CEILING），再触发「断点续写」重试，最多恢复 MAX_OUTPUT_TOKENS_RECOVERIES 次（agent.py:713）。
  • 崩溃恢复。crashlog.py 把异常落盘，__main__.py 兜住框架之外的部分；会话以 jsonl 存到 .personalcode/sessions/，/rewind + 文件历史可回溯到任意检查点。
  • 工具错误不炸循环。单个工具失败被收成一条带 tool_id 的 ToolResult(is_error=True)（agent.py:301 的 _error_result）喂回模型，让它自己换个做法，而不是中断整轮。
  • Worktree 隔离。多 Agent 并行改代码时用 git worktree 隔离（worktree/），互不踩踏。

14. Agent 工程师的几点心得

  1. 事件驱动，而非黑盒函数。 把 Agent 的每一步（思考、用工具、要授权、压缩上下文）都 yield 成事件，内核就能挂 TUI、CLI、WebSocket 任意前端，可观测性和复用性一起拿到。
  2. 先定工具的契约，再谈智能。 一套 Tool 抽象（schema + 校验 + 并发安全 + 分类）是整个系统地基。工具的 is_concurrency_safe 看参数不看类别，这是并发调度正确性的关键。
  3. Agent 的「权力」必须受约束。 写文件、跑命令的能力配上六层权限管线 + 拒绝带反馈 + 允许落规则，才能既强大又可被人类否决。
  4. 上下文是稀缺资源，要分层治理。 大结果溢写落盘、长历史摘要压缩、工作上下文做恢复快照、MCP 工具按需加载——每一处都在给上下文窗口「精打细算」。
  5. 复杂任务交给协调者 + 专职 Worker。 调度者只放任务分解和汇总，脏活分给只读验证等专用 Worker；用独立的 Verification Agent 对抗式质检，别让实现者自己验收。
  6. 记忆和可观测性一起建。 文件级记忆让 Agent「记得你」且人可审计；trace 树 + 事件流让它「可解释、可排障、可计费」。
  7. 永远有终止条件。 任何重试 / 反思 / 迭代循环都要有硬性上限，否则一次失控就烧光预算。

拆解 OpenAI Codex 的 Harness 架构：模型有了”眼睛和手”的秘密

本文内容整理自《小林面试笔记 · Codex Harness 架构》系列，系统梳理一次 Agent 任务的完整执行链路：从用户输入，到会话编排、上下文组装、工具执行，再到状态持久化与长期记忆。

大模型原本只会根据输入生成输出，既看不见文件，也没有手去运行命令。可一旦接进 Codex，模型却像突然长出了眼睛和手，还能连续工作十几步，命令失败后甚至会读报错、换一种方法接着做。为什么？答案藏在模型外面的 Codex Harness 里。

Codex 源码已在 GitHub 开源（https://github.com/openai/codex），本文沿着一次任务的执行过程，把 Harness 的架构一层层拆开讲清楚。

一、为什么只有模型不够？

先做一个最简单的假设：Codex 里面只有一个大模型。

用户说「帮我修改项目」，模型读到这句话，最多生成一段回答。哪怕回答里写出了正确代码，也只会停留在文本中——文件没有改变，命令没有运行，任务更不会因为一次回答失败就自动发起下一次请求。

那还缺什么？

  1. 要有人把项目规则、代码片段和之前的执行结果交给模型。
  2. 要有人接住模型提出的动作，真的去读文件、改文件、运行命令。
  3. 要有人记住任务进行到哪里，判断什么时候继续、什么时候停下来。

承担这些工作的，就是 Harness。

所以理解 Codex 的第一步，不是先背模块名称，而是先分清三个角色：

角色 职责
模型 决定下一步做什么
Harness 组织上下文、安排工具执行、收集结果，再交给模型继续判断
执行环境 实际存放项目文件、运行命令的地方

模型没有直接碰文件：模型提出动作 → Harness 把动作交给工具 → 工具在执行环境里完成操作 → 结果交回 Harness → Harness 重新组织输入 → 再次请求模型。模型给出下一步，Harness 把很多个”下一步”接成一项完整的工作。

Harness 要回答的五类问题

把一次任务放慢来看，Harness 至少要回答五类问题，这也就构成了它的五大部分：

  1. 接入与交互：用户从哪个界面发来输入，运行过程怎样返回界面？
  2. 会话与编排：一项任务要请求模型多少次，下一步是否继续？
  3. 上下文管理：这次到底给模型哪些规则、历史和工具结果？
  4. 工具与执行系统：模型提出一个动作，谁来执行，权限够不够？
  5. 状态持久化和记忆：任务关闭后怎样恢复，过去的经验怎样在以后被找到？

于是就能把 Codex Harness 画成一张完整地图：

  • 最上面是客户端和 AppServer；
  • 中间是会话状态、Agent 循环与模型客户端；
  • 一侧负责上下文和记忆，另一侧负责工具、路由与执行；
  • 底部保存会话历史、元数据和记忆产物。

Harness 会向模型服务发送请求，拿回模型的回答或工具调用。用哪个模型、开放哪些工具、命令怎样运行，由配置决定；真正执行工具时，还要按照权限策略处理审批和沙箱限制。

二、为什么需要 AppServer？

Codex 不只有一种界面。终端、IDE、桌面应用都可能提交任务，也都需要接收文字增量、工具进度、文件变更和审批请求。

如果每个界面都自己实现一套 Agent 循环，同样的任务，在终端和桌面应用里就可能按不同流程执行；以后修一个问题，也得分别修改多套实现。

AppServer 解决的正是接入问题：把界面发来的需求转交给 Agent 引擎，再把模型输出、工具进度和审批请求传回界面。它既可以作为独立服务供客户端连接，也可以在同一个进程里使用。

关键点在于——交流是双向的。因为 Agent 并不是普通接口那种”请求进去、结果出来”。执行遇到审批时，服务还会反过来向客户端提问，等待用户允许或拒绝，然后再继续原来的工作。所以 AppServer 负责的是一段持续交互，而不是一次简单的问答。

一项任务怎么流动？

一句话「帮我修改一下这个项目」第一次穿过总图：

  1. 输入先经过 AppServer 进入会话（Session）；
  2. 会话引擎准备这一轮工作；
  3. 上下文系统把规则、环境和已有历史组织起来；
  4. 再由模型客户端请求模型；
  5. 模型可能先提出搜索代码，工具系统接到调用后在执行环境中完成搜索，把结果写回历史。

真正的主线是一个闭环：准备上下文 → 请求模型 → 执行动作 → 得到反馈 → 再准备下一次上下文。地底部的历史会持续记录过程，后台记忆在满足条件时处理过去的历史，为未来任务提供材料，且不阻塞眼前这项任务。

三、Agent 循环怎么运转？

为什么要多次请求模型？

还是那句最简单的需求：「帮我修改一下这个项目。」

  • 第一次请求模型时，模型连项目里有哪些文件都不知道，合理的动作可能只是先读规则，或搜索相关代码。只有工具真的返回结果后，模型才获得了新的事实。
  • 第二次请求就和第一次不一样了：第一次决定从哪里开始，第二次根据刚读到的内容判断该改什么。
  • 修改完成后，验证命令又可能带回成功或失败的新信息，第三、第四次请求继续建立在这些反馈上。

这就是 Agent 循环存在的原因：很多信息无法靠模型猜出来，只能先行动，再根据环境反馈。

最小理解是：Agent 不是模型连续思考的神秘过程，而是”模型判断”与”环境反馈”不断交替。 模型每次只基于当前输入给出输出，Harness 负责把前后几次请求接起来。

模型输出怎么变成动作？

模型返回的不是一大段完整答案，而是流式事件：

  • 文字增量到达时，Harness 可以交给界面展示；
  • 一个工具调用完整生成后，才进入工具分发；
  • 响应完成事件到达时，Harness 更新本次请求的状态和用量，由外层循环判断后面是否还有工作。

连接和传输方式由模型客户端内部处理，对主循环来说，收到的始终是统一的文字增量、工具调用和完成事件。

关键：工具执行完成后，结果要带回原来的调用标识。假如模型一次提出两个动作（读配置、跑命令），Harness 必须知道每段返回属于哪次调用，模型才能判断刚才哪一步成功、哪一步失败。

任务状态由谁保存？

一次响应结束，用户的任务远没有结束。正在等待的工具、用户刚补充的一句话、已经完成的动作，放在哪里？答案是会话状态，而不是模型自己记住。

先记住几个层级概念：

概念 含义
Thread（线程） 装着一整段多轮会话（如”先修 Bug，再补测试”）
Turn（轮次） 这次任务产生的多个 Item（一个 Turn 可请求模型很多次，不等于一次模型 API 调用）
Session（会话） 在程序内部保存这段会话的历史、待处理输入，以及运行时需要的共享服务

为什么需要 StepContext？

想象一个场景：模型请求发出去时，工具目录里还有工具 A，模型按眼前能力生成了对 A 的调用。可在结果返回前，配置刚好刷新，新目录里已经没有 A。如果 Harness 按新目录解释这次调用，模型明明用了刚才展示的工具，却会收到「工具不存在」。

所以 Codex 会为每次模型请求捕获一份 StepContext，固定这一步使用的模型设置、环境视图、MCP 绑定、工具路由和项目规则。工具调用返回后，Harness 仍沿用同一份请求上下文分发——模型按哪份工具列表发起调用，Harness 就按同一份列表处理。

注意边界：StepContext 固定的只是请求采用的配置、工具列表和项目规则。文件仍可能被用户或其他任务修改，外部服务也可能变化——StepContext 不会把整个文件系统和外部世界一起冻结。

等待、取消与失败

  • 等待：工具需要审批时，Harness 记下哪个操作正在等用户确认，把审批请求发到界面；用户答复后，交给对应操作继续处理。模型向用户提问同理。
  • 用户追加输入：Codex 运行时你补一句「修改范围只限当前模块」，这句话通常先进入输入队列，主循环在合适边界取走，让后续请求看到。
  • 取消：Harness 触发取消信号并收尾，但已写入的文件不会自动恢复；仍在运行的进程或子 Agent 有各自生命周期。
  • 失败：重新请求模型、重新执行工具、从历史恢复会话，是三件事。尤其当一个命令已产生副作用时，模型连接重试不代表命令可以安全重跑。

循环什么时候结束？

模型没有继续调用工具，任务也不一定立刻结束。主循环还要确认：有没有用户刚补充的要求、有没有未处理的错误、停止前的检查是否允许结束。如果用户追加了要求，或停止前的钩子（StopHook）补入了需继续处理的内容，Agent 就可能再执行一轮。

Codex 停下来，也不代表要求一定完成了。修 Bug 时文件改完只能说明代码变了，还要看测试和验证结果，才能判断问题是否解决。

四、上下文怎么组织？——ContextManager

模型实际看到了什么？

发请求前，Harness 要把这些内容组织进输入：

  • 基础指令：规定 Codex 整体行为；
  • 用户需求与项目规则：说明当前任务和仓库约束；
  • 环境信息：如工作目录等；
  • 历史记录：前几次请求和工具结果，标记任务进度；
  • 工具定义：告诉模型这一步能提出哪些动作。

为什么工具定义也要放进去？因为模型不会凭空知道工具名和参数格式，只有 Harness 告知本次可见能力，模型才能生成一条结构正确的调用。

一句话：上下文决定模型”知道什么”，工具定义决定模型此刻”能要求 Harness 做什么”。

项目规则怎么注入？

Codex 会围绕项目边界和当前工作目录查找规则文件，按层级组织，并受读取预算限制。根目录规则适用于整个项目，越接近当前目录的规则越具体。模型需要同时知道全局要求和局部约束。

但仓库里不会所有说明都被自动塞进模型——发现范围、候选文件、工作目录和读取预算都会影响最终内容。

这里有一条边界要停一下：写进上下文的规则，可以要求模型怎样做，却不能直接扩大执行权限。 项目文件里即使写了「允许访问某个目录」，实际工具能否访问，仍由 Harness 的权限策略和执行环境决定。文字指令解决”行为选择”，沙箱解决”资源边界”，两者属于架构中不同的位置。

上下文基线（Context Baseline）

如果每调用一次模型就把相同规则再追加一遍，上下文很快充满重复内容。Codex 会记下已介绍过的规则和环境信息（上下文基线）：第一次请求提供必要环境说明，以后环境变化再补充变化部分。之前的对话和工具结果仍随请求发给模型，只是不重复追加相同的环境说明。

让前面内容保持稳定还有一个实际好处：连续请求拥有相同前缀时，模型服务才有机会复用前缀缓存。

限长与历史规范化

工具输出可能一次返回几万行。Codex 会在记录工具输出等环节应用限长策略，控制进入模型历史的内容规模。被省略的细节怎么办？模型需要发起更精确的动作——读取指定文件范围、按关键词搜索，或用范围更小的命令重新取得证据。

这里没有免费的午餐：限长换来可控上下文，也可能丢掉暂时看不出价值的细节。Harness 负责控制体积，模型通过后续工具调用补回真正需要的信息。

除了文本长短，还有个结构问题更麻烦——调用与结果配对。模型提出调用、工具返回结果，这两个条目通过调用标识配成一对。发送历史前要做规范化：缺失结果的调用补出中止状态，孤立结果按协议处理，不支持的输入类型按模型能力调整。

理解了这点就能解释很多现象：Codex 有时重新读一段文件，不一定是模型完全忘了，也可能是旧输出被限长，或压缩后需要重新取得精确证据。

上下文满了怎么办？

历史持续增长，最终会接近模型上下文窗口。Codex 会跟踪使用量，在轮次开始前或运行中触发压缩，具体方式受模型服务和配置影响。

其中总结式压缩可以理解成写一份”交接说明”：目标是啥、哪些改完了、确认了哪些事实、试过哪些失败的方法、接下来还要做什么。下一次请求靠这些信息接着做，就不必再带每一步的完整输出。

压缩最容易被高估的地方，是被想成无损存档——事实并非如此。摘要保住主线，也可能丢掉某段完整日志和局部细节。必须分清三个范围：

范围 作用
当前模型窗口 本次请求能看到什么
Harness 维护的会话历史 为原会话恢复服务
长期记忆 跨任务复用的知识

上下文压缩服务于眼前任务的继续运行，不会自动把全部细节变成跨任务知识。

五、工具调用怎么执行？

模型能看到哪些工具？

模型要使用工具，必须看到名称、用途和参数结构。每次请求前，Codex 都要安排工具计划：哪些直接展示、哪些等需要时再查找、模型调用后交给谁处理。

这里要区分三件事：

  1. 系统里存在什么工具；
  2. 这次请求向模型展示什么；
  3. Harness 最终能调用哪个执行器。

三者相关，却不是简单的完整列表。这就解释了为什么同一个 Codex 在不同项目、模型或权限配置下，可用工具可能不同——不是模型临时忘了一个工具，而是本次 StepContext 固定的工具计划可能不同。

工具怎么路由到执行？

模型生成一条完整调用后，Harness 在本次工具计划中找到对应处理器（ToolRouter）。工具不存在或参数不合法，就返回错误，不能把模型生成的任意内容直接拿去执行。 找到处理器后，Harness 把调用参数、会话信息和 StepContext 一起交给处理器。结果走向两个地方：事件通道把进展展示给客户端，ContextManager 把结果记入历史供下次请求使用。

审批和沙箱做什么？

对于执行类工具，Harness 先走一段公共流程：根据当前策略判断是否需要审批，再选择合适的沙箱方式运行。

  • 审批回答：”这个动作要不要额外获得许可？”
  • 沙箱限制：”进程能够接触哪些资源？”

两者不能混为一谈：用户批准某个动作，不代表进程自动获得无限资源；沙箱里的执行失败，也不代表系统会直接提升权限重跑。只有策略允许时，执行链路才可能请求许可或调整执行方式。

长进程与 UnifiedExec

编译、测试或开发服务可能持续很久。要是一次工具调用必须等到进程退出，Agent 就无法在运行中观察新输出，也很难与交互式进程继续通信。

UnifiedExec 把「一次工具请求」和「一个进程的完整生命周期」分开处理：负责启动、跟踪进程、收集输出，并处理继续等待、写入输入和取消等操作。第一次调用先返回当前输出和进程标识，底层进程继续运行；后续调用用标识读取新输出或发送输入，直到取得退出状态。

工具调用返回了一段日志，只能说明 Harness 当前拿到了这些内容，不能直接推断进程已经结束。

工具如何并发和执行环境？

模型一次可能提出多个动作，Harness 判断能否并行。可以想象成一道门：允许并行的工具拿共享通行证一起进去；需单独运行的工具拿专用通行证，其他调用在门外等它完成。这道门控制的是工具分发顺序，不是给整个文件系统上锁。

确定工具后还要确定它在哪运行：

  • 启动进程、读写文件 → ExecServer，在本地或远程环境中执行；
  • MCP 工具 → 请求各自连接的外部服务；
  • 内部控制工具 → 直接在运行 Harness 的 Codex 进程里处理。

别被两个相近的名字绕进去：AppServer 连接客户端和 Agent 运行核心，负责传递用户请求与执行事件；ExecServer 连接工具和执行环境，负责进程与文件操作。两者做的是不同的事。

工具系统不是一个巨大的 Shell：不同类型的工具走不同的处理程序、权限策略和执行环境，最后把结果送回同一个 Agent 循环。

六、长期记忆怎么形成？

三种记忆的区别

先想三个时间点：

时间点 依赖 作用
当前任务进行中 上下文 下次模型请求知道刚才读了什么、改了哪里
重新打开原会话 持久化历史/状态重建 继续之前的工作
全新会话 长期记忆 把跨任务有价值的项目经验带进新任务

如果把三者都叫”记忆”，很容易得出错误结论：以为压缩历史是在写长期记忆，以为会话保存后新会话会自动读到全部旧聊天。

更准确的理解是：

  • 上下文 —— 服务下一次模型请求；
  • 持久化历史 —— 服务原会话恢复；
  • 长期记忆 —— 尝试把跨任务仍有价值的信息带进新任务。

会话怎么恢复？

任务运行时，当前本地实现以 JSONL 保存事件历史，状态数据库可用时用 SQLite 保存便于查询的元数据。重新打开原会话，Harness 先还原已发生的用户消息、模型回复和工具结果，再恢复上下文基线与窗口用量等。

但恢复有明确边界：某些等待中的审批、交互对象或运行中的进程，只存在于当时进程内；历史保存了什么，恢复才能重建什么；已发生的文件修改，不会靠重放聊天自动撤销或重执行。

历史怎么提炼？——后台记忆任务

长期记忆不能只是”保存更多”，还得先回答：过去哪些内容值得留下？

后台记忆任务的启动时机：带输入的新轮次成功启动、运行环境准备好后，尝试调度后台记忆任务。启动前要确认：长期记忆已开启、非临时会话或子 Agent 会话、状态数据库可用、账号调用量高于阈值。任一条件不满足就跳过。

后台流程先筛选候选（按会话来源、时间、空闲状态、记忆配置和数量限制），再通过任务租约抢占处理资格（可理解成一把有时间限制的锁，时间到自动释放，材料可被后续任务接手）。选中后，模型提炼结构化的原始记忆和任务摘要，目标是留下可复用偏好、有效步骤、失败教训等。如果这次任务没有值得长期保留的内容，允许没有产出。

为什么还要整理？

单任务记忆只是材料，还不是容易使用的知识。不同任务可能重复记录同一条命令，也可能保留已变化的项目约定。所以第二阶段做跨任务整理：

  1. 取得全局租约（给整个整理加锁）；
  2. 选择第一阶段材料，同步到记忆工作区，比较内容是否变化；
  3. 确实需要更新时，启动整理 Agent，整理成几类文件：
    • 导航摘要：告诉模型有哪些经验可查；
    • 详细记忆：说明具体内容；
    • 任务摘要：帮模型追溯当时做了什么；
    • 可复用步骤：记录以后遇到同类任务可以怎么做。

还应避免整理过程再次触发自身。

新任务怎么读取记忆？

读取分两步：先给导航，再按需展开。把全部记忆塞进去只会让上下文难以控制。

  1. 记忆读取功能启用且存在非空摘要时，把有限长度的记忆导航和说明注入开发者指令；
  2. 模型先看到”过去大概有哪些经验”，判断是否相关；
  3. 需要细节时，通过专用工具搜索详细记忆，必要时继续读任务摘要和可复用步骤。

当前本地搜索主要按文字匹配，只返回命中位置附近一小段内容。但如果两段话意思相近、用词不同，就可能搜不到。

过去的经验仍然是线索，不是标准答案。 项目代码和环境可能已变化，模型必须回到当前文件和工具结果上验证，不能把长期记忆当成永远正确的事实库。系统会根据记忆引用等信号记录使用情况（结合时间窗口和数量上限），但使用次数只能说明被引用过，并不构成自动事实校验机制。

七、扩展能力怎么接入？

扩展怎么接入主循环？

如果每增加一项能力都去改主循环大量代码，Harness 很快难以维护。Codex 内部提供扩展注册机制：每个扩展先登记自己会增加什么、要在哪些时机运行——有的往模型输入补充说明，有的增加工具，有的在会话启动、轮次结束等时机执行处理。

Harness 先登记这些扩展，等准备模型输入、组装工具列表或运行到对应时机时，再调用相应扩展。

注意：这里讲的是源码内部架构接口。内部扩展机制解释了核心运行时怎样组织扩展点，不代表所有面向用户的插件、MCP 服务和 Skills 都遵循同一个公开接口。

Skills、MCP 和 Hooks 做什么？

机制 作用
Skills 告诉模型某类任务应该怎么做，并提供说明和资源
MCP 把外部服务的工具接进来，让模型可请求 Harness 调用
Hooks 让程序在指定时机介入（收到用户输入时、工具执行前后、任务准备停止时）

一个提供做事方法，一个接入工具，一个在特定时机执行处理。

子 Agent 怎么运行？

子 Agent 沿用同一套运行架构，也需要会话、上下文、模型循环和工具执行。多 Agent 机制复用这些核心组件，再增加父子关系、消息传递和并发控制。

父 Agent 可以把部分调查任务交给子 Agent，子任务按配置继承相应上下文，独立运行后把结果传回。独立会话意味着运行状态分开，却不等于文件环境一定隔离——如果父子 Agent 指向同一工作目录，仍可能看到或修改相同文件；真正需要隔离时，还要配合独立工作目录或相应环境策略。

核心不变：无论加上 Skill、MCP 还是子 Agent，本质仍是准备输入 → 请求模型 → 执行动作 → 接收反馈 → 决定下一步。

八、总结：一句话回答”Codex 的架构是怎样的？”

Codex 的核心是在大模型外面加了一套 Harness：模型负责判断下一步，Harness 负责把判断变成真实行动。

整体上，Codex 可以分为五个部分：

  1. 客户端接入（AppServer）
  2. 会话编排（Session / Thread / Turn）
  3. 上下文管理（ContextManager）
  4. 工具执行（ToolRouter + 审批/沙箱 + ExecServer）
  5. 状态与记忆（持久化历史 + 长期记忆）

执行流程是一条闭环：请求模型 → 回结果 → 中途需要审批或用户补充信息时先等待 → 收到答复后再继续。

其中：

  • ContextManager 把规则、历史和工具结果整理给模型；
  • ToolRouter 找到对应的工具处理器；
  • 执行流程 按照权限策略处理审批、沙箱和实际操作；
  • Session 保存任务状态、压缩上下文、恢复会话；
  • 长期记忆 负责跨任务复用经验。

整套架构的主线就是一句话：模型决定下一步，Harness 让这一步安全执行，再把结果交给模型继续判断。

知识点：主循环（Agent Loop）
一个 Agent 的本质是一个循环：感知当前状态 → 决定下一步行动 → 执行并观察结果 → 更新状态 → 再决定。SalesPilot 把它具象成 Plan/Act/Reflect/Generate 四个显式模块，用函数把认知步骤显式建模，好处是每一步都可单独测试、单独替换。很多成熟的 Agent（ReAct、Plan-and-Execute、Reflexion）都是这种「显式步骤」思路的变体。

3. 核心二：规划模块 —— 让 Agent 自己决定「用哪个工具、查什么」

agent_plan()（agent.py）是 Agent 的「大脑前置决策器」。它用一个 system prompt 教模型做两件事：

  1. 工具路由：根据查询内容判断该用「本地文档搜索」还是「网络搜索」；
  2. 查询扩展：把用户的一条原始问题，拆解 / 延伸成 1-2+ 个更细的子查询，覆盖信息死角。
def agent_plan(query):
    prompt = '''
    # 汽车销售助手Agent的Plan模块
    你是一个专业的汽车销售助手的规划模块。你的任务是：
    1. 分析用户的查询:{0}
    2. 基于已有的信息，决定使用哪个工具来查询以获得更多需要的信息（本地文档搜索或网络搜索）
    3. 将用户的原始查询拆解或延伸为1-2个相关问题
    ...
    ## 工具选择规则
    - 当查询明确涉及星辰电动ES9的具体信息、参数、功能或服务时，优先使用**本地文档搜索**
    - 当查询涉及以下情况时，使用**网络搜索**：
      · 与其他品牌车型的详细对比
      · 最新市场动态或新闻
      · 非官方的用户体验或评测
      · 需要实时数据（如当前市场价格波动等）
    ## 输出格式
    [{"action_name": "本地文档搜索", "prompts": ["原始查询", "延伸问题1", ...]}]
    '''
    result = middle_json_model(prompt)     # 强制 JSON 输出
    json_list = extract_json_content(result)
    structure_output = json.loads(json_list)
    return structure_output

为什么这很关键？ 规划模块相当于 Agent 的「手电筒」——它决定了后续 RAG / Web 搜索的查询质量。如果直接拿用户那句口语化问题去搜，ES 的 BM25 可能召回很差；而这里把「星辰电动ES9和特斯拉Model Y相比怎么样？」扩展成「ES9 的技术规格和配置」「Model Y 最新规格和价格」等检索友好的子查询，召回率立刻不同。

3.1 结构化输出的三层防御

规划模块的输出是 JSON，而大模型吐 JSON 常常是残缺的。这里做了三层防御（agent.py）：

result      = middle_json_model(prompt)          # ① 请求时声明 response_format="json_object"
json_list   = extract_json_content(result)       # ② 正则提取首个"["到末尾"]"之间的内容
structure_output = json.loads(json_list)         # ③ 正规 JSON 解析

其中 extract_json_content 用 r'(\[[\s\S]*\])' 把「模型多嘴输出的包裹文字」剥掉，只留 JSON 数组。而 middle_json_model 强制 response_format={"type": "json_object"}，用「请求端约束 + 响应端兜底」双保险压低解析失败率。

知识点：结构化输出的韧性（Robustness）
生产级 Agent 不能赌 LLM 每次都输出完美 JSON。标准套路是：请求约束（json_object / JSON Schema）+ 响应解析器（剥代码块 / 取最外层括号）+ 失败兜底（返回 None / 用 thought 补抽）。这一层防不住，Agent 就没法稳定地驱动工具。

3.2 一个值得品的小设计：adjust_format

规划模块返回的结构是「一个 action 配多个 prompts」，但执行时希望「每个 action 只干一件事」。于是 adjust_format 把它拍平成 [{action_name, prompt}] 的一对一列表：

def adjust_format(original_data):
    adjusted_data = []
    for item in original_data:
        for prompt in item['prompts']:
            adjusted_data.append({'action_name': item['action_name'], 'prompt': prompt})
    return adjusted_data

工程启示：数据契约的适配层。LLM 倾向于输出「分组」结构，而执行器更适合「扁平」结构，中间加一层无副作用的纯函数做转换，让上下游各用自己舒服的格式。这是 Agent 工程里被低估但极高频的模式。

4. 核心三：执行模块 —— 让 Agent 长出「手」，把工具结果收进记忆

process_actions()（agent.py）是执行器。它遍历规划好的每个动作，根据 action_name 派发到两个工具之一，并把结果结构化地收进 memory：

def process_actions(actions):
    memory = []
    for action in actions:
        action_name = action['action_name']; prompt = action['prompt']
        try:
            if action_name == '本地文档搜索':
                result = rag(prompt)                 # → RAG：ES 混合检索
            elif action_name == '网络搜索':
                result = web_search_answer(prompt)   # → Serper：Google 实时搜索
            else:
                result = f"未知的动作类型: {action_name}"
            memory.append({"提问": prompt, "结果": result})   # 工具结果进记忆
        except Exception as e:
            print(f"--------{action_name}检索失败: {e}-----------")   # 失败不中断
            continue
    deduplicated_memory = deduplicate_memory_global(memory)  # 全局去重
    return deduplicated_memory

这里的几个工程点很实在：

  • 单一入口的 try/except：单个工具失败只影响自身，不会让整条 Agent 链路崩掉，而是跳过继续。
  • 结果是「有结构」的：memory 里每条是 {"提问": prompt, "结果": result}，这形成了「这个查询 → 查到什么」的可追溯记忆，喂给反思和生成。
  • 执行与决策解耦：规划只产出「意图 + 查询词」，执行只负责「调工具、拿结果」，两层可以各自替换。

4.1 工具一：RAG —— Elasticsearch 混合检索

rag() 薄薄一层，真正干活的是 service/core/retrieval.py 里的 Dealer：

知识点：混合检索（Hybrid Search）
只用向量（语义）或只用关键词（BM25）都不够——vector_similarity_weight=0.6 表示最终得分是向量相似度与词项相似度的加权和。这样既懂「充电快不快」的语义，也保得住「最大功率 150kW」这种精确匹配。这是 RAG 召回质量的关键调参旋钮。

4.2 工具二：Web 搜索 —— Serper 接 Google

web_search_answer() 调 service/web_search/web_search.py，通过 http.client 打 Serper，把 organic 结果抽成 {title, url, content} 的 snippets：

def serper_search(q="apple inc", hl="zh-cn", num=20):
    return make_request(q, hl, "/search", num)

def process_search_results(search_results):
    snippets, questions = [], []
    for result in search_results['organic']:
        snippets.append({"title": result['title'],
                         "url": result['link'],
                         "content": result['snippet']})
    for q in search_results['peopleAlsoAsk']:
        questions.append(q['question'])

知识点：Agent 的「双知识源」。RAG 管私有且静态的资料（自家车的参数/FAQ），Web 搜索管公有且动态的信息（竞品对比、最新价格、用户评测）。Agent 的价值之一就是把这两种互补的知识源，按查询场景自动分发给正确的工具——这是大模型「时效与私域」两个短板的同时解法。

5. 核心四：全局去重 —— 别把重复内容喂给模型

多轮、多查询检索后，memory 里很容易出现内容重复（同一个 ES chunk 被不同的扩展查询命中多次）。deduplicate_memory_global() 会基于 content_with_weight 字段做全局去重：

def deduplicate_memory_global(memory):
    seen_content = set()
    for memory_item in memory:
        for item in memory_item['结果']:
            content = item['content_with_weight'].strip()
            content_hash = hash(content)          # 用 hash 避免长字符串比较开销
            if content_hash not in seen_content:
                seen_content.add(content_hash)    # 首见 → 保留
            else:
                print(f"发现重复内容，已过滤: {content[:50]}")

知识点：上下文预算管理（Context Budget）
大模型的上下文窗口有限，而检索是「廉价的、大量的」。把重复 / 低价值内容在进上下文前清掉，等于给生成模型留出了更宝贵的「有效信息预算」，也直接降 token 成本。这是所有检索增强型 Agent 的必修课。

6. 核心五：反思模块 —— 让 Agent 自查「信息够不够」（Reflexion 味道）

一轮执行拿到 memory_global 后，Agent 并没有急着生成，而是先进入 reflection()——拿着「已有的信息」再问一次 LLM：还缺不缺、要不要再补查。这就是学术上 Reflexion（反思） 范式的工程化落地：

def reflection(user_query, memory_global):
    prompt = '''
    你是一个专业的汽车销售助手的规划模块。你的任务是：
    1. 分析用户的查询:{0}
    2. 基于已有的信息，是否还需要延伸再进行查询
    ## 目前已有的信息: {1}
    ## 重要！至多再扩展不超过3个查询，如果需要扩展则按格式输出，如果不需要则返回 None
    [{"action_name": "工具名称", "prompts":'一个扩展问题'}]
    '''.format(user_query, memory_global)
    result = middle_json_model(prompt)     # 强制 JSON
    return json.loads(extract_json_content(result))

三个关键点：

  • 把「评估信号」显式回写：memory_global 是上一轮行动的产出，反思模块读取它来决策，形成「行动 → 观察 → 反思 → 再行动」的闭环，而不是无脑重跑。
  • 有界迭代：prompt 里明确「至多再扩展不超过 3 个查询」，给循环一个硬性上限，防止 Agent 陷入无限补查。
  • 失败了不阻塞：即使反思输出的 JSON 解析失败，structure_output = None，主流程仍能继续走到生成——容错优先，绝不让反思环节卡死整个链路。

知识点：反思型循环（Reflexion）
关键词是把上一次行动的结果当作下一次决策的输入，并显式设定迭代上界。比起「一条路走到黑」的普通 ReAct，反思让 Agent 在信息不足时主动补齐；而 max_iterations 一类的定量，则是保证系统一定终止、不烧光预算的刹车。

6.1 一个真实的「工程观察」

在 final_answer 的反思分支里，有一处典型的『半成品』代码——它把反思的返回值 action_reflect 仅用于 if 判断，但内部补跑时用的仍是最初的那批 actions：

action_reflect = reflection(user_query, memory_global)
if action_reflect:
    memory_new = process_actions(actions)   # ← 跑的还是原始 actions，而非反思扩展出的新查询
    memory_global.extend(memory_new)

也就是说：「反思 → 扩展新查询」的意图已经在 prompt 里设计好了，但执行侧还没把反思输出的新查询真正接进去。这恰恰是很多 Agent Demo 会踩的中间态——规划/反思的 prompt 已经很丰满，落地执行却还差一步。

工程启示：读源码时，别只盯着「宣称的能力」，要看「实际的执行路径」。 对一个做 Agent 的人而言，能一眼识别这种「prompt 已设计、执行未接上」的断层，是很好的排障直觉。

7. 核心六：生成模块 —— 带思考的销售话术，SSE 流式输出

收集够信息后，final_answer 构造最终 prompt——一句很有「销售味」的系统设定：

final_prompt = f'''
你是一个星辰电动ES9的智能销售助手，负责根据用户的问题和提供的参考内容生成回答。
基于提供的参考内容进行回答，如果原文没有参考内容,根据你自己的知识进行回答。
你需要用有打动力的销售的语言进行输出，突出星辰电动的优势。
参考内容：{memory_global}
用户问题：{user_query}
'''

然后换用 deepseek-r1（一个带显式「思考链」的强模型）流式生成，并且把「思考过程」和「正式回答」分开推送：

completion = client.chat.completions.create(model="deepseek-r1", stream=True, ...)
for chunk in completion:
    delta = chunk.choices[0].delta
    if delta.content:                       # 正式回答
        yield sse("assistant", delta.content, thinking=False)
    else:
        yield sse("assistant", delta.reasoning_content, thinking=True)  # 思考过程

这里有个很妙的区分：delta.content 是给用户看的话术，delta.reasoning_content 是模型的内心推理。前端拿到 thinking: true/false 就能把「推理过程」和「正式回答」渲染成两种不同的气泡——这是让 Agent 看起来「真的在思考」的产品级细节。

知识点：异构模型路由（Model Routing）
规划/反思阶段用 qwen-plus（便宜、快，只需结构化 JSON 输出），生成阶段用 deepseek-r1（贵、强，长文本 + 会思考）。用「角色 × 模型」的矩阵做调度，是规模化 Agent 的成本结构核心：把便宜模型的活交给便宜模型，把聪明模型的活留给聪明模型。

8. 另一条线：Direct Answer —— RAG + Web 的「直答」管线

除了 Agent 线，项目还有一条更轻的 POST /ai_search/（router/ai_serarch_rt.py），它走的是经典 RAG 直答流程：

用户问题 → 知识库检索(retrieve_content)
        → Web 搜索摘要(store_and_query_snippets)
        → 拼 DirectAnswerPrompt（含历史上下文）
        → deepseek-r1 流式回答
        → 推荐问题 + 图片/视频搜索 + 落库

关键差异：

  • 无规划、无反思：直接「查一遍就答」，比 Agent 线快但浅。
  • 返回更丰富：除了正文，还流式回传 documents、web_search、recommended_questions、image_results、video_results，前端能渲染出「引用文档」「推荐问题」「相关图片视频」一整屏。
# get_chat_completion 里，按阶段 yield 不同事件
yield sse({"documents": retrieved_content})        # 知识库引用
yield sse({"web_search": snippets})                # 网页摘要
yield sse({"recommended_questions": related})      # 推荐问题
yield sse({"image_results": ...})                  # 图片
yield sse({"video_results": ...})                  # 视频
yield "event: end\ndata: [DONE]"                   # 结束

知识点：SSE 事件协议（Event Protocol）
一个健壮的大模型产品必须把「不同类型的内容」做成结构化事件流，而不是只吐一段纯文本。前端才能据此渲染引用卡片、推荐列表、富媒体。event: message / event: end 这套约定，让后端组装与前端渲染解耦。

9. 单智能体 vs 多智能体：为什么这个场景「一个 Agent 就够了」

如果你看过我上一篇文章（六专家协奏的多智能体系统），一定会问：SalesPilot 为什么不搞多智能体？

答案在任务复杂度：

维度 六专家系统 SalesPilot
任务形态 开放式长研究（规划/检索/分析/写作/审校） 单轮销售问答（查资料 → 说话术）
认知子任务 多个正交子任务，需分角色 一个线性闭环：查→反思→答
Agent 数 6 个角色分治 1 个（Plan/Act/Reflect 是同一 Agent 的四个步骤）
状态共享 多 Agent 共享大 ResearchState 单 Agent 内部 memory 传递
协作成本 高（交接契约、阶段路由） 低（无跨 Agent 通信）

判断标准很朴素：如果任务能被「一个 Agent 的多个顺序步骤」覆盖，就不值得引入多 Agent 的编排与通信成本。 多智能体不是银弹，它解决的是「并发 + 分治」问题；而单智能体擅长「顺序 + 聚焦」。SalesPilot 把 Plan/Act/Reflect 做进同一个函数里，已经足够支撑销售话术生成，反而更轻、更好调试。

知识点：单智能体 vs 多智能体

  • 单智能体：一个模型 + 一个工具集，靠循环自我驱动。优点：简单、便宜、易调试；缺点：无法并行、上下文单一。
  • 多智能体：多个角色各持一个模型/工具，共享状态协作。优点：可并行、认知负载分摊；缺点：编排与通信成本高。
    选型的核心是任务本身是不是「可拆分的多角色任务」。 起步永远先做单智能体，当任务确实需要「分工 + 并行」再拆多智能体。

10. 工程韧性：那些让 Agent 真正能用的「脏活」

聊了这么多「聪明的部分」，最后必须强调——真正拉开生产级与 Demo 差距的，都是不起眼的工程韧性：

10.1 坏 JSON 的层层兜底

  • 请求端：response_format="json_object" 强制。
  • 解析端：extract_json_content 用正则 r'(\[[\s\S]*\])' 剥掉模型多嘴的文字。
  • 失败端：try/except: structure_output = None，解析失败就让规划/反思返回 None，主流程继续。

10.2 单工具失败不拖垮全局

process_actions 里每个 action 独立 try/except，检索失败只打印堆栈、continue 跳下一个，绝不中断整条链路。

10.3 有界迭代

反思模块 prompt 明写「至多扩展 3 个查询」，加上 JSON 解析失败返回 None，从两个维度保证 Agent 一定有限步终止。

10.4 领域绑定的知识库

规划 / 反思的 prompt 里都枚举了「星辰电动ES9」的 18 个章节（产品概述 / 技术规格 / 驱动系统 / 电池与充电 / 智能座舱 / 智能驾驶 / 安全系统 / 竞品对比 / 用户评价……），把领域先验直接写进 prompt，让 Agent 的工具路由和查询扩展始终「围着车转」，而不是泛泛而谈。

12. Agent 工程师的几点心得

  1. 先用「主循环」把认知步骤显式建模。 Plan→Act→Reflect→Generate 四步拆开，每一步都可单独测、单独换，比一个糊在一起的「提示词调用」好维护一个数量级。
  2. 查询质量决定召回质量。 用户口语问题直接去检索往往很差；规划阶段让 LLM 拆子查询，是 RAG 型 Agent 最容易被忽略的提效点。
  3. 结构化输出要有三层防御。 请求约束 + 响应解析 + 失败兜底，缺一层，Agent 就没法稳定驱动工具。
  4. 按认知成本路由模型。 规划用便宜的 qwen、生成用会思考的 deepseek-r1，角色 × 模型矩阵是省钱又保质的关键。
  5. 永远有迭代上界。 反思 / 重试循环都要有「至多 N 次」的硬限制，否则灾难。
  6. 别迷信多智能体。 任务是「顺序 + 聚焦」就用单智能体，是「并发 + 分治」才拆多智能体。一个能自我驱动的 Agent，通常比一群不会接活的 Agent 强。
  7. 读源码要看执行路径，而非宣称能力。 SalesPilot 的反思 prompt 已设计得很丰满，但执行侧还没真正用上反思产出的新查询——能识别这种「断层」，是 Agent 排障的关键直觉。

1. 先看一眼：这个系统由什么组成

「金融研报 RAG」是一整套基于 RAG（Retrieval-Augmented Generation） 技术的智能文档问答平台。它不只有「检索 + 生成」一段简单链路，而是有两条独立的 RAG 流水线协作：

知识点：表格结构化
对强结构的表格数据，直接存「平文本」会丧失语义（「营收」「同比」各自离散）。转成 HTML 表格后，向量化和关键词检索都能把整行作为检索单元，召回质量明显更高。

3. 核心二：切片策略 —— 不要一刀切

解析出 (文本, 图片/标签) 后，下一步是切片。这里用的是 RAGFlow 的 naive_merge 策略（同理 naive_merge_docx、tokenize_chunks）：

  • 默认切片 token 数：chunk_token_num = 128
  • 切分符：delimiter = "\n!?。；！？"（中英文句号、问号、分号、换行）
  • 逻辑：先按分隔符把长文切碎成「句」，再贪心合并进不超过 128 token 的 chunk，并保留相邻关系。
chunks = naive_merge(sections, int(parser_config.get("chunk_token_num", 128)),
                     parser_config.get("delimiter", "\n!?。；！？"))
res.extend(tokenize_chunks(chunks, doc, is_english, pdf_parser))

tokenize_chunks 对每个 chunk 产出多份表示（rag/nlp/__init__.py）：content_ltks（轻量分词）、content_sm_ltks（细粒度/去除停用词）、content_with_weight（原文本 + 权重标记）——后面检索时它们各司其职。

知识点：为什么是 128 token，不是越长越好
chunk 太短召回不全、太长噪声多且稀释向量语义。研究类文档通常选 128~256 token 的「中分块」，并配合下一节的稠密/稀疏双表示来召回。工程里这个值是可调的超参，parser_config 处处可覆盖，调优时应结合真实问题的命中率来做 A/B，而不是拍脑袋。

5. 核心四：混合检索 —— 关键词 + 向量 + 相似度

这是本项目 RAG 工程味道最浓的一块。检索走 service/core/retrieval.py → Dealer.retrieval（rag/nlp/search_v2.py）。入口把 vector_similarity_weight 设为 0.6：

def retrieve_content(indexNames, question):
    results = dealer.retrieval(question=question, embd_mdl=None,
                               tenant_ids=indexNames, kb_ids=None,
                               vector_similarity_weight=0.6,   # ← 核心超参
                               page=1, page_size=5)

而 Dealer.retrieval（search_v2.py:336）内部有两级排序：

  1. 先重排候选：把 top 结果取到 RERANK_PAGE_LIMIT * page_size（≥128 条）
  2. 再按混合相似度排序挑前 N：rerank_by_model（有重排模型）或 rerank（无模型）

5.1 混合相似度公式

核心计算在 query.py:200：

def hybrid_similarity(self, avec, bvecs, atks, btkss, tkweight=0.3, vtweight=0.7):
    tksim   = self.token_similarity(atks, btkss)      # 关键词(BM25风格)相似度
    vtsim   = cosine_similarity(avec, bvecs)           # 向量余弦相似度
    return tkweight * tksim + vtweight * vtsim

两路权重默认 30% 关键词 + 70% 向量，与 vector_similarity_weight=0.6 呼应（在 rerank 中 vtweight = vector_similarity_weight）。

知识点：为什么向量检索需要混合（Hybrid Search）
只走向量检索，精确数字、专有名词（如「世运电路」「CAGR」）容易被语义漂移；只走关键词检索，同义改写、长问句则召回不到。混合检索让两路互相补位，用加权融合分数统一排序。vector_similarity_weight 是最值得调的旋钮：研报问答里术语精确度高，可保持较高的关键词权重。

5.2 阈值裁剪，保证「回答有据可依」

retrieval 最后按 similarity 阈值和 page_size 裁剪：

for i in idx:
    if sim[i] < similarity_threshold:  # 相似度低于阈值的直接丢弃
        break
    if len(ranks["chunks"]) >= page_size: break
    ...

doc_aggs：按文档聚合，返回每个文档的命中片段数

知识点：召回阈值 = 幻觉防护第一道闸
检索不是召回越多越好。低于阈值的低相关片段拼进 prompt，反而会诱导模型「编」。设定 similarity_threshold 让弱召回直接不进入上下文，是 RAG 工程用「数据」而非「prompt 恐吓」来控幻觉的做法。

6. 核心五：重排序 —— 让检索结果更「贴题」

初级召回用的是快速的（近似）向量 + 关键词并查，精度一般。前 N 条里往往混着不太相关的片段。这里再用一个重排模型精排（search_v2.py 的 rerank_by_model）：

vtsim, _ = rerank_similarity(query, [rmSpace(" ".join(tks)) for tks in ins_tw])
return tkweight * (np.array(tksim) + rank_fea) + vtweight * vtsim

rerank_similarity（model.py:45）基于 llama-index 的 DashScopeRerank：

def rerank_similarity(query, texts):
    nodes = [NodeWithScore(node=Node(text=text), score=1.0) for text in texts]
    dashscope_rerank = DashScopeRerank(top_n=len(texts), api_key=api_key)
    results = dashscope_rerank.postprocess_nodes(nodes, query_str=query)
    scores = np.array([res.score for res in results])
    return scores, None

知识点：召回(Recall) vs 精排(Rerank)
「召回要广、精排要准」。第一阶段用便宜的向量/关键词并查把候选从海量文档中捞出上百条，第二阶段用更强的交叉编码器（Cross-Encoder）逐条对「问题×片段」打分，只留最相关的前 N 条进 prompt。这比「直接取 top-k 向量」质量高一个量级，尤其在金融术语场景里。检索是两级架构，不是一次完成。

检索到的片段最终要拼进 prompt，并强制模型逐句标注出处编号。这是 service/core/chat.py 的 get_chat_completion 最核心的工程设定。

8. 核心七：SSE 流式输出 —— 三种事件类型

生成用 DashScope 的流式接口 stream=True，模型 deepseek-r1，通过 SSE（Server-Sent Events） 实时推给前端。整个响应拆成三类事件，顺序清晰：

① 先发「文档」事件 —— 一次性把检索到的引用先给前端

message = {"documents": all_documents}
json_message = json.dumps(message, ensure_ascii=False)
yield f"event: message\ndata: {json_message}\n\n"

② 再流式发「正文 + 思考」事件

for chunk in completion:
    delta = chunk.choices[0].delta
    if delta.content:
        model_answer += delta.content
        yield f"event: message\ndata: {json.dumps({'role':'assistant','content':delta.content, 'thinking':False})}\n\n"
    else:
        think += delta.reasoning_content   # 思考过程单独累加，未推到前端

这里有个细节：reasoning_content（思考链）被累进 think 变量却不实时推送，把「思考」和「答案」解耦——用户看到的是顺滑的答案流。

③ 完成时发「推荐问题 + [DONE]」

if chunk.choices[0].finish_reason == "stop":
    recommended_questions = generate_recommended_questions(question, retrieved_content, session_id)
    message = {"recommended_questions": recommended_questions}
    yield f"event: message\ndata: {json.dumps(message)}\n\n"

    yield "event: end\ndata: [DONE]\n\n"   # 结束标记
    write_chat_to_db(session_id, question, model_answer, all_documents, recommended_questions, think)

知识点：SSE 事件协议让流式对话变得可控
不用 WebSocket 而是 SSE，前端 fetch + ReadableStream 逐行解析即可，兼容性好。把「引用文档」「生成中」「已完成」拆成不同事件，前端才能在恰当节点渲染引用卡片、思考态、推荐问题。事件即协议，是前后端协作的关键契约。

这个系统很聪明的一点是：不把所有文档都塞进知识库。针对「单次会话小文档」走快速解析链，service/quick_parse_service.py：

知识点：RAG 流水线的弹性设计
不是所有问题都值得走完整向量检索链。对小文档、单会话场景，省去「切片/向量化/建索引」直接用原文生成，延迟和成本都更低。把最重的计算留给真正需要的场景，是 RAG 架构里常被忽略的成本优化。两条链共用下游生成与引用协议，是「可插拔流水线」的体现。

10. 核心九：推荐问题 —— 生成时的「事后抠图」

回答结束后，系统再让模型基于「当前问题 + 已引用文档名」生成 3 个推荐问题，形成追问闭环（chat.py 的 generate_recommended_questions）：

知识点：追问引导把单次问答做成对话
金融研报问答往往是「一问不够，要深挖」。回答后自动补 3 个相关问题，既提升留存，又暗示系统「已理解你关心的维度」。推荐问题用 JSON 强制格式返回，是「结构化输出」在轻量生成任务里的应用。

13. RAG 工程师的几点心得

  1. 入口决定上限，解析决定了 RAG 的「视力」。 金融研报的表格、版面、图表不处理好，向量和关键词都建立在噪声上。先在一套好的 DeepDoc 解析上花力气，再谈检索优化。

  2. 检索永远是多级架构。 是「向量/关键词并查召回 + 交叉编码器重排精排」，不是「一次 top-k」。vector_similarity_weight、similarity_threshold、page_size 是你最该调的三个旋钮。

  3. 引用溯源不是加分项，是可信问答的命门。 一行 prompt 约定 ##编号$$ + 前端可点回原文 = 面向专业用户的产品力。没有溯源，RAG 和「随便聊」没有本质区别。

  4. Prompt 决定「能用」，检索 + 数据决定「好用」。 引用溯源、流式、批量 embedding、fail-soft（检索失败不崩、直接无库回答）这些工程韧性，比换模型更能拉开体验差距。

  5. 弹性设计双通道。 不是所有问题都值得完整检索链。小文档走轻量 Redis 链，省延迟省成本，下游协议统一。让流水线可插拔，是 RAG 架构的进阶题。

  6. 可控性 > 性能。 用占位符 ??、动态字段 q_1024_vec、固定 batch=10，处处「显式优于魔法」，好排查、好调参、好扩展。

1. 先看一眼：这个系统由什么组成

「KamaChat」是一套前后端分离的仿微信即时通讯系统，代码总量约 1.5 万行。后端用 Go，前端用 Vue 3。它不是只有一个「发消息」功能，而是覆盖 IM 的完整业务面：

能力线 说明
登录/注册 账号密码登录 + 阿里云短信验证码登录 / 注册
单聊 & 群聊 消息统一发到后端聊天服务器，由服务器精确转发给接收方
离线消息 离线时消息落库，登录时从库/缓存回补历史记录
多种消息 文本、文件、音视频通话信令（AudioOrVideo）
联系人体系 添加、删除、拉黑、申请/同意/拒绝
群聊管理 建群、退群、解散、踢人、进群方式（直接/审核）
后台管理 管理员的禁用/启用/删除用户、设置管理员、管控群聊

其中后端三位一体的消息链路——WebSocket 长连接 → 进程内总线/Kafka → MySQL 持久化 + Redis 缓存——最为精华，是本文主线。

2. 核心一：分层架构 —— 「薄控制器 + 重 Service」

后端采用很典型的 Go 分层，目录即职责（项目根 api/、internal/、pkg/ 三大块）：

api/v1/                     # 控制器层：只做绑定与响应的「薄层」
internal/https_server/      # Gin 引擎初始化 + 全部路由注册
internal/service/gorm/      # 业务 Service 层（核心逻辑都在这里）
internal/service/chat/      # WebSocket 聊天核心（Channel/Kafka 双模式）
internal/service/redis/     # Redis 封装
internal/service/kafka/     # Kafka 封装
internal/service/sms/       # 阿里云短信
internal/dao/               # 全局 GORM 实例 + 自动迁移
internal/model/             # GORM 数据模型
internal/dto/               # 请求/响应结构体
pkg/                        # 常量、枚举、SSL、日志、工具

控制器层的「薄」，体现在它几乎不写业务。以 api/v1/message_controller.go 为例，一个接口就是「绑参数 → 调 Service → 统一返回」三步：

func GetMessageList(c *gin.Context) {
	var req request.GetMessageListRequest
	if err := c.BindJSON(&req); err != nil {
		c.JSON(http.StatusOK, gin.H{"code": 500, "message": constants.SYSTEM_ERROR})
		return
	}
	message, rsp, ret := gorm.MessageService.GetMessageList(req.UserOneId, req.UserTwoId)
	JsonBack(c, message, ret, rsp)
}

知识点：统一响应协议 / 错误码约定
所有 controller 都走同一个 JsonBack(c, message, ret, data)（api/v1/controller.go）。关键在 ret 的三位语义：0 = 成功（code 200）、-2 = 业务失败（如”用户不存在”，code 400，面向用户提示）、-1 = 系统错误（如 DB 挂了，code 500，只记日志不返回给用户）。把「业务问题」和「系统问题」用返回码严格区分，前端拿到 message 既能直接展示给用户，后端也能据此区分该不该抛告警。这在 docs/业务逻辑.md 里有明确约定。

3.2 启动流程（cmd/kama_chat_server/main.go）

启动时通过 signal.Notify 监听 SIGINT/SIGTERM 实现优雅退出：关闭 Kafka、关聊天服务、最后 myredis.DeleteAllRedisKeys() 清理缓存。

知识点：模式抽象 / 配置驱动
同一套业务代码，靠一个 messageMode 字段切换消息分发后端，而不需要在流程里写两套。这种做法把「技术选型」从代码里抽出到配置层，不仅降低了耦合，也让「单机学习版 → 分布式生产版」的演进变成了改一行配置——这是 IM 系统很值得借鉴的抽象思路。

4. 核心三：WebSocket 双 Channel 读写模型与背压保护

WebSocket 是本系统的「神经末梢」。每个连接对应一个 Client（internal/service/chat/client.go）：

type Client struct {
	Conn     *websocket.Conn
	Uuid     string
	SendTo   chan []byte        // 给 server 端（上行）
	SendBack chan *MessageBack  // 给前端（下行）
}

type MessageBack struct {
	Message []byte   // 序列化后的消息
	Uuid    string   // 消息 uuid，写成功后回写状态用
}

每个连接开两个 goroutine：Read() 读上行、Write() 写下行，通过带缓冲的 channel 解耦，避免直接读写阻塞对方。

Read()（上行分流） —— 读完消息后按消息模式走不同路径：

if messageMode == "channel" {
	// 背压：若转发总线没满，先把积压的 SendTo 冲刷上去
	for len(ChatServer.Transmit) < constants.CHANNEL_SIZE && len(c.SendTo) > 0 {
		sendToMessage := <-c.SendTo
		ChatServer.SendMessageToTransmit(sendToMessage)
	}
	if len(ChatServer.Transmit) < constants.CHANNEL_SIZE {
		ChatServer.SendMessageToTransmit(jsonMessage)   // 总线有空位 → 直接上总线
	} else if len(c.SendTo) < constants.CHANNEL_SIZE {
		c.SendTo <- jsonMessage                          // 总线满了 → 进本地缓冲队列
	} else {
		// 缓冲区也满了 → 主动降级：告诉客户端稍后重试
		c.Conn.WriteMessage(websocket.TextMessage, []byte("消息发送失败，请稍后重试"))
	}
} else {
	// kafka 模式：生产者 → 写入 ChatTopic
	kafka.KafkaService.ChatWriter.WriteMessages(ctx, kafka.Message{Key: ..., Value: jsonMessage})
}

Write()（下行 + 状态机推进） —— 把消息写回前端，并在成功后把消息 status 从 Unsent 更新为 Sent：

for messageBack := range c.SendBack {
	err := c.Conn.WriteMessage(websocket.TextMessage, messageBack.Message)
	if err != nil { return }   // 失败直接断开连接
	// 在线消息的「已发送」状态在这里推进
	dao.GormDB.Model(&model.Message{}).Where("uuid = ?", messageBack.Uuid).Update("status", message_status_enum.Sent)
}

知识点：背压（Backpressure）与阻塞语义
Go Channel 的 len() / 容量在这里被当成水位计用：总线满 → 进本地缓冲，缓冲满 → 主动拒绝而非阻塞死等。因为 WebSocket 是长连接，一旦某条链路堵死，很容易拖垮整个连接甚至服务器。这里用「分级缓冲 + 主动降级」而不是简单阻塞，是 IM 并发下保证单连接可用的关键。

另外注意 CheckOrigin 直接返回 true、配合全局 CORS 放开，这里是为了便于前端从任意源连接——生产环境应换成白名单校验，属于可点评的安全改进点。

5. 核心四：进程内消息总线 —— 用原生 Channel 写 IM 服务器

这是本项目单机模式最有辨识度的设计：Server（internal/service/chat/server.go）没有引入任何消息中间件，而是用原生 Go Channel 手写了一个内存消息总线。

type Server struct {
	Clients  map[string]*Client   // 在线客户端表（uuid → conn）
	mutex    *sync.Mutex          // 保护 Clients
	Transmit chan []byte          // 消息转发总线
	Login    chan *Client         // 登录通道
	Logout   chan *Client         // 退出登录通道
}

Start() 是一个单 for-select 主循环，一次性消费登录、登出、消息三个通道：

for {
	select {
	case client := <-s.Login:          // 登录：登记 + 欢迎语
		s.Clients[client.Uuid] = client
	case client := <-s.Logout:         // 登出：移除 + 提示
		delete(s.Clients, client.Uuid)
	case data := <-s.Transmit:         // 消息：真正的核心处理
		// 反序列化 → 持久化 → 在线投递 → Redis 回写
	}
}

它只有一个架构师级的优雅之处：Transmit 通道让「任意连接产生的消息」都汇聚到唯一的事件循环里处理，天然避免了并发写 map 的数据竞争（所有对 Clients 的操作都在主循环完成，加锁粒度很小）。

知识点：事件循环 + 单消费者
把并发模型收敛成「多个生产者（各连接） → 单消费者（主循环）」，好处是所有共享状态（在线表）都在一个 goroutine 里被访问，正确性大幅提升，也不需要处理复杂的锁嵌套。这是「Actor / 事件总线」思路在单机 Go 里的经典落地。

5.1 在线投递的逻辑

处理消息时分单聊 / 群聊两条路径，判定标准是接收方 ID 前缀（详见第 8 节）：

  • 单聊（ReceiveId[0] == 'U'）：在线则 receiveClient.SendBack <- messageBack，同时后端替发送者做回显（因为前端 store 只能存 rsp 不能存 req，注释明确写了「后端回显，前端不回显」）。
  • 群聊（ReceiveId[0] == 'G'）：把 group.Members（JSON 数组）反序列化成 []string，遍历投递给每个在线成员。
var members []string
json.Unmarshal(group.Members, &members)   // Members 是 json.RawMessage 存 JSON 数组
for _, member := range members {
	if member != message.SendId {
		if rc, ok := s.Clients[member]; ok { rc.SendBack <- messageBack }  // 其他人
	} else {
		s.Clients[message.SendId].SendBack <- messageBack                    // 发送者回显
	}
}

知识点：为什么 Redis 只写不读（此处）
在线消息走的是 WebSocket 实时推送；Redis 里的 message_list_* 只负责缓存历史，让「切换会话 / 二次拉取」从内存命中而非每次打 DB（详见第 6 节）。IM 系统要理解清楚哪条链路是实时、哪条是持久/缓存，才不会出现冗余双写。

6. 核心五：Kafka 模式 —— 从单机到分布式的一小步

Channel 模式单机很爽，但一个实例里所有连接共享一条内存总线，横向扩展就受限了。Kafka 模式（internal/service/chat/kafka_server.go + internal/service/kafka/kafka_service.go）用消息队列把「生产」和「消费」解耦。

6.1 生产端：每个连接都是生产者

在 Read() 里，WriteMessages 把消息写进 chatTopic。Writer 配置值得注意（kafka_service.go）：

k.ChatWriter = &kafka.Writer{
	Addr:  kafka.TCP(kafkaConfig.HostPort),
	Topic: kafkaConfig.ChatTopic,
	Balancer: &kafka.Hash{},          // 根据 key 哈希分区，保证同 key 有序
	RequiredAcks: kafka.RequireNone,  // 不强制等待 ack，高吞吐
	AllowAutoTopicCreation: false,    // 不让自动建 topic，防止误建
}

6.2 消费端：单 goroutine 消费 + recover 兜底

KafkaServer.Start() 里，用一个 goroutine 持续拉取 KafkaReader.ReadMessage，对每条消息走与 Channel 模式完全相同的持久化 + 投递 + Redis 逻辑（代码高度复用）：

for {
	kafkaMessage, err := kafka.KafkaService.ChatReader.ReadMessage(ctx)
	// topic/partition/offset/key/value 都打日志，方便回溯
	var chatMessageReq request.ChatMessageRequest
	json.Unmarshal(kafkaMessage.Value, &chatMessageReq)
	// ... 与单机模式同样的：存库 → 在线投递 → Redis 回写
}

两个生产级细节：

  • 每个 goroutine 用 defer + recover() 捕获 panic，避免单条异常消息把整个消费协程打死（代码里明确写了 kafka server panic 的日志）。
  • Reader 配置了 GroupID: "chat"、StartOffset: kafka.LastOffset，意味着多个实例可以同属于一个消费组——这正是后续做多实例横向扩展的基础。

知识点：Channel vs Kafka，IM 架构怎么选

维度 Channel 模式 Kafka 模式
依赖 无外部中间件 需要 Kafka 集群
延迟 内存级，极低 引入网络/队列延迟
横向扩展 受限（单机内存总线） 消费组支持多实例
适用 学习 / 单机小规模 分布式 / 高吞吐生产

而本项目两者共用一套业务处理逻辑，靠 messageMode 切换——这就是第 3 节「配置驱动」带来的红利。

7. 核心六：消息的持久化与投递闭环（MySQL + Redis 双写）

IM 最怕丢消息。本项目用「在线投递 + 落库 + Redis 缓存 + 离线回补」把消息生命周期串起来。以文本消息为例（server.go）：

// ① 构造消息并落库（status 初始为 Unsent）
message := model.Message{
	Uuid: "M" + random.GetNowAndLenRandomString(11),
	SessionId: ..., Type: ..., Content: ..., SendId: ..., ReceiveId: ...,
	Status: message_status_enum.Unsent,
}
dao.GormDB.Create(&message)

// ② 在线投递（见第 5 节）：成功后再把 status 置为 Sent
// ③ Redis 追加缓存，供二次拉取
rspString, _ := myredis.GetKeyNilIsErr("message_list_" + message.SendId + "_" + message.ReceiveId)
var rsp []respond.GetMessageListRespond
json.Unmarshal([]byte(rspString), &rsp)
rsp = append(rsp, messageRsp)
rspByte, _ := json.Marshal(rsp)
myredis.SetKeyEx("message_list_"+message.SendId+"_"+message.ReceiveId, string(rspByte), time.Minute*constants.REDIS_TIMEOUT)

离线消息靠「先落库」保证不丢：接收方不在线时消息落库，对方登录后调用 GetMessageList（internal/service/gorm/message_service.go）按需回补。而 GetMessageList 遵循 Cache-Aside：先查 Redis，miss 则查库，用 errors.Is(err, redis.Nil) 判断「键不存在」走 DB：

rspString, err := myredis.GetKeyNilIsErr("message_list_" + userOneId + "_" + userTwoId)
if err != nil {
	if errors.Is(err, redis.Nil) {        // Redis 没有缓存 → 查库
		dao.GormDB.Where("(send_id = ? AND receive_id = ?) OR (send_id = ? AND receive_id = ?)",
			userOneId, userTwoId, userTwoId, userOneId).
			Order("created_at ASC").Find(&messageList)
	}
}

知识点：Cache-Aside 与消息一致性
本项目的思路是：实时靠 WebSocket，历史靠 Redis 缓存，兜底靠 MySQL。一条消息被写入后同步更新 Redis 缓存，保证「切会话、翻历史」走内存。值得留意的是，代码里有相当多 SetKeyEx（写缓存）被注释掉，说明它是「缓存已实现、按需开启」的半成品——这恰恰是博客里可点评的优化空间（见第 12 节）。

8. 核心七：UUID 前缀语义化驱动的路由分发

这是本项目贯穿全系统、最简洁有效的标识设计：一切实体都用带前缀的 UUID 标识。

前缀 含义 示例
U 用户 Uxxxxxxxxxx
G 群组 Gxxxxxxxxxx
S 会话 Sxxxxxxxxxx
M 消息 Mxxxxxxxxxx

它的红利在消息路由里零成本地发挥了作用——不需要查 DB，只看 ReceiveId[0] 就能决定走单聊还是群聊：

if message.ReceiveId[0] == 'U' {   // 单聊
} else if message.ReceiveId[0] == 'G' {  // 群聊
}

知识点：语义化主键 / 前缀分型
用「前缀 + 长度固定」的字符串做主键，好处是：任何地方拿到 ID 就知道对象类型，还能天然分区（不同前缀可路由到不同存储）。对 IM 这种频繁查询实体类型的场景，比独立的 type 字段更省一次判断、更省一次查询。这是从「能跑」走向「简洁优雅」的一个小设计观。

9. 核心八：认证 —— Redis 验证码的一次性消费

登录/注册的验证码闭环是一个完整的「Redis 防重发 + 一次性消费」范例（internal/service/sms/auth_code_service.go + internal/service/gorm/user_info_service.go）。

9.1 发送验证码（sms.VerificationCode）

key := "auth_code_" + telephone
code, _ := redis.GetKey(key)
if code != "" {
	return "目前还不能发送验证码，请输入已发送的验证码", -2   // 已有有效码 → 防重发
}
code = strconv.Itoa(random.GetRandomInt(6))              // 6 位随机码
redis.SetKeyEx(key, code, time.Minute)                    // 1 分钟过期
// 封装短信模板并调用阿里云 SendSmsWithOptions

9.2 消费验证码（Register / SmsLogin）

登录/注册时校验收证码后立即删除，确保一次性：

code, _ := myredis.GetKey("auth_code_" + req.Telephone)
if code != req.SmsCode {
	return "验证码不正确，请重试", -2
}
myredis.DelKeyIfExists(key)   // 一次性：用完即删

短信 SDK 用惰性单例建客户端（createClient），AK/SK 从配置读取，Endpoint dysmsapi.aliyuncs.com。

知识点：验证码的两把钥匙
① 防靡发：已有未过期验证码就直接拒绝重发（用 Redis TTL 做节流）；② 一次性：消费后立刻删 key，防止重复使用。另外代码注释里那句「手机号验证，最后一步才调用 api，省钱」，是工程上很真实、很接地气的成本取舍——不是所有流程都要优先考虑 API 消耗，但故意把昂贵调用后置、或复用已验证状态，都值得借鉴。

10. 核心九：社交关系与群聊管理 —— 状态机设计

IM 的「联系人和群」不是简单的外键表，而是一张带丰富状态位的关系状态机。核心在 internal/service/gorm/user_contact_service.go / group_info_service.go，关键枚举在 pkg/enum/contact/contact_status_enum：

// 联系人状态（简化示意）
NORMAL          // 正常
BE_BLACK        // 被拉黑
BLACK           // 我拉黑了对方
BE_DELETE       // 已被删除
DELETE          // 我删除了对方
SILENCE         // 被禁言
QUIT_GROUP      // 已退群
KICK_OUT_GROUP  // 被踢出群

这些状态位直接驱动诸如 CheckOpenSessionAllowed（能否打开会话）等判断，而群聊又有自己的「加群方式」枚举（DIRECT 直接进群 / AUDIT 需审核）。

知识点：关系即状态机
「谁拉黑了谁」「谁被禁言」「谁退群了」这些关系，很适合做成一张关系表 + 状态位而不是一堆布尔字段。好处是：新增一种关系状态只需加一个枚举分支，且能统一承载权限判断逻辑（被拉黑/被禁言/被踢出 → 不能打开会话）。把「权限」建模成「状态」，是社交类系统一个成熟的做法。

11. 后台管理：管理员的能力边界

后台管理能力集中在 user_info_service.go 的几个方法，最值得讲的是 级联软删除。

以 DeleteUsers / DisableUsers 为例，删/禁一个用户不只是改一个 status，而是级联把该用户关联的会话软删除（gorm.DeletedAt 置为有效），保证被删用户的会话列表不再可见：

uid := user.Uuid
GormDB.Where("send_id = ? or receive_id = ?", uid, uid).Find(&sessionList)
for _, session := range sessionList {
	session.DeletedAt.Valid, session.DeletedAt.Time = true, time.Now()
	GormDB.Save(&session)
}
// 再级联删联系人关系、删申请记录…

而管理员看全量用户（含已软删除的）时用 Unscoped() 绕过软删除过滤：

GormDB.Unscoped().Where("uuid != ?", ownerId).Find(&users)   // 连软删数据一起给管理员看

知识点：软删除的价值与代价
用 gorm.DeletedAt 做软删除，是为了保留审计痕迹、支持恢复，代价是几乎所有查询都要记得排除软删数据（GORM 默认自动过滤）。这里又叠加了「业务级删除」——Service 层显式置 DeletedAt 来实现级联，思路清晰。但也要注意：禁用用户后仅软删会话、未清 Redis 缓存（相关 DelKeysWithPrefix("contact_user_list") 被注释），会导致缓存里仍残留旧状态，属于一个真实的工程取舍点。

12. 工程韧性：那些让 IM 真正能用的「脏活」

聊了这么多华丽的功能，最后必须强调——真正拉开生产级与 Demo 差距的，都是不起眼的工程细节。

12.1 路径归一化（server.go 的 normalizePath）

消息里发送者头像经常是 https://ip:port/static/xxx，直接入库会导致同一张图因 IP 前缀不同而不一致。一个 3 行函数把它规约为 /static/xxx：

staticIndex := strings.Index(path, "/static/")
if staticIndex < 0 { zlog.Error("路径不合法") }
return path[staticIndex:]   // 只要从 /static/ 开始的部分

这类「看着不起眼、漏了必踩坑」的细节，恰恰是 IM 头像/文件路径体系容易出现脏数据的地方。

12.2 统一日志（pkg/zlog + zap + lumberjack）

所有分支都有日志，区分 Info / Debug / Error / Fatal，错误场景全部 zlog.Error(err.Error())。配合 docs/业务逻辑.md 的约定——业务问题记日志不抛前端，系统问题才抛——排查问题时有据可循。

12.3 安全注意事项（可改进项，也是很好的反思素材）

  1. 密码明文比对：Login 里 user.Password != password，未见哈希——生产必须用 bcrypt。
  2. 上传文件名未消毒：UploadFile 直接 os.Create(staticFilePath + "/" + fileHeader.Filename) 保存前端原始文件名，未做白名单/随机重命名/路径穿越校验，存在任意文件上传风险；且 FILE_MAX_SIZE（50000 字节 ≈ 48KB）偏小。
  3. CheckOrigin 全放行：WebSocket 握手不校验来源，生产应白名单。
  4. DeleteAllRedisKeys：优雅退出用 SCAN 清空整个 Redis，隐含”部署即单租户”假设，生产不可复用。
  5. Redis Keys 命令：批量删除多处用 Keys 模式匹配，大数据量有性能隐患（DeleteAllRedisKeys 已正确改用 SCAN，可作为正面对比）。

14. 后端工程师的几点心得

  1. 长连接是 IM 的地基，Channel 是它的骨架。 用「多生产者 → 单消费者事件循环」把并发收敛起来，共享状态就只剩一个 goroutine 在管，正确性直线上升。
  2. 抽象要可配置，而非硬编码。 一个 messageMode 就让单机版和分布式版共用一套业务逻辑。先把「技术选型」抽成配置，后续演进会非常轻松。
  3. 消息链路要想清楚「哪条是实时、哪条是兜底」。 实时走 WebSocket、历史走 Redis、兜底走 MySQL，三者各司其职，才不会重复设计或丢消息。
  4. 前缀即语义。 U/G/S/M 一个字符换来全系统类型路由的简洁，是「小设计、大价值」的典型。
  5. 状态 vs 权限，用状态机而不用一堆 if。 拉黑/禁言/退群/踢出，越往后加越依赖清晰的状态模型。
  6. 生产级的差距在脏活。 密码哈希、上传消毒、来源校验、缓存一致性——这些才是把 Demo 变成产品的地方。
